# API универсального планировщика

API работает на том же origin, что и интерфейс. Локальный запуск по умолчанию: `http://127.0.0.1:4317`. JSON-запросы передают `Content-Type: application/json`. Изменяющие запросы передают HTTP/HTTPS `Origin`, совпадающий с host приложения. HTTPS-прокси сохраняет исходный `Host` и `Origin`.

Ответ на ошибку: `{ "error": "Сообщение", "code": "код", "details": [] }`, где `details` присутствует при необходимости. Основные статусы: 400 — неверные данные, 401 — требуется вход, 403 — недостаточно прав, 404 — объект недоступен или отсутствует, 409 — конфликт версии или состояния, 413 — превышен размер, 429 — временная блокировка попыток входа.

## Авторизация и доступ

При привязке к `127.0.0.1`, `::1` или `localhost` локальное соединение с допустимым Host получает локального владельца. Чужой Host и cross-site изменения отклоняются. При привязке к публичному интерфейсу, включая `0.0.0.0`, API требует зарегистрированный аккаунт и cookie. Локальный обход прав при публичной привязке отсутствует.

Пароли сохраняются как scrypt-хеши с индивидуальной солью. Cookie `planner_session` имеет `HttpOnly`, `SameSite=Strict` и срок семь дней; сервер хранит только хеш токена. Для запросов с HTTPS origin cookie получает `Secure`. Сам сервер слушает HTTP; публичный HTTPS обеспечивается внешним прокси. Лимит входа: восемь неудачных попыток на сочетание адреса подключения и email за пятнадцать минут.

Email вводит сам пользователь. API не отправляет письма и не подтверждает владение почтовым ящиком. Код приглашения передаёт владелец пространства через согласованный им канал. `User.pending: true` означает ожидающее приглашение в конкретное пространство.

| Роль     | Возможности                                                                                      |
| -------- | ------------------------------------------------------------------------------------------------ |
| viewer   | Чтение состояния, поиск, история, экспорт и скачивание файлов своего пространства                |
| editor   | Изменение объектов, связей, типов, ресурсов и правил; комментарии, сценарии и обработка сигналов |
| approver | Чтение, комментарии, решения по отправленным сценариям и обработка сигналов                      |
| owner    | Все действия, управление участниками, пространством и подключениями                              |

История проверяет **текущий** доступ к пространству. Удалённый участник не получает его данные через старые снимки, поиск, файлы или аудит. Уведомления в снимке относятся только к текущему пользователю.

| Метод и маршрут           | Запрос                                                          | Результат                                |
| ------------------------- | --------------------------------------------------------------- | ---------------------------------------- |
| GET `/health`             | —                                                               | Публичный статус SQLite и режима сервера |
| GET `/api/auth/me`        | —                                                               | `{user, mode, localModeAvailable}`       |
| POST `/api/auth/register` | `{email, password, displayName, invitationToken?, claimLocal?}` | 201, снимок и session cookie             |
| POST `/api/auth/login`    | `{email, password}`                                             | Снимок и session cookie                  |
| POST `/api/auth/logout`   | —                                                               | `{ok:true}`, cookie удалена              |

Пароль регистрации: 10–256 символов. `claimLocal:true` позволяет первому зарегистрированному аккаунту присоединить локальные пространства при регистрации из локального режима. Новый аккаунт без приглашения получает своё пустое личное пространство.

## Приглашения и участники

| Метод и маршрут                | Запрос                                     | Результат                                          |
| ------------------------------ | ------------------------------------------ | -------------------------------------------------- |
| POST `/api/memberships`        | `{workspaceId, email, role, displayName?}` | Снимок с одноразовым полем `invitation`            |
| POST `/api/memberships`        | `{workspaceId, userId, role}`              | Снимок; добавление известного участника по ID      |
| PATCH `/api/memberships`       | `{workspaceId, userId, role}`              | Снимок                                             |
| DELETE `/api/memberships`      | `{workspaceId, userId}`                    | Снимок; приглашение и доступ отозваны              |
| POST `/api/invitations`        | `{workspaceId, userId}`                    | 201, новый объект приглашения; прежний код заменён |
| POST `/api/invitations/accept` | `{invitationToken}`                        | Снимок вошедшего зарегистрированного аккаунта      |

Объект приглашения: `{userId, workspaceId, email, token, expiresAt}`. Код действует семь дней и возвращается только при создании или замене. База хранит его хеш; снимки, аудит и история код не содержат. Владелец может изменить роль ожидающего участника или отозвать приглашение.

Приглашение по email создаёт отдельную ожидающую запись для этого пространства, в том числе когда аккаунт с таким email уже зарегистрирован. Новый участник передаёт код в регистрацию; зарегистрированный — в `/api/invitations/accept` после входа. Email аккаунта должен совпадать с email приглашения. Принятие кода переносит роль, ответственного и участников связанных объектов на аккаунт только в указанном пространстве. Повторное использование, старый, просроченный, отозванный или чужой код отклоняется. Два пространства имеют разные ожидающие записи и разные коды. В пространстве всегда остаётся действующий владелец; ожидающее приглашение владельца его не заменяет.

## Состояние и объекты

Большинство изменений возвращают `PlannerSnapshot`: доступные пространства, участники, типы, объекты, зависимости, ресурсы, шаблоны, правила, сигналы, личные уведомления, комментарии, сценарии, аудит и настройки. `revision` — номер сохранённого изменения; `serverTime` — время сервера. Интерфейс может читать `GET /api/events` как SSE: события `ready` и `change` сообщают revision, после чего клиент запрашивает актуальное состояние.

| Метод и маршрут                              | Запрос                                                    |
| -------------------------------------------- | --------------------------------------------------------- |
| GET `/api/state`                             | —                                                         |
| GET `/api/history?at=<ISO>`                  | Сохранённое состояние на указанное время                  |
| GET `/api/audit?workspaceId=<id>`            | Аудит доступного пространства                             |
| GET `/api/search?q=<text>&workspaceId=<id>`  | Поиск по заголовку, описанию, тегам и полям               |
| POST `/api/workspaces`                       | `{name, mode:"personal"\|"team", timezone, description?}` |
| PATCH `/api/workspaces/<id>`                 | `{patch:{name?, timezone?, description?}, revision?}`     |
| DELETE `/api/workspaces/<id>`                | `{confirm:true, revision?}`                               |
| POST `/api/entities`                         | `{workspaceId, typeId, title, ...}`                       |
| PATCH `/api/entities/<id>`                   | `{version, patch:{...}, reason?}`                         |
| DELETE `/api/entities/<id>`                  | `{version}`                                               |
| POST/PATCH/DELETE `/api/dependencies[/<id>]` | Определение зависимости или `{patch, revision?, reason?}` |
| POST/PATCH/DELETE `/api/types[/<id>]`        | Определение типа или `{patch, revision?, reason?}`        |
| POST/PATCH/DELETE `/api/resources[/<id>]`    | Определение ресурса или `{patch, revision?, reason?}`     |
| POST/PATCH/DELETE `/api/rules[/<id>]`        | Определение правила или `{patch, revision?, reason?}`     |
| POST `/api/comments`                         | `{entityId, text}`                                        |
| DELETE `/api/comments/<id>`                  | —                                                         |
| PATCH `/api/settings`                        | `{notifications:{...}, lastSeenAt?}`                      |

Объект хранит `plan`, неизменяемый `baseline`, записанный `actual` и отдельный `forecast`. Диапазон: `{start:null\|ISO, end:null\|ISO, timezone, precision:"exact"\|"day"\|"month"\|"approximate"\|"unknown", earliest?, latest?}`. Для периодов/процессов с заданным временем требуется корректное окончание. Заметка без даты — полноценный объект; информационный сигнал об отсутствующей дате не создаёт напоминания и эскалации.

`version` защищает от потерянных изменений. Защищённые поля — ID, пространство, baseline, источник, происхождение прогноза и служебные даты/версия. Ручное создание не может объявлять объект полученным из webhook или импорта. Исправление дат завершённого факта требует причины. Родитель, владелец, участники, ресурсы, типы и файлы проверяются в пределах пространства. Циклы вложенности и зависимостей отклоняются. Встроенные типы сохраняются неизменными; используемый тип или ресурс нельзя удалить.

Повторение: `{frequency:"day"\|"week"\|"month", interval, weekdays?, count?, until?, exceptions:[], calendarPolicy?, durationPolicy?}`. `count` ограничен 100000. Политика `adjust` корректирует недопустимый календарный день; `skip-invalid` пропускает его. Длительность `calendar` (по умолчанию) сохраняет календарные дни, `elapsed` — точное прошедшее время: в ICS время `DTEND` задаёт точную длительность, а дни в `DURATION` — календарную, что учитывает переходы DST. Зона времени сохраняется. Бинарные вложения, ACL, комментарии, аудит и активные сценарии не экспортируются как резервная копия через CSV/ICS.

## Сценарии и сигналы

| Метод и маршрут                          | Запрос                                                     |
| ---------------------------------------- | ---------------------------------------------------------- |
| POST `/api/scenarios/preview`            | `{workspaceId, changes:[{entityId,plan}]}`                 |
| POST `/api/scenarios`                    | `{workspaceId, name?, reason?, changes:[{entityId,plan}]}` |
| POST `/api/scenarios/<id>/submit`        | `{reason?}`                                                |
| POST `/api/scenarios/<id>/approve`       | `{reason?}`                                                |
| POST `/api/scenarios/<id>/reject`        | `{reason?}`                                                |
| POST `/api/signals/<id>/ack`             | —                                                          |
| POST `/api/signals/<id>/resolve`         | —                                                          |
| POST `/api/signals/<id>/accept-risk`     | `{reason}`                                                 |
| POST `/api/signals/<id>/snooze`          | `{until:ISO}`                                              |
| POST `/api/notifications/<id>/delivered` | `{state:"delivered"\|"failed"}`                            |

Предпросмотр показывает затронутые объекты, зависимости, ресурсы и конфликты. Согласование меняет текущий план и сохраняет baseline/факт. Версии всех объектов пространства, его настройки, граф зависимостей, ресурсы и определения типов входят в контекст сценария. Изменившийся контекст помечает вариант `stale`; при согласовании последствия вычисляются повторно. Начатый или завершённый факт не переносится автоматически.

Вычисленный прогноз имеет `forecastProvenance:"derived"`. При исчезновении задержки он очищается, возвращая отображение к плану. Ручной прогноз имеет `"manual"` и сохраняется, даже если зависимость ему противоречит; противоречие становится сигналом.

`ack` подтверждает прочтение, сохраняя действующее условие. `resolve` отклоняется, пока условие сохраняется. Принятие риска требует причины. Отсрочка ограничена тридцатью днями. Браузерные и webhook-уведомления учитывают тихие часы в зоне пользователя, повтор и эскалацию; in-app остаются видимыми сразу. Сервер хранит очередь, ключи дедупликации и журнал выполнений правил в SQLite. Перезапуск не создаёт повторный follow-up; временно не доставленный webhook имеет ограниченные повторные попытки.

## Файлы, импорт и помощник

| Метод и маршрут                                          | Запрос / результат                                                                     |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| POST `/api/files`                                        | Multipart `{workspaceId, entityId?, file}`; до 20 МБ. Ответ `{id,url,label,size,mime}` |
| GET/HEAD `/api/files/<id>`                               | Скачивание при текущем доступе к пространству                                          |
| DELETE `/api/files/<id>`                                 | Удаление бинарных данных и ссылок из объектов                                          |
| POST `/api/import`                                       | `{workspaceId, format:"json"\|"csv"\|"ics", content}`                                  |
| GET `/api/export?workspaceId=<id>&format=json\|csv\|ics` | Файл с данными доступного пространства                                                 |
| POST `/api/templates/<id>/apply`                         | `{workspaceId, start:ISO, title?}`                                                     |
| POST `/api/assistant`                                    | `{workspaceId, text, start?}`; локальное предложение                                   |
| POST `/api/assistant/apply`                              | `{workspaceId, drafts}`; явно принятые объекты                                         |

Удаление объекта сохраняет файл, когда на него ссылается другой объект, и передаёт привязку оставшемуся объекту. Если ссылок больше нет, его файлы удаляются. Данные удалённых файлов не восстанавливаются просмотром истории. Файл другого пространства нельзя прикрепить ссылкой; внешние ссылки допускают HTTP/HTTPS.

Импорт выполняется одной транзакцией: ошибка JSON, даты, второго объекта, внешних ссылок или цикла отменяет весь импорт. Родители, связи, custom types и ресурсы сопоставляются внутри целевого пространства. JSON и CSV со служебными колонками `entityData`/`workspaceData` сохраняют модель, включая baseline, actual и forecast. CSV без этих колонок импортирует читаемые поля. ICS передаёт календарный план; неопределённое время и повторения с семантикой, несовместимой с календарём, отклоняются с предложением использовать JSON. Бинарные вложения исключаются из логического экспорта. Предупреждения экспорта находятся в заголовке `X-Planner-Warnings` как URL-encoded JSON-массив строк; импорт возвращает `importWarnings` вместе со снимком. Копии имеют новые ID и новую историю. Локальный помощник предлагает данные до применения и возвращает `provider:"local"`; внешний LLM или провайдер данных автоматически не подключается.

## Универсальный webhook

Подключение управляется владельцем пространства. Это универсальный вход/выход с документированным API, без автоматического подключения сторонних систем.

| Метод и маршрут                         | Запрос / результат                                                                               |
| --------------------------------------- | ------------------------------------------------------------------------------------------------ |
| GET `/api/connections?workspaceId=<id>` | Безопасный статус входа/выхода, endpoint и время обновления; токен не возвращается               |
| POST/PATCH `/api/connections`           | `{workspaceId, endpoint?, enabled?, regenerateToken?}`; входной токен только при создании/замене |
| DELETE `/api/connections`               | `{workspaceId}`; подключение отключается                                                         |
| POST `/api/webhooks/<workspaceId>`      | `Authorization: Bearer <token>`, `Idempotency-Key`, `{entities:[...]}`                           |

Каждый входной объект имеет `externalId`; по нему webhook создаёт либо обновляет объект собственного пространства. Обновление принимает title, description, plan, actual, forecast, status, dueAt, fields и tags; источник фиксируется сервером. Опциональная `version` проверяет конфликт. Один ключ идемпотентности с тем же содержимым возвращает `{ok:true,duplicate:true}`; другое содержимое под тем же ключом отклоняется. Владелец/редактор, создавший подключение, должен сохранять доступ для входа webhook.

Исходящий webhook передаёт ID уведомления, ID пространства, соответствующий сигнал, summary и occurredAt. Endpoint требует публичный HTTPS-адрес без логина в URL; локальные, приватные, IPv4-mapped и переходные IPv6-адреса отклоняются. DNS проверяется перед отправкой, подключение закрепляется за проверенным адресом, перенаправления не выполняются. Внешний ответ не попадает в аудит или пользовательскую ошибку.

## MCP и доступ агентов

`/mcp` обслуживает стандартный Streamable HTTP MCP: initialize, discovery, tools, resources и prompts. Подключение и восемь инструментов описаны в [MCP.md](../MCP.md). Stdio адаптер обращается к тому же серверу через `GET /api/agent/tools` и `POST /api/agent/call` (`{name, arguments}`). Изменения сохраняются в общей SQLite и появляются в интерфейсе через существующий поток событий.

Bearer ключ ограничивает доступ выбранными пространствами, сроком и read-only режимом; права аккаунта перепроверяются при каждом запросе. Он действует только на MCP и маршрутах agent tools/call, а не на остальных REST маршрутах. Отсутствие Origin разрешено протокольному клиенту MCP; переданный Origin и Host проверяются, включая GET. Cross-site запросы браузера отклоняются.

`GET /api/agent/keys` возвращает безопасный список ключей и параметры подключения. `POST /api/agent/keys` создаёт ключ владельца с `{name, workspaceIds, readOnly?, expiresInDays?}` и единожды возвращает секрет. `DELETE /api/agent/keys/<id>` отзывает его. Эти маршруты требуют обычной сессии сайта или локального owner режима; ключ MCP не выпускает новые ключи. Секреты и конфигурации с Authorization не должны попадать в логи или отчёты.

`POST /api/templates` принимает универсальный шаблон, проверяет типы, родителей, связи, даты и ресурсы до сохранения, возвращает снимок с кодом 201. Неуспешная проверка сохраняет прежнюю revision.

## Хранение и проверки

База по умолчанию — `data/planner.sqlite`; путь можно задать `PLANNER_DB_PATH`. `PLANNER_HOST` и `PLANNER_PORT` меняют интерфейс и порт. SQLite хранит состояние, до 2000 исторических ревизий, пароли/сессии/приглашения в хешированном виде, файлы, настройки, очередь уведомлений, исполнение правил и идемпотентность webhook. Для полной резервной копии остановите сервер и сохраните базу вместе с существующими WAL/SHM-файлами; логический экспорт не заменяет её.

Регрессионные проверки: `node --max-old-space-size=512 --import tsx --test --test-concurrency=1 server/server.test.ts`. Они используют отдельные временные базы и HTTP-порт 0, проверяют перезапуск, ACL, актуальные права истории/файлов, приглашения, сценарии, rollback импорта, прогнозы, тихие часы и устойчивую очередь.
