# Стандартный выпуск приложения в Сотах

Прочитай при первом полноценном выпуске или развитии бизнес-приложения в Сотах. Начинай применимые подключения вместе с основным приложением: вход и защищённое управление, приватная обратная связь, публичные отзывы Поведай, документы Переметрики, API/MCP для агента и понятный гид с настоящим видео. Явное ограничение текущего поручения имеет приоритет. Концепция без приложения, одиночная правка, DNS/TLS или повторная доставка уже принятого выпуска сохраняют свой объём.

## Сначала установить действительный контракт

Определи для каждой строки ниже применимость, текущие app/project/entity/resource IDs, владельца и аудиторию, Source/adapter revision, необходимые действия и существующие права. Читай актуальный контракт и реализацию соответствующего модуля; endpoint или UI из старого проекта не является готовым адаптером. Переиспользуй подключение только в той же границе владельца/проекта и полномочий.

В рамках уже порученного выпуска запускай доступные применимые подключения вместе с проектом и доводи их до проверяемого результата либо конкретного reviewable действия владельца. Уже порученная публикация не требует нового общего согласования. Существование инструмента, platform login, декларация capability и запись в манифесте не создают Native/project permission, consent или agent grant. Разрешение на чтение не расширяется до записи, отправки, публикации и управления командой. Отдельный запрос нужен для действительно новой security-sensitive авторизации/consent, когда его требует действующая browser policy и контракт; ранее подтверждённое действие повторно не согласуется. До такого завершающего шага подготовь модуль, точный ресурс, действие/получателя, требуемый grant/экран владельца и ожидаемую проверку, продолжая независимую работу. Выбор поверхности записи и подтверждение отправки выполняются по действующему контракту; общий стандартный комплект не заменяет реальный user gesture.

## Матрица подключения и доказательств

| Модуль | Граница результата | Минимальная проверка подключения |
|---|---|---|
| Soty identity и защищённая админка | Проверенная Human OIDC identity через серверный Source RP/BFF плюс отдельные предметные роли/tenant ACL; ingress cookie сам не сообщает human identity. Сохранить существующий доверенный вход и данные до проверенного перехода. | Реальный вход нужного участника → разрешённый API/UI → прежний объект → reload/новая сессия. Анонимный, чужой аккаунт/tenant и неподтверждённый identity header получают отказ; отзыв закрывает следующий запрос. Владелец Сот не становится владельцем другого Native приложения автоматически. |
| Приватная обратная связь проекту | Проблема/пожелание относится к выбранному приложению/проекту, имеет реального получателя и видимый результат. Приватные обращения остаются в рабочем контуре. | Контекст/receiver ACL → явная отправка безопасной проверочной записи → настоящий ID/receipt → чтение в правильном проекте после reload. Attachment preview/capture, очередь в браузере и нарисованное «успешно» не доказывают submit или дальнейшую агентную обработку. |
| Публичные отзывы Поведай | Правильная сущность бизнеса/продукта, существующий API и виджет через актуальный `povedai-reviews`; авторизация управления и правила модерации. | Реальное разрешённое чтение/действие → правильный entity/record ID → сохранность после reload → гостевой виджет показывает допустимый результат. Проверочная запись не изображает реальный отзыв клиента и не публикуется ради теста без соответствующего поручения. Приватный feedback сюда не переносится. |
| Документы Переметрики | Выбранная страница, версия библиотеки или иной подтверждённый документный ресурс в границах его Native ACL. Docs MCP требует отдельного grant; Soty/agent login его не создаёт. Возможность чтения, создания или редактирования определяется текущим адаптером. | Реальный разрешённый вызов по точному ресурсу → совпавшие структура/версия/ID → повторное чтение после reload; связь/конфигурация сохраняется. При read-only контракте не выполнять mutation для имитации проверки. Запись/экспорт/публикация проверяются отдельно, только если входят в поручение и доступны по контракту. Это подключение документов, а аналитика требует своей отдельной capability. |
| Agent API/MCP | Каталог реально доступных инструментов приложения с серверной авторизацией, точным ресурсом/tenant и scopes. Сессия или права агента проверяются собственным контрактом. | Обнаружить реальные tools/schema → выполнить безопасный разрешённый call → проверить фактический результат/ID → повторить чтение после reload. Для заявленной записи проверить её сохранение и отказ без требуемого scope. Нельзя обещать права всем имеющимся инструментам или выставлять admin mutations публично. |
| Гид и настоящее видео | Доступная из приложения оформленная инструкция показывает текущие реальные пути гостя и применимых ролей. Текст, видео и release относятся к одной принятой версии; coverage map покрывает заказанный объём; голос сверён с выбором пользователя. Недоступный модуль показан честно. | Учебная fixture → реальное действие и изменение UI → открытие гида нужной аудиторией → воспроизведение, chapter seek, Range, заявленные captions/подписи, мобильный плеер и reload → возврат fixture в исходное состояние. Приватные данные/секреты не раскрываются гостю. Короткий разовый ролик допускает простой capture; повторяемый каталог использует текущий `product-video-guide`. Полнота карты проверяется до сборки, а voice pilot — до массовой озвучки; ASR не доказывает прослушивание. |

Для каждого применимого модуля нужны четыре отдельных результата: **права**, **фактический вызов**, **сохранение результата или привязки**, **повторное чтение/reload**. Добавь отрицательный ACL-сценарий по риску. UI-кнопка, HTTP 200 корня, локальная fixture и наличие адаптера в репозитории не являются production-подключением.

До съёмки гида составь coverage map: все значимые разделы, действующие роли и применимые интеграции → действие → наблюдаемый результат → сцена/глава либо честное ограничение. Для «полного гида» сопоставь с ней весь запрошенный объём, а не только основной счастливый путь. Не изображай неработающие платежи, роли или UGC; отсутствие возможности объясняется без постановочного успеха. Перед приёмкой свяжи строки карты с финальными главами и доказательствами.

Для озвученного гида проверь выбор голоса по прямому поручению, прежнему принятому видео и проектному предпочтению пользователя; сохрани его в профиле проекта. До массового синтеза сделай короткий voice pilot и реально проверь голос/разборчивость на слух. Заказанный провайдер не подменяется системным TTS молча: недоступный канал означает точный блокер или явно согласованную замену. ASR сверяет текст, но не доказывает прослушивание или соответствие голоса. Немой обзор не требует TTS, а выбранный в одном проекте голос не становится общим default.

Платформенный Root OAuth/MCP и MCP самого приложения имеют отдельные состояния и полномочия. Недоступный Root transport не исправляется отключением проверки OAuth, ослаблением ролей/ACL или поддельной identity и не объявляется активным. Приложение может отдельно предоставить проверенный read-only MCP с допустимыми публичными/разрешёнными данными; это не доказывает работу Root OAuth или доступ к приватным документам/записи. Зафиксируй, какой именно контур и scope фактически проверен.

Допустимый самостоятельный адаптер — Node runtime, в том числе Node 24, с отдельными listener для UI/HTTP и read-only MCP. Два listener могут обслуживать один проект и его данные; это не требование создавать два приложения всем проектам. Отдельный app/ingress выбирай, если действующий gateway не может выразить требуемую границу аудитории/доверия одним допуском и раздельной серверной авторизацией; разные роли внутри приложения сами по себе не требуют второго app ID. Проверь реальные bind/route/TLS/auth, публичную read-only проекцию и закрытость admin/private API; общая codebase не объединяет разные аудитории автоматически.

## Статус и безопасный выпуск

Храни в приватной матрице выпуска для каждого модуля: contract/revision, безопасные IDs и scope, состояние, ссылки на evidence четырёх проверок, ограничения и следующий шаг. Используй различимые состояния: `not-applicable` с причиной, `unavailable` при отсутствии действующей capability/транспорта, `unconfigured` при недостающей конфигурации, `awaiting-permission` при конкретном недостающем праве, `configured` до сквозной проверки и `verified` по фактическим доказательствам. Сбой или недоступность не превращаются в verified; прежние рабочие данные/доступ сохраняются.

Подготовку и независимые части выпуска продолжай при недоступном отдельном модуле. Админка и приватные API остаются закрыты при непроверенной авторизации. Не объявляй весь стандартный комплект завершённым, пока применимые подключения ожидают прав или проверки; дай работающую часть и точный остаток, подготовленный для завершающего действия владельца.

Секреты хранятся только в предусмотренной приватной серверной/операторской среде. Токены, passwords, headers, sessions и grant payloads не попадают в `.soty/app.json`, source ZIP, public JS, URL, скриншот или release receipt. Строгая схема `.soty/app.json` сохраняется: она не расширяется произвольными `modules`, credentials или grants. Публичная страница видит только разрешённую проекцию; внутренняя матрица доказательств не становится публичной автоматически.

После изменения runtime/origin/identity повтори затронутые подключения на целевом HTTPS и проверь iframe/top-level, данные, роли и PWA. Включи безопасные module statuses/evidence в receipt принятого выпуска. Правила переноса секретов, rollback и границ существующей авторизации остаются в основном skill и `existing-data.md`.
