# Существующие данные и вход

Сначала отдели серверные данные от browser storage. Один серверный том не
переносит IndexedDB, localStorage, WebCrypto identity, local drafts и outbox
между разными origins. Смена поддомена создаёт новый origin даже на том же site.

## До изменения

- Прочитать фактический сервис, источник базы, mounts и публичный origin.
  Секреты разобрать локально/в памяти и выводить только whitelist.
- Зафиксировать project/app/domain IDs, revisions, права и hashes прежних строк.
  Полный приватный документ не включать в открытый receipt.
- Зашифровать конфигурацию; при миграции данных — согласованный encrypted backup
  с проверкой restore и SQLite WAL/SHM. Запись копии sqlite без WAL не считать
  гарантированным резервированием.
- Подготовить совместимый откат с текущей базой и доступный прежний браузерный
  entry. Не отзывать старые device keys ради подключения нового адреса.

## Выбор входа

Обычный gateway изолирует приложение: он фильтрует Cookie/Authorization/Origin
и ограничивает CSP/workers. Если приложение рассчитывает на собственную
HttpOnly cookie или OAuth, проверь native fixed ingress. Не ослабляй общий
gateway, чтобы сделать один проект работоспособным.

Native приложение обязано само проверять приватные API и Origin/CSRF.
Проверь точные callback URLs и допустимых frame ancestors; сохранить прежние
callbacks/issuer/security settings. Cookies — host-only/Secure/HttpOnly с
подходящим SameSite, без Domain на весь site.

Новый browser identity связывать только штатной подтверждённой процедурой
приложения. Для HIVE существует ограниченный двусторонний challenge/proof bridge
между прежним origin и точным активным HIVE iframe. Он не является общим
экспортом ключей для других проектов. Private key остаётся в прежнем хранилище.
Для другой аппки разработать её штатный перенос/вход; не подменять новым пустым
аккаунтом и не присваивать owner ID напрямую в базе.

## Проверка

На отдельном проверочном объекте: прежний ID → чтение во встроенном новом входе →
запись → reload → чтение той же записи через прежний вход.
Дополнительно сравнить прежние строки/ACL/device keys и валидность базы.
Количество объектов само по себе не доказывает сохранность.

Несинхронизированные drafts/outbox остаются в старом entry до отдельно
проверенного переноса. Не очищать storage и не удалять этот вход. Пользовательское
полотно/данные не редактировать ради проверки, если есть отдельный fixture.

HIVE structured mutations выполнять по его AGENTS/HIVE_FORMAT/AGENT_BRIDGE:
полный read, stable IDs, минимальный atomic batch, expectedRevision и
requestId только для того же намерения. Обычная публикация проекта не требует
изменять содержимое его полотен.
