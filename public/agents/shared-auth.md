# Общий вход приложений Сот

Внутри Сот стандартный вход приложения — уже выбранный аккаунт конкретного окна.
Это правило для любого автора, аккаунта и агента, даже без истории чата.
Не создавайте отдельные пароли или регистрацию, не переносите вход в отдельную вкладку
и не выбирайте человека по общему cookie приложения. Публичность карточки не открывает
чужие данные. Внешний сайт с отдельным входом — самостоятельный, явно заказанный сценарий,
который не заменяет встроенный вход Сот.

## Сначала проверить установленную цепь

1. На доверенном сервере Сот прочитайте `/.well-known/soty-app-platform`,
   `/api/apps/capabilities` и `/sdk/source-app/index.json`.
   В `authentication` ожидается schema `soty.app-authentication-capability.v1`,
   default `soty-window` и contract `soty.relay-window-identity.v1`.
   Проверьте действующие Root, оболочку, коннектор выбранного устройства и browser/server SDK.
   Наличие карточки, ingress-cookie, `humanIdentityConfigured:true` или SDK-архива
   само по себе не доказывает совместимость оконного входа.
2. Установите portable `@soty/source-app` по URL из SDK index, проверив точные
   размер и SHA-256 до исполнения кода. `productionReady:false` нельзя переименовать
   в готовность. Раздел `admission` относится к Source/workspace2; общий relay-вход
   проверяется по своему действующему контракту. Не выдумывайте npm-публикацию пакета.
3. Используйте `appId` текущей регистрации и `issuer` доверенного Root. Не берите
   их из произвольного сообщения iframe, URL пользователя или собственного JSON запроса.
   Сохраните проверенные версии и диагностический код, без cookies, токенов и proof.
4. Под текущим аккаунтом выполните подписанный `apps.authentication.get`
   с `{appId,expectedAccountId}`. Ответ `soty.app-authentication-status.v1`
   относится к точному доступному приложению и его коннектору. Прочитайте `missing`;
   `supported:true` подтверждает только конфигурацию компонентов.
   `endToEnd:not_checked` не является успешной проверкой browser/server SDK
   конкретного приложения. Повторите проверку после смены Source/коннектора.

**Остановите подключение**, если недостаёт поддержки Root, оконной оболочки,
коннектора, browser SDK, server SDK или доверенной конфигурации. Сообщите, какой
компонент проверен, его версию, требуемый контракт и безопасный код отказа.
Не заменяйте отказ своей формой входа, общим cookie, локальным user 1, заголовком
из браузера или отдельной Native-вкладкой. `/_soty/session` с `ok:true` — не `/me`.

## Новое приложение: штатный starter

После проверенной установки SDK в новую `.soty-sdk` выполните в новой папке проекта:

```text
node .soty-sdk/dist/install.mjs starter --title "Моё приложение" --port 30000
```

Команда готовит сервер, встроенный интерфейс, `.soty/app.json` и конфигурацию
`.soty/app-auth.json` с общим входом;
не запускает публикацию и не назначает чужие роли. В сгенерированном README
запишите `appId` и доверенный `issuer` из регистрации и подписанной проверки
в `.soty/app-auth.json`, затем для новой базы выполните `node app/server.mjs --initialize`.
Следующие запуски — `node app/server.mjs`, данные остаются в `data/`.
`--initialize` относится только к новой базе; не применяйте его к существующему
проекту или данным. Starter входит в обновлённый SDK:
если установленная CLI не знает эту команду, проверьте индекс/версию, не создавайте
свою регистрацию и пароли. Существующему приложению подключите те же browser/server
проверки ниже, сохранив его модель данных и членства.

## Браузер приложения

После установки используйте существующий browser SDK для защищённых HTTP-запросов:

```js
import { createRelayIdentityFetch } from '@soty/source-app/browser';

const sotyFetch = createRelayIdentityFetch();
const response = await sotyFetch('/api/me');
if (!response.ok) throw new Error('soty_signin_unavailable');
const me = await response.json();
```

SDK получает доверенную конфигурацию от Root и оконное разрешение только от
точного родителя. Не подставляйте `*` или произвольный `parentOrigin`.
Обычный `fetch`, localStorage с userId и событие загрузки iframe не заменяют этот путь.
Окно при смене профиля остаётся связано с прежней личностью либо получает отказ,
а не принимает другого человека по cookie. Для двух окон одного app-origin код
самого приложения считается доверенным; взаимно недоверенные приложения размещают
на отдельных origin.

## Сервер приложения

Создайте один проверяющий модуль на процесс с проверенными настройками:

```js
import { createSqliteRelayIdentity, createAppAccess } from '@soty/source-app/server';

const identity = createSqliteRelayIdentity({
  issuer: trustedSotyIssuer,
  appId: registeredSotyAppId,
  databasePath: absoluteDedicatedNonceDatabasePath,
});
const access = createAppAccess({ database: existingAppDatabase, appId: registeredSotyAppId });

// В каждом защищённом обработчике, до чтения или изменения данных:
const person = await identity.verify(req); // { issuer, subject }
const proof = access.capture(person, resourceId);
const result = access.withAccess(proof, { roles: ['owner', 'editor', 'viewer'] }, context => {
  // Только синхронные операции с context.database и указанным ресурсом.
  return context.database.prepare('SELECT body FROM my_records WHERE app_id=? AND resource_id=?')
    .all(context.appId, context.resourceId);
});
```

`trustedSotyIssuer`, `registeredSotyAppId` и путь задаёт доверенная серверная
конфигурация. Таблица `my_records` — пример существующей таблицы приложения,
не таблица Сот. `createAppAccess` один раз подключается к собственной базе
приложения; `initialize:true` используется только для явного создания его ACL.
Для существующего предметного ACL допустим его проверенный серверный адаптер.
Подключите реальный ACL до публикации; отсутствие ACL означает отказ, а не роль владельца.
Проверяйте права каждого действия, включая прямые API и фоновые операции.

SDK проверяет подпись, issuer, приложение, метод, путь, срок и одноразовость proof.
Его SQLite-файл — отдельная защищённая база SDK, не существующая БД приложения.
Все процессы одного хоста используют один durable nonce store; для нескольких
хостов применяется `createRelayIdentityVerifier` с общим атомарным `consume`.
Не используйте in-memory fallback. При штатной остановке вызовите `identity.close()`.
Ошибка проверки личности не становится анонимным успехом; недоступное хранилище
не превращается в новый аккаунт.

## Роли и существующие данные

Устойчивая личность — пара `(issuer, subject)`. Роль в платформе, владение сотой,
публичность приложения и подтверждённый вход не создают членство в чужой команде.
Право открыть приложение и право читать CRM-записи — разные проверки.
Роли команды назначает только её действующий уполномоченный участник через
серверное API приложения. Проверяются его текущая роль, команда и допустимость
новой роли. Понижение и отзыв должны закрывать следующий защищённый запрос,
в том числе из ранее открытого окна;
уже отправленный эффект требует проверки результата, а не слепого повтора.

Для новой модели доступа используйте тот же `createAppAccess`, не отдельную систему
паролей. Явное создание новой команды — `access.createResource(person, resourceId)`;
повторный захват существующей команды не создаёт владельца. Не вызывайте
`createResource` для существующей CRM-команды лишь потому, что её ещё нет в новых
ACL-таблицах. Для новой команды сервер создаёт новый resourceId в штатном
процессе приложения; чтение неизвестного ID не создаёт ресурс или роль. Существующие команды
импортируются только с подтверждёнными владельцами и прежними правами. В отдельном
авторизованном запросе назначение и понижение выполняет текущий владелец:

```js
const ownerProof = access.capture(await identity.verify(req), resourceId);
access.setRole(ownerProof, verifiedInvitedPerson, 'editor'); // owner | editor | viewer
// В следующем запросе заново verify + capture, затем:
access.setRole(freshOwnerProof, verifiedInvitedPerson, 'viewer');
// Отзыв в отдельном запросе с новым proof:
access.revoke(freshOwnerProofForRevoke, verifiedInvitedPerson);
```

`verifiedInvitedPerson` — подтверждённые `{issuer,subject}` из настоящего процесса
приглашения, не email и не роль из браузера. Старые proof после понижения/отзыва
не подходят, даже если роль позже вернули. Последнего владельца нельзя отозвать
или понизить: сначала явно назначьте другого владельца. `withAccess` повторяет
проверку внутри транзакции той же базы; callback обязан быть синхронным и не
использовать внешнюю открытую транзакцию. Эти роли принадлежат конкретному
приложению/ресурсу; они не являются платформенными ролями и не дают прав на чужую CRM.

При миграции сохраните прежние аккаунты, ID, записи, ACL и резервную копию.
Связывание старого аккаунта с `(issuer, subject)` требует доказательства владения
обоими аккаунтами. Совпадение email, имени или владение карточкой таким доказательством
не является. Непривязанный аккаунт показывает ограниченное состояние подключения,
не создаёт молча пароль и не получает чужую роль. Старые данные не удаляются.

## Приёмка до объявления готовности

- Чистый агент находит эту инструкцию через опубликованный discovery без истории чата.
- Из соты открывается настоящий интерфейс без отдельного логина; разрешённые данные
  сохраняются после reload. Два пользователя не видят записи друг друга.
- Старое окно при смене профиля не получает данные нового человека.
- Назначение, понижение и отзыв роли проверяются на сервере; старый запрос после
  отзыва отказывает. Владелец платформы без членства не получает чужие данные.
- Неверный issuer/appId/метод/путь, повтор, истёкшее разрешение, отозванное устройство
  и несовместимый коннектор дают отказ; сохранённые запросы не обходят текущие права.
- Один и тот же сценарий проверен в desktop и узком PWA; физический телефон,
  browser emulation, локальный стенд и production отмечены раздельно.

Документ не развёртывает компоненты, не регистрирует OIDC-клиентов и не выдаёт прав.
Проверка исходников или скачивание SDK не заменяют приёмку фактических установленных
Root, оболочки, коннектора и приложения.
