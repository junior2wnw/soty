# Один аккаунт на нескольких устройствах

## Основной путь

1. На новом устройстве: **Профиль → Открыть прежний аккаунт**. QR появляется сразу.
2. На прежнем устройстве: отсканировать QR, сверить аккаунт и код, нажать **Подтвердить вход**.
3. Новое устройство открывает аккаунт само. Оба устройства продолжают работать.

На новом устройстве нет кнопок «Проверить подтверждение» и повторного «Открыть».
Сканер Сот сразу открывает единственное подтверждение входа. Обычная камера
может открыть ту же ссылку. Автозавершение действует только для QR, который
человек явно запросил на этом устройстве; сканирование не выдаёт доступ само.
Созданный автоматически аккаунт сохраняется отдельно вместе со своими данными.

## Другие способы

Под QR расположен **Другой способ**: ссылка, файл восстановления, логин с
паролем, фраза. Ссылка ведёт к тому же подтверждению на прежнем устройстве.
Файл открывает аккаунт своим проверенным ключом. Логин/пароль и фразу нужно
заранее настроить в **Профиль → Безопасность → Восстановление профиля**.
Эти способы независимы; отключение пароля не отключает устройства, QR или файл.

Пароль: 15–256 символов Unicode. Фраза: 20–1024, любой язык, без заданного
словаря или требования пробелов. Используется NFC; у фразы пробелы по краям
удаляются, повторные пробелы объединяются. Пароли не обрезаются и не меняют
регистр. Логин содержит 3–80 символов и приводится к нижнему регистру.
Длина сама по себе не гарантирует стойкость: нужен длинный уникальный секрет.

## Модуль и сохранность

Общий browser Connect client владеет ключами и входом; приложения продолжают
получать прежнюю устойчивую личность через Соты. Для каждого нового устройства
создаются отдельные ключи. Сервер не получает пароль, фразу или открытый root.
PBKDF2-HMAC-SHA256 600000, отдельные HKDF-домены, AES-GCM с привязкой к аккаунту,
проекту и способу входа. Серверные проверки привязаны к подписанному получателю.
Публичный зашифрованный descriptor допускает офлайн-подбор слабого секрета и
корреляцию account ID; generic ошибка не является обещанием полной анонимности.

Connect5 — аддитивное расширение хранилища. Выпуск требует заранее проверенного
reader5 bridge, полного encrypted backup, off-host copy/restore proof и
квалификации обоих точных images. Старый reader4 image не допускается к DATA5
по старой декларации. UI/API выпускаются согласованно; downgrade DATA не нужен.
HTML входа выдаёт backend, а его assets обслуживает текущий UI release.
Перед каждым backend-переключением нужен asset-only bridge с сохранением старых
index/worker, затем готовность API и финальный UI по
[порядку раздельного выпуска](../deployment/ui-release.md#порядок-при-раздельном-выпуске-backend-и-ui).

При повторном открытии подтверждённо просроченный QR заменяется автоматически;
пока окно открыто, код сам не меняется. Потерянный ответ проверяется по прежнему
запросу; при неизвестном результате замены нет. Очистка известного pending защищена
точным запросом, локальной ревизией, активным профилем и отменой перед записью.
Закрытие окна прекращает ожидание и
локальную активацию, но не отменяет уже принятый сервером запрос. Подтверждённый
запрос можно продолжить после открытия окна. A→B→A и отмена во время очереди
IndexedDB проверяются по ревизии и внутри транзакции. Ошибка запасного способа
возобновляет прежний QR.

Основания выбора KDF и работы с Unicode:
[OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html),
[NIST SP800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html).
Реализация не заявляет формальную сертификацию по этим стандартам.
