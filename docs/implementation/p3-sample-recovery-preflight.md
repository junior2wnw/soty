# P3-R4: сохранность ввода и восстановление примера

30.09.2026. Read-only preflight к [плану liveness](p3-runtime-liveness-plan.md). Пример и runtime не изменялись; реализация R4 начинается после R1–R3. Это восстановление небольшого независимого приложения, не замена платформенного heartbeat и не новая система сообщений.

## Установленное поведение

[sample-app.mjs](../../modules/apps/examples/sample-app.mjs), SHA256 `a15d474b3f11056dcc98ca203c258268ade6fe9762019df994499f737807170e`:

- Строка 49 очищает поле сразу после начала POST, до ответа. Нет catch и проверки `response.ok`.
- Строка 48 при любом WS close отключает все input/button, включая несданный текст; восстановления нет. Значение остаётся в DOM, но человек не может нормально продолжить работу.
- Строка 46 отправляет неидемпотентный toggle; повтор такого POST способен отменить первый эффект. POST добавления также не имеет request ID/receipt — повтор может создать дубликат.
- GET, WS snapshot и POST response независимо перерисовывают список. При восстановлении нужно исключить поздний ответ старого соединения и перерисовку более нового списка старым HTTP ответом.

Выполнен маленький RED probe **на настоящем выдаваемом `/app.js`**: собственный `createSampleApp({port:0})`, HTTP GET скрипта, Node VM с контролируемыми fetch/WS и минимальными DOM объектами. Рабочий API 5421 и существующие QA вкладки не использовались. Только синтетический текст; он и headers не выводились. Сервер fixture закрыт.

Результат: `clearedBeforeAck=true`, `missingAfterLostResponse=true`, `unhandledRejectionCount=1`, `unsentValueRetained=true`, `unsentInputDisabled=true`, `allActionButtonsDisabled=true`, `postCalls=1`. Это проверка поведения emitted script, не браузерная проверка геометрии, реального туннеля или сохранности на диске.

## Минимальная дельта

1. **Редактирование отдельно от связи.** Поле остаётся доступным при close/error/reconnect; form/input не пересоздаются при обновлении списка. Отключаются новые изменения списка, пока нет свежего валидного snapshot либо пока другое изменение ожидает ответа. Старый список можно оставить с подписью «Не удалось обновить список»; не выдавать его за актуальный.
2. **Одна операция записи за раз.** Локально фиксировать `{operationId, draftRevision, text|itemId, state}` до POST. Текст очищается только после проверенного успешного ответа и только если текущая draftRevision равна отправленной. Новое редактирование, включая A→B→A, увеличивает revision; поздний ACK его не стирает. Если во время POST человек набрал B, исходный неподтверждённый A остаётся доступным отдельным локальным текстом, не перезаписывает B.
3. **Явное восстановление только чтением.** Кнопка `type=button` «Подключить снова» запускает один GET и один новый WS, закрывает предыдущий socket и ограждает callbacks connection generation. Повторные клики во время подключения не создают параллельные sockets. Никакого POST, toggle, автоматической очереди или business heartbeat при reconnect.
4. **Раздельные статусы связи и операции.** WS `open` ещё не означает полученный список. Готовность наступает после валидного snapshot. Потеря WS сама по себе не превращает принятый POST в неуспех; независимый pending POST тоже не становится успешным от нового WS. Поздний корректный ACK того же действия учитывается отдельно от connection generation, без отката списка или стирания нового ввода.
5. **Один источник текущего списка.** На открытом WS его последовательные snapshots обновляют список; POST response подтверждает действие, но не заменяет более новый WS snapshot. Reconnect GET может дать начальную/диагностическую картину, но после первого snapshot текущего WS его поздний ответ список не перезаписывает. Snapshot/ошибка старого socket никогда не действует на новое соединение. Это небольшая локальная arbitration, не обещание distributed revision protocol.
6. **Проверенные ответы и конечное ожидание.** GET/POST проверяют HTTP status и форму JSON; malformed data не попадает в render. Все rejection/timeout обрабатываются. После отправки POST abort/timeout не означает откат эффекта. Для toggle после неизвестного результата обязательно заново прочитать список; не повторять прежнюю инверсию.

Операции со списком остаются прежними. Не добавлять durable outbox, серверные idempotency receipts, account protocol, автоматическое подтверждение по совпадению текста или хранение всех прошлых drafts. Если нужны гарантированные повторные доставки, это отдельное изменение sample API; R4 их не обещает.

## Слова, соответствующие фактическому результату

| Что известно | Текст человеку | Разрешённое действие |
|---|---|---|
| Close, новых POST не было | «Связь прервалась. Введённый текст остаётся здесь.» | Редактировать/копировать; «Подключить снова» |
| Локальная проверка остановила действие до fetch | «Не отправлено: …» | Исправить ввод, отправить вручную |
| Получен валидный успешный ответ POST | «Добавлено» / «Изменение принято» | Очистить только исходную неизменённую draft revision |
| POST уже начат, ответ потерян/неполон/невалиден | «Не удалось подтвердить добавление. Оно могло сохраниться. Обновите список перед новой отправкой.» | Сохранить исходный текст; read-only reconnect, затем осознанное новое действие |
| GET не удался | «Не удалось обновить список. Попробуйте подключиться снова.» | Не объявлять ошибку отправки либо отзыв прав только по сетевой ошибке |
| После восстановления доступ всё ещё недоступен | «Не удалось открыть приложение. Откройте его заново; перед этим скопируйте введённый текст.» | Явное повторное открытие через уже существующую оболочку; без встроенного обхода авторизации |

Для generic sample один HTTP 4xx/5xx после POST не доказывает отсутствие эффекта: ошибка может появиться после изменения или на промежуточном узле. «Точно не отправлено» допустимо до dispatch либо при отдельном явном pre-commit error contract, которого сейчас нет. Совпадение строки в общем списке тоже не является receipt исходной операции. После unknown исходный POST не повторяется ни таймером, ни reconnect, ни checkbox handler. Новая ручная отправка обозначается как новая и предупреждает о возможном повторе.

## Навигация, клавиатура и узкий экран

Draft сохраняется **в открытой странице**, включая disconnect/reconnect. Пример не знает Soty account и не умеет выдавать новую сессию: session expiry требует существующего platform reopen/fresh admission. Не внедрять tokens, shell redirects, фиктивную личность или app-specific postMessage.

Не обещать сохранность через reload/закрытие окна и не добавлять молча localStorage без account scope. Текст остаётся доступным для выделения и копирования; при необходимости повторного открытия явно предупредить о его сохранении. В [app-stage.ts](../../src/world/app-stage.ts) sandbox содержит `allow-scripts allow-forms allow-same-origin`, но не `allow-modals`. Поэтому beforeunload prompt не является страховкой для этого iframe; [HTML Standard](https://html.spec.whatwg.org/multipage/browsers.html#sandboxing-flag-set) связывает его с sandboxed modals. Sandbox ради примера не расширяется.

Reconnect — отдельная кнопка с текстовой подписью, минимум 44×44 CSS px, не `+` без понятного имени. Enter в поле выполняет только допустимую новую отправку, Enter на reconnect — только чтение. Status `role=status` без перехвата фокуса; неопределённый результат остаётся видимым и не затмевается «подключено». При обновлении списка сохранять фокус существующей строки, только если он был в ней; не уводить его из draft input. При 320 px действия переносятся, поле имеет `min-width:0`, длинное сообщение не создаёт horizontal overflow. Проверить также 667×375. Общую перестройку дизайна не делать.

## Тесты после R1–R3

Новый focused test должен получать `/app.js` и HTML/CSS от реального `createSampleApp`, а не копировать реализацию в fixture и не искать нужные строки regex. Node VM/небольшой DOM harness с управляемыми HTTP/WS даёт детерминированные причинные проверки. Отдельный loopback fault proxy может подавить POST response **после принятия origin response**, чтобы доказать настоящий committed-but-lost ACK. Только собственные синтетические данные/порты; не печатать sample request headers. Запуск последовательно, без общего heavy suite.

| Сценарий | Проверяемое следствие |
|---|---|
| Unsent text → WS close → explicit reconnect → fresh snapshot | Текст/selection не потеряны; 0 POST при reconnect |
| POST A → ACK pending → draft B, отдельно A→B→A | ACK A не стирает новую revision; исходный A recoverable при unknown |
| Origin принял add, proxy потерял ответ | Unknown, исходный текст сохранён; reconnect показывает список, origin POST count остаётся 1 |
| Ошибка до dispatch / 500 после dispatch / malformed success / timeout | «Не отправлено» только для первого; остальные не объявляют rollback и не дают unhandled rejection |
| Двойной submit/toggle, затем reconnect | Не более одного одновременно активного POST; ни одного скрытого повторного toggle |
| Old socket message/close + поздний old GET после нового подключения | Новая готовность/список не меняются; ограниченное число sockets/таймеров |
| WS новый snapshot → поздний POST/GET response | Список не откатывается старым HTTP snapshot; outcome POST учитывается отдельно |
| WS close при живом pending POST, затем успешный ответ | Связь остаётся честно disconnected; принятый эффект не становится failed |
| Expired/revoked access при read-only recovery | Нет POST/auto renew/navigation; draft остаётся доступным для копирования |
| Real browser keyboard, 320×760 и 667×375 | Порядок Tab/Enter, доступное имя, стабильный input/focus, 44 px targets, отсутствие overflow |

Эти проверки закрывают R4 recovery примера. Настоящий тихий/односторонний туннель, Ping/Pong, caps, revoke и absolute TTL доказываются R1–R3 отдельно. Реальный браузер нужен для focus/selection/geometry; VM не заменяет его. До принятия предыдущих этапов executable source остаётся неизменным.
