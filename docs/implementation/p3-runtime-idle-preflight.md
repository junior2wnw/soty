# P3 — WebSocket idle: диагностика и отдельный подплан

Дата: 2026-09-30. Проверены текущие исходники и выбранные безопасные показатели локального QA. Код, процессы, конфигурация, данные приложения и открытые вкладки не изменялись. Это read-only диагностика; исправление и приёмка нового поведения ещё не выполнены.

## Вывод и граница доказательства

Для описанного симптома «сначала подключено, спустя несколько минут соединение закрыто» есть прямое объяснение в действующей реализации: каждый HTTP/WS поток получает **120 секунд idle**, а пример «Общий список» после начального сообщения не посылает heartbeat и не переподключается. Его `onclose` безусловно отключает все поля и кнопки. Внешний канал коннектора продолжает отвечать на ping и выполнять HEAD-наблюдения, но это не продлевает внутренний поток приложения.

Отдельно найдено несоответствие сторон: сервер продлевает idle при данных **источник → браузер**, но не при данных **браузер → источник**. Коннектор продлевает его в обоих направлениях. Поэтому даже активная запись браузера без ответа источника не гарантирует сохранение потока на сервере. Это подтверждено чтением точных веток; специальный сетевой RED для этого случая в текущем QA не запускался.

Точный close-code и время последнего кадра проблемной вкладки не записаны. Поэтому 120-секундный idle — установленный механизм, согласующийся с наблюдением, но не трассировка конкретного старого закрытия. Перезапуск API, смена эпохи/источника, отзыв доступа и реальный сетевой разрыв тоже закрывают поток. Текущая доступность не исключает прежний краткий разрыв.

## Действующая политика

| Уровень | Предел | Что продлевает / проверяет | Что не продлевает |
| --- | --- | --- | --- |
| Launch ticket | 30 с, одно использование | Обмен с повторной проверкой допуска | Трафик приложения |
| Авторизованная сессия | Абсолютно 1 час после обмена ticket | Проверки сохраняют первоначальный deadline | HTTP, WS, heartbeat и подписанный public-доступ не продлевают час |
| Анонимный public lease | 30 с | Повторная проверка ещё действующего допуска, включая аудит живого потока; истёкший lease не оживает | Наличие старого cookie не превращается автоматически в гостевой вход |
| Аудит допуска | По умолчанию каждые 10 с и на async-границах | Текущие права, epoch, target, binding floor и текущий канал | Не является подтверждением живости браузерного WS |
| Канал API ↔ коннектор | Ping каждые 10 с; отказ при отсутствии входящих кадров/pong более 45 с, проверяемый очередным tick | `lastSeenAt` обновляется pong или входящим кадром канала | Сам по себе не трогает idle отдельных приложений |
| Начало потока | 30 с до head | Получение head заменяет таймер на idle | Отдельный HEAD probe источника |
| Поток после head | 120 с | Сервер: принятый `data` от коннектора; коннектор: принятые и отправленные `data` | Stream ACK, sync/binding ACK, outer ping/pong, периодический probe |
| Доставка одного chunk | 30 с до ACK | ACK снимает отдельный pending timer | ACK не сбрасывает stream idle |

Источники: `modules/apps/server/index.mjs:189–255, 514–518, 562–590, 639, 673, 692–721`; `modules/apps/server/protocol.mjs:5`; `scripts/agent-modules/local-apps.mjs:303–318, 342–416`. Двухминутный idle уже описан в `modules/apps/README.md:104`; сессии и аудит — там же, строка 65.

Сроки — настройки таймеров, а не жёсткий wall-clock SLA: блокировка event loop может задержать закрытие. Нельзя продлевать авторизацию только потому, что транспорт жив.

## Где проходят ping/pong

Здесь два разных WebSocket:

1. **Внешний канал API ↔ коннектор.** Сервер использует пакет `ws`, явно вызывает `channel.ws.ping()` и принимает `pong`. Коннектор использует `globalThis.WebSocket` Node. Ответ на control ping относится к WebSocket-реализации, а не к JSON `local-apps` протоколу или JavaScript приложения. `local-apps` не выпускает heartbeat каждого мини-приложения.
2. **Внутренний WS браузер ↔ исходное приложение.** Он проходит как байты внутри `data` внешнего канала. Сервер проверяет framing, mask direction, control-frame validity и размер сообщения, но сам не создаёт inner ping/pong. Пример использует `ws` на источнике: его установленная реализация автоматически отвечает pong на ping, но не генерирует периодические ping. В примере периодического инициатора нет.

Control ping/pong внутреннего WS, если их создаёт один из endpoint, проходят как данные туннеля. Ping от источника обновил бы серверный idle; ответ браузера обновил бы коннекторный. Только browser-originated inner ping при отсутствующем ответе источника не устраняет серверную асимметрию. TCP ACK/keepalive вообще не проходит как `data` этого протокола.

RFC требует ответить pong на принятый ping, если close ещё не получен. Браузерный API не предоставляет JavaScript методы control ping/pong; рассчитывать на добровольный heartbeat браузера нельзя. Это подтверждено [RFC 6455 §5.5.2–5.5.3](https://www.rfc-editor.org/rfc/rfc6455.html#section-5.5.2) и [WHATWG WebSockets](https://websockets.spec.whatwg.org/#ping-and-pong-frames). Здесь не проводилась отдельная проверка реализации Node native WebSocket.

## Почему пример остаётся выключенным

`modules/apps/examples/sample-app.mjs:38` посылает начальный список и повторяет входящие сообщения. Изменения списка через HTTP POST рассылаются всем WS-клиентам. Если изменений нет, источник молчит. Строка 48 при любом закрытии выводит «Соединение закрыто» и отключает поля; обработчика повторного открытия нет. Срок сессии и причина закрытия там не различаются.

Сервер при ошибке потока уничтожает сырой сокет (`index.mjs:197`), не посылая inner close-frame с типизированной причиной. Даже предполагаемый браузерный код 1006 сам по себе не отличил бы idle от сети; фактический код старой вкладки не измерен. Коннекторный `app_idle_timeout` также сейчас отображается сервером в общий `app_upstream_failed` (`index.mjs:695`).

Увеличение числа вкладок может исчерпать **32 одновременных потока на коннектор**, включая HTTP; public-basis ограничен 24, оставляя резерв для grant-basis. Admission отказывает новому потоку, а не вытесняет уже подключённый через несколько минут. Само число вкладок не равно числу потоков.

## Варианты следующего отдельного изменения

| Вариант | Пользовательский результат | Граница |
| --- | --- | --- |
| Сохранить idle 120 с как контракт приложения | Приложение обязано иметь heartbeat и восстановление после закрытия | Конечные ресурсы освобождаются предсказуемо, но произвольное молчащее стороннее приложение перестаёт работать; это существенное ограничение платформы |
| Добавить heartbeat и повторное подключение только примеру | Демонстрационный список продолжает работать в тишине | Проверяет пример, не исправляет совместимость платформы. Нельзя автоматически повторять пользовательские POST или считать потерянный ответ отказом |
| Универсальная политика живости WS | Тихий, но живой WS не закрывается только из-за отсутствия бизнес-сообщений; мёртвый peer удаляется в ограниченное время | Нужна отдельная проверка живости обоих endpoint, отличная от heartbeat внешнего канала, с сохранением абсолютной авторизации и всех лимитов |

Рекомендованная цель отдельного подплана — третий вариант. HTTP idle оставить отдельным. Двунаправленную активность WS учитывать симметрично; heartbeat считать только живостью транспорта, не активностью пользователя и не продлением прав. Зафиксировать конечный ping/pong deadline и явное восстановление после сети/истечения сессии. Пример дополнительно должен сохранять несданный ввод и предлагать повторное подключение, а не становиться навсегда недоступным.

У текущего сырого туннеля нельзя безопасно «просто написать ping-байты» в сокет: запись может попасть в середину уже передаваемого frame. Понадобится либо framing-aware планировщик с корректным разделением собственных control frames и чужих, либо осознанное завершение WS на транспортной границе. Выбор требует отдельного небольшого дизайна и отрицательных тестов; здесь новый механизм не внедрён. Простое бесконечное отключение idle не доказывает очистку half-open соединений и не является предложенным исправлением.

Сохраняемые ограничения: 32 общих / 24 public-basis потока; 1 MiB на WS message, включая fragmentation; 48 KiB chunk и один ожидаемый ACK на поток; 4 MiB buffered limit внешнего канала; head/ACK deadline 30 с; точные origin/binding/epoch проверки; абсолютная 1 h account-session. Живые старые вкладки действительно занимают слоты: конечный cap должен давать честный отказ новому подключению, а не скрытое вытеснение работающего. Более тонкая справедливость между аккаунтами — отдельная задача, не обещание этого исправления.

## Необходимая приёмка будущего исправления

- Тихий WS живёт дольше 120 с; отдельно проверены трафик только браузер → источник и только источник → браузер. Тест обязан использовать настоящий туннель, а не только heartbeat примера.
- Живой внешний коннектор при мёртвом внутреннем peer не удерживает поток бесконечно. Потерянный pong/ACK закрывает только нужный поток и освобождает слот один раз.
- Ping/pong не ломает fragmented/binary кадры, маски, размеры, порядок и backpressure; нельзя вставить control frame внутрь байтов другого frame.
- Heartbeat не продлевает абсолютный час, не восстанавливает истёкший public lease, не обходит revoke/смену source/binding/epoch.
- 32/24 caps и резерв сохраняются; соседние активные приложения не закрываются из-за отказа одного.
- Восстановление не повторяет HTTP side effects и не выдаёт старый WS за непрерывный. Пример сохраняет ещё не отправленный ввод и показывает понятное действие после закрытия.

Этот перечень не запускался против текущего QA. Root продолжает D3 browser gate независимо; runtime-изменение — следующий согласованный подплан.
