# C2-C: независимая приёмка управления источником

Дата: 2026-09-30. Основание: C2-B `5a4cb1d`, подплан `p3-source-settings.md`.

Статус: **PASS в границах локального C2-C**. Независимые network/state проверки, финальный read-only UI audit и компонентный браузерный повтор пройдены. На зафиксированных ниже исходниках материальных блокеров не осталось. Решение о checkpoint принимает интегратор; этот документ не разрешает production-выпуск и не подменяет внешние gates.

## Проверенный смысл

Переключение меняет маршрут существующего приложения, сохраняя его адреса и права. Оно не переносит и не откатывает данные проекта. «Устройство в сети», подтверждение точного маршрута и ограниченный HTTP ответ — разные факты. История показывает неизменяемые конфигурации, а не резервные копии.

Незавершённый ввод источника живёт в памяти окна с обычными предупреждениями при уходе. После явной отправки сохраняется точный запрос переключения. Восстановление незапущенной формы после аварии здесь не обещается.

## Реальная сеть и текущий маршрут

Файл: `modules/apps/test/source-runtime.acceptance.test.mjs`. Добавлены четыре C2-C сценария; прежние девять C2-B оставлены.

1. Owner-only список устройств и повторное присоединение сообщают фактически согласованную версию: v2, offline/null, legacy1. Чужой аккаунт не получает inventory или inspection.
2. После переключения B его удержанный ACK даёт `pending`, старое наблюдение A и ещё не подтверждённое B не дают свежей готовности. Сам ACK даёт `bound`, но не HTTP evidence. Floor2 с legacy reconnect даёт `update-required` и отказ runtime.
3. Два настоящих `createAppsService` читают один SQLite, каждый имеет отдельный настоящий connector. Второй подтверждает и переключает target; первый ещё содержит ACK прежнего target. Inspection первого возвращает новый tuple с `pending/unknown`; launch и HTTP отказывают до нового ACK. Прежний upstream не получает запрос.
4. Отзыв приложения убирает binding/readiness/share claims и действия. Другое приложение на устройстве продолжает открываться.

Команда: `node --test --test-name-pattern='C2-C' modules/apps/test/source-runtime.acceptance.test.mjs` — **4/4 PASS**. Затем весь файл вместе с первыми девятью клиентскими случаями — **22/22 PASS**, без пропусков. Дополнительно owner `apps.list` сохраняет имя текущего устройства B после переключения; granted viewer не получает `deviceName`. Контролируемая задержка отдельных wire frames проверяет границу асинхронного исполнения, а не физические потери сети или backpressure.

## Сохранение намерения и конфликтов

Файл: `src/world/app-source.acceptance.test.mjs`. Здесь настоящие Apps service, SQLite receipts, локальный HTTP upstream и connector HEAD. Storage/Web Locks и доставка ответа — управляемые адаптеры; авторские fixtures не импортируются.

- Потерянный ACK переживает remount и истечение proof: повтор отправляет прежний requestId и args. Исторический receipt B не подменяет уже текущий источник C.
- Два окна не заменяют общий pending разными целями. Конфликт не меняет введённый путь или прежнюю CAS-базу автоматически.
- Поздний ACK не очищает более новый pending и не возвращает результат в сменившийся аккаунт.
- Шесть подмен receipt, включая proof hash, digest, floor и requestId, отклоняются с сохранением pending.
- Истечение проверки внутри ожидания Web Lock и отказ локальной записи приводят к нулю сетевых promotion-запросов.
- Hidden/edit/account invalidation не принимает позднюю подготовку.
- Сохранение одного названия сохраняет проверку источника; изменение прав делает её устаревшей.
- `resetPublication` оставляет черновики имени, групп и нового адреса. Source promotion не сохраняет их попутно.
- История не меняет CAS-базу редактирования. Возврат требует свежего proof и точного согласия.
- Реальные 22 конфигурации проверяют переход по cursor: следующая ограниченная страница не теряет выбранную неизменяемую цель.

Первый основной срез `node --test src/world/app-source.acceptance.test.mjs` — **10/10 PASS**, без пропусков. После добавления девяти сценариев альтернативного действия — **19/19 PASS**. Это не доказательство браузерных Web Locks, реальных событий visibility или работы на телефоне.

Первый пробный прогон одного сценария столкнулся с лимитом двух живых preparations: тест передвинул только локальные часы, оставив серверные proofs действующими. Исправлен тестовый ход времени на согласованное течение серверного и локального времени; проверки продукта не ослаблены.

## Ограничение времени

[W3C: Timing Adjustable](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html) объясняет, почему человеку нужно время на чтение и подтверждение; security timeout сам по себе не исключает требование. Это основание проектного решения, а не заявление о полном соответствии WCAG.

Принят узкий дополнительный путь: сохранённая карточка читается без таймера, пользователь явно выбирает «Перепроверить и переключить». Новая подготовка должна точно совпасть с прочитанными tuple/pins, epoch, текущей целью и выбранной политикой. Любое изменение возвращает просмотр без promotion. Старый durable pending проходит только точный retry. Proof30s не продлевается и таймер ничего не переключает.

После API freeze проверены девять дополнительных сценариев: отсутствие согласия даёт ноль API-вызовов; долгое чтение сохраняет карточку, новая проверка получает другой preparationId с прежними pins; helper возвращает intent, но сам ничего не записывает; consent/tuple-ABA/policy/hidden/account/epoch drift во время ожидания не даёт intent; другой digest или повтор старого preparationId возвращает просмотр; конкурирующий durable pending и повторное истечение внутри Web Lock дают ноль promotion-запросов.

Конкретное прежнее ожидание `exposureConfirmed=false` после 30s заменено по этому принятому решению: согласие с прочитанной карточкой остаётся, но `canPromote=false` и `promoteIntent()` для просроченного proof отклоняется. Выполнить действие можно только через явную свежую перепроверку. Это изменение контракта взаимодействия, не отключение проверки срока.

После первого полного повтора **45/45 PASS** коллега обнаружил отдельную гонку повторной отправки. Кнопка показывала pending A, но могла прочитать заменивший его pending B. Независимый тест с реальным service воспроизвёл отказ проверки: при ожидании lock другой поток удалил A и записал B, retry отправил B. Это был материальный blocker, а прежний зелёный прогон его не покрывал.

Исправление: retry требует `expectedPending`, захваченный из показанного состояния до `perform/render`; под тем же Web Lock проверяются операция, args и expectedSource. Отсутствие, очищенный slot или несовпадение — `app_settings_pending_changed`, ноль API-вызовов. Оба UI retry и локальное завершение проверки захватывают именно показанную запись. Новая команда не подменяется старым повтором.

Добавлены три независимых negatives: замена до нажатия, замена перед получением lock и отсутствие/очищенная ожидаемая запись. Прежние C1 retry tests теперь передают известную точную pending-запись, сохраняя все прежние проверки последствий.

После браузерного обнаружения пустой истории root и автор воспроизвели дополнительный дефект: обычный clean `observe` при render вызывал тот же reset, что явная отмена, и отбрасывал уже начатый ответ истории. Автор разделил эти действия. Независимый составной сценарий удерживает настоящий ответ Apps service с конфигурациями A+B, вызывает unchanged inspection между запросом и ответом, затем проверяет обе строки для initial и latest. На исправлении он PASS; собственного запуска RED до исправления для этого случая не было. Explicit reset/dispose по-прежнему инвалидируют запрос; история с несовпавшей authority остаётся stale и не разрешает переключение.

Итоговый независимый повтор после исправления истории и строгих receipt shapes: `node --test modules/apps/test/source-runtime.acceptance.test.mjs src/world/app-source.acceptance.test.mjs src/world/app-settings.acceptance.test.mjs` — **49/49 PASS**, 0 fail, 0 skip.
