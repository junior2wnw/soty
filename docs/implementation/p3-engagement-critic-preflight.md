# P3-D0: независимый preflight сохранения и обсуждений

Дата: 2026-09-30. Основание: принятый C2-C `60876fb`, чтение рабочей копии `soty-platform` на `b89bee1`, P3.5 основного плана и P3-D/E из `p3-implementation-preflight.md`. Это контрактное предложение и аудит существующих границ, **не реализация и не PASS будущей функции**. Production и пользовательские данные не менялись.

## 1. Минимальная продуктовая модель

Человек сохраняет конкретный вход в приложение в свой аккаунт и возвращается к нему с другого устройства. Возле приложения есть одно место **«Обсуждение»**, где всегда видно, какой аудитории отправляется сообщение. Сохранение, запуск, сообщение, подписка на уведомления и вступление в сообщество — разные действия.

Сохранение не выдаёт право запуска и не становится резервной копией приложения. Обсуждение работает в доверенной оболочке Сот, независимо от доступности ноутбука автора. Оно не внедряется в чужой runtime-origin и не получает cookies/Connect credentials оттуда. Переключение источника сохраняет обсуждение; смена аудитории сохраняет данные, но не расширяет прежнюю закрытую историю.

Для первого D достаточно сохранённого входа, одной поверхности обсуждения, ограниченного списка доступных архивов и явных результатов отправки. Реакции, ветки ответов любой глубины, медиа, presence, рекомендации, публичные счётчики сохранений и push не нужны для доказательства этого цикла.

## 3. Серверное сохранение

Предлагаемый ключ записи — `(accountId, appId)`. Значение: выбранные `domainId`, валидный локальный `entryPath`, savedAt/updatedAt. Согласованное после обсуждения решение — отдельный монотонный account library head, до200 активных записей и последние128 receipts. Снятие сохранения удаляет активную строку, но не head. Сохраняется постоянный вход, **никогда** boot URL, ticket, session nonce или свободный внешний origin. Origin разрешается сервером из конкретного domainId. Путь проходит тот же validator, включая hash-SPA; это не произвольный return URL.

- Default при сохранении берётся из **фактически открытого** входа. Публичный alias не заменяется canonical. После retire выбранного адреса другой alias автоматически не подставляется: это иной origin и иное локальное хранилище приложения. Новый выбор — отдельное явное действие.
- При потере app/domain-доступа личная запись остаётся удаляемой. Она может показывать последнее название, законно сохранённое самим пользователем, с пометкой «Недоступно»; это личный snapshot, не свежая app metadata. Не возвращаются новые название/описание, participants, unread, connector, hostDevice, grants или причины приватных изменений. Неизвестный private URL не получает даже такого snapshot.
- Отключение устройства не удаляет запись и не запрещает сохранить уже разрешённый вход. Revoke приложения не удаляет bookmark; снятие bookmark не отзывает grant, не удаляет приложение или переписку.
- Операция задаёт состояние `saved=true/false`, а не `toggle`. RequestId + нормализованный fingerprint + expected revision фиксируют решение. Два окна с одной revision не перетирают друг друга; retry повторяет показанный intent, не последнее содержимое общего slot.
- Удаление сохраняет монотонный account head как эквивалент durable tombstone floor. После prune receipt старый add несёт прежнюю expected revision и не может воскресить снятое сохранение. Исторический receipt `saved=true` и current `saved=false` возвращаются/отображаются отдельно. Цена простоты — параллельные изменения разных app в одной библиотеке тоже могут конфликтовать; UI не перебазирует unresolved запрос автоматически.
- Удаление собственной записи разрешено даже без текущего доступа к app; добавление/смена domain/path требует текущего допуска. Владение bookmark выводится из проверенного actor, не из args.
- Список ограничен, сортировка стабильна. При согласованных200 активных сохранениях/128 receipts предлагаются default page40/max100; окончательный page contract фиксируется авторами. Полная квота не блокирует remove или проверку прежнего запроса. Состояние пустой библиотеки не обнуляет head.

Старые local pins нельзя тихо считать серверными. Миграция сохраняет их до подтверждённого результата. Для записей только с appId нельзя угадывать прежний public origin; предложить явное сохранение текущего разрешённого входа. Недавние действия, порядок сот и локальные предпочтения не обязаны становиться отдельной синхронизируемой системой в D.

## 4. Аудитория и история обсуждения

С root и модельным автором согласовано направление **неизменяемых поколений обсуждения**. Пользователь видит одно место «Обсуждение», а не технический список новых продуктов.

Каждый conversation связан с appId и содержит immutable audience descriptor: mode public/restricted, owner, нормализованные exact accountIds/communityIds. При изменении mode или grant-set создаётся новый conversationId; прежний становится read-only. Возврат public→private→public создаёт новый public ID, даже если descriptor совпадает с первым. Простое название, source switch, listed, изменение runtime epoch без изменения аудитории не ротируют разговор.

Переход и указатель текущего conversation должны фиксироваться в одной Apps transaction с publication/grants/source-policy изменением. Нельзя полагаться на best-effort уведомление после commit: потеря уведомления оставит прежний private поток текущим. Получение текущей модели чтения не создаёт новые сообщения или новые аудитории.

| История | Условие чтения |
| --- | --- |
| Текущий разговор | Текущий доступ к выбранному exact domain плюс audience predicate этого conversation и собственные ограничения обсуждения. |
| Архив restricted | Текущий **grant**-допуск к приложению **AND** исходный restricted predicate. Public-допуск никогда не заменяет grant. |
| Архив public | Текущий разрешённый app/domain-доступ; он не раскрывает соседние restricted conversation. |
| Отозванное приложение | Новые сообщения запрещены. Предложение: владелец имеет явно административное чтение/модерацию архива; чужие пользователи получают generic unavailable. Это исключение надо назвать в окончательном контракте. |

В исходно выбранных community membership остаётся динамической, как в существующем World: новые участники **той же** группы могут читать относящуюся к ней app history. Это осознанный ограниченный контракт, не снимок каждого человека. Добавление другой группы в app grants не даёт ей архив. Действительность group grant включает текущую membership читателя и текущие необходимые полномочия app owner в группе. Не показывать постороннему приватные названия/состав других групп из descriptor.

Все архивы, counts, previews, reply targets и cursors фильтруются до выдачи. Недоступный conversation ID не раскрывает существование, число скрытых эпох или последний текст. Прямой reply разрешается только внутри того же разрешённого conversation. Общая community history остаётся в своём хранилище и не копируется ни при публикации, ни при вступлении, ни при rollback источника.

Автор приложения не может гарантированно отозвать уже прочитанные/скопированные публичные сообщения. Private/public переключатель регулирует последующий сервисный доступ, а не чужую память или экспорт. Перенос владения app текущая модель не поддерживает; наследование архивов новым владельцем не вводить попутно.

## 5. Сообщения, повтор и синхронизация

Минимальная поверхность API, имена пока рабочие: saved `get/list/set`; discussion `get/list/send/remove/read/changes`; owner `setPostingRestriction` для закрытия записи/бана. Везде typed scope, authenticated actor и expectedAccountId guard. Не добавлять общий endpoint чтения любой таблицы, новые identities или свободный `execute`.

Рекомендуемый первый D: чтение/отправка через подписанный Connect аккаунта. Anonymous runtime остаётся работающим; сохранение/обсуждение переводят в trusted shell с тем же entry context и затем требуют аккаунт. Публичная аудитория при этом означает всех нынешних и будущих пользователей, не конфиденциальность за формой входа. Отдельный anonymous discussion endpoint не нужен для этого доказательства.

Сообщение имеет conversation-scoped ID/order, author, clientId, immutable request fingerprint, plain text до6000 символов, replyTo внутри того же разговора, createdAt, tombstone и версию изменения. Author DTO — ID, displayName и разрешённая avatar projection; без bio, interests, private memberships и device metadata. Новый Connect аккаунт может ещё не иметь World profile: предусмотреть trusted actor label/нейтральный fallback, не вызывать скрытую запись `ensurePerson` внутри read-only World fence. Внешний агент получает только явно предоставленную typed capability: появление API не даёт ему автоматического права читать/отправлять переписку.

1. Pending сохраняется **до сети** и содержит account/app/conversation/domain, текст/reply, clientId. Storage fail — нет тихой отправки с ложной гарантией восстановления. Новый текст хранится отдельно и не заменяет unresolved pending.
2. Replay сохраняет точный fingerprint. Удалённый body очищается, fingerprint и clientId tombstone остаются: точный retry возвращает tombstone/receipt без воскрешения, изменённый текст — conflict. Actor и разрешённый scope проверяются до возврата private результата.
3. Переход аудитории не переносит pending или несданный private draft в новый public composer. Старый локальный draft остаётся в своём контексте; новый разговор пустой. Отправка из старого окна после ротации отвергается; уже принятый старый запрос может сверяться только как старый запрос.
4. История страниц и cursor изменений — разные задачи. Изменения включают старые удаления; простого `after message.creationSeq` недостаточно. Cursor opaque, привязан к app/conversation и не раскрывает глобальный счётчик сообщений в скрытых разговорах.
5. Ограниченный retention журнала изменений возвращает `reset_required`, если клиент слишком старый. Клиент очищает недостоверную доставленную history, загружает разрешённый snapshot, **сохраняя draft/pending**, scroll/focus по возможности. Не продолжать с произвольно новым cursor и не называть пустоту отсутствием сообщений.
6. Limit/byte/page budgets действуют на сервере. При catch-up максимум несколько страниц за один цикл, без бесконечного `.all()`/неограниченного DOM. Hidden polling останавливается. Read watermark монотонен, привязан к разрешённому conversation и видимому полученному сообщению; обновление не создаёт публичные read receipts.
7. Удаление, revoke, смена account и audience проверяются не только в composer, но в list/changes/read/remove/replay и перед применением каждого позднего UI ответа. Ошибка сети оставляет последнее состояние с пометкой; явный access denial убирает доставленную историю из активного экрана и блокирует отправку. Собственный draft можно сохранить/скачать, не публикуя его в новом месте.

## 6. Модерация и граница P3-E

Для локального D нужны минимальные тормоза: аутентифицированная отправка, размер текста/ответа, частота на account и conversation, квота сохранённых сообщений/байтов, own remove и owner moderation, запрет новых сообщений в закрытом архиве, persistent app-level posting ban. Бан не должен исчезать при следующей ротации conversation. Роль модератора community не становится ролью модератора app.

Персональный запрет записи в app discussion не означает запрет анонимно открыть публичное приложение или прочитать уже публично доступный контент. Owner не должен обещать «этот человек больше ничего не увидит», оставляя anyone. Пользователь должен иметь путь удалить собственное сообщение даже при запрете дальнейших публикаций, с ограниченным собственным scope.

P3-E остаётся обязательным до открытого пилота: жалоба/обработка жалоб, платформенная quarantine, эксплуатационная поддержка, защита от массовой регистрации/спама, численные глобальные storage/rate пределы и политика экспорта/retention. Нельзя включать публичную запись с формулировкой «модерация потом». Если этих механизмов нет, D — закрытая локальная проверка, публичный admission не расширяется.

Квоты не блокируют emergency restrict/revoke/moderation. Чтобы churn аудитории не создавал бесконечно много пустых архивов, допустимо материализовать payload conversation при первом сообщении; монотонная граница аудитории всё равно должна существовать и отвергать старый send. Прежние сообщения/дедупликация не удаляются молча для освобождения места.

## 7. Слабые места, которые надо закрыть до реализации

- **Хранилище и reader.** Новые связанные записи разумно держать в Apps5 с FK на app/owner, а не расширять World messages фальшивыми communities. Точный DDL/migration/reader label и исторический Apps4 fixture должны быть согласованы до первой записи. Старый Apps4 reader/writer обязан отказать до записи; rollback не стирает saved/history. Если выбрано отдельное хранилище, это не отменяет требование атомарной ротации аудитории — нужен доказанный механизм, а не обещание.
- **Динамическая community — отдельная база.** Root выбрал host-owned synchronous fence для новых engagement операций: Connect actor fence → World `BEGIN IMMEDIATE` без World writes → bounded Apps5 transaction и текущая policy → Apps COMMIT → освобождение World. Никаких await/thenable/network/user callbacks. Это конкретное решение удерживает проверенную World authority на время Apps commit; его ещё надо реализовать и проверить, оно не возникает из текущих callback-проверок само. Все новые пути обязаны проходить один lock order. Busy policy100ms с controlled503/same-ID retry — не hard wall-clock deadline. Author primitive probe с другим SQLite writer заявлен отдельно; настоящий signed API/failure/lock-order gate пока не выполнен. Ошибка после Apps COMMIT означает неизвестный ACK с сохранённым receipt, а не откат. Уже доставленные байты и произвольный root filesystem writer этот механизм не отзывает.
- **Tombstones и лимиты.** Saved head/200 active/128 receipts согласованы; до кода остаётся выбрать bounded retention/reset для changes и admission quota сообщений/байтов. Нельзя одновременно обещать вечный retry, безлимитные удаления и физическое удаление всех ключей дедупликации.
- **Owner/archive exception.** Явно утвердить административное чтение владельца после app revoke; оно не должно случайно стать публичным read-path или полным обходом actor revocation.
- **Простая поверхность.** Один значок «Сохранить» с подтверждением и одно «Обсуждение». Не размножать local pin/server save/install/follow под одинаковыми звёздочками. «Убрать у меня» не выглядит как удаление проекта. Отдельно подписан «Чат сообщества» и личный помощник; source/apps tab switching не перемещает текст между ними.

## 8. Решающий acceptance-подплан

| № | Исполняемый сценарий | Обязательный результат |
| --- | --- | --- |
| D01 | Два аккаунта, два устройства одного аккаунта, публичный alias сохранён с hash/query. | Другой аккаунт не читает saved; второе устройство открывает exact domain/path, не canonical и не boot ticket. |
| D02 | Save ACK потерян → remove в другом окне → старый save retry; затем prune receipt/restart. | Исторический результат отделён от current; removed не воскресает; stale CAS не перебазируется. |
| D03 | Retire выбранного alias при другом активном alias; private/revoke/offline; затем remove bookmark. | Нет автоматического origin switch; offline отличается от denial; старый личный snapshot допустим, свежие private поля/counts не возвращаются; remove работает. |
| D04 | Сообщение restricted A → public B → restricted C → public D. | Четыре lineage; B/D не видят A/C; старые ID, reply, search, cursors и counts не обходят границу. |
| D05 | Меняется grant-set, затем возвращается прежний; source/name/listed/epoch-only отдельно. | Grant-set создаёт новую lineage, повтор старого ACL не возвращает прежний поток в writable. Source/name не уничтожают обсуждение. |
| D06 | Добавлен новый участник исходной community; добавлена другая community; owner теряет admin; читатель выходит/забанен. | Новичок исходной группы получает только согласованную dynamic history; другая группа старую restricted не получает; текущие недействительные grants закрыты. |
| D07 | Pending private текст, смена аудитории/аккаунта/роута во время delayed ACK и storage lock. | Ноль отправок в новый conversation/account; локальный draft не потерян, late ACK очищает только exact old pending и не меняет чужой экран. |
| D08 | Send committed/lost ACK → own/owner remove → точный retry и тот же clientId с другим текстом/reply. | Одно сообщение, tombstone не восстанавливается; точный повтор отличён от подмены; quota не препятствует replay/remove. |
| D09 | Загружено старое сообщение, пришло >2 страниц новых; удалено старое вне tail; changes retention истёк. | Tombstone доставлен; bounded catch-up без пропуска; reset_required очищает stale history и сохраняет draft/pending. |
| D10 | Фальшивые foreign app/domain/conversation/cursor/read watermark; скрытый профиль автора и приватные группы. | Deny до полезного payload; нет чужого текста, counts, bio/interests, device/grants и глобальной последовательности. |
| D11 | App-level ban/закрытие записи, ротация аудитории, flood/квота; neighbouring app. | Бан сохраняется, новый send отклонён, own remove/owner moderation доступны; другое app не выключается. |
| D12 | Настоящий signed API + UI320/667: save→другое устройство→discussion, empty/loading/error, Back/Escape, focus, unsent→audience change. | Нет ложного «сохранено/отправлено», нет смешения app/community/assistant, текст не переносится молча; уведомления/вступление не включаются сами. |
| D13 | Исторический Apps4→5, WAL/restart, отсутствующий constraint/неизвестный формат; downgrade runner. | Старые apps/grants/targets/domains сохранены, чужой writer не открывает новый формат, отказ до записи и без очистки истории. |
| D14 | Capability/HTTP клиент с правом поиска или notes.create пробует save/chat.send; сообщение содержит текст-инструкцию для ИИ. | Права не расширяются от обнаружения; текст обсуждения остаётся данными. Автоматическая отправка от имени человека без отдельного допуска невозможна. |
| D15 | Настоящий signed handler удерживает World fence; второй SQLite writer отзывает membership. Busy/throw до и после Apps COMMIT; первый аккаунт без World profile. | Право не меняется внутри admission/commit; после release следующий вызов denied. Нет deadlock/thenable/скрытого World write. Отказ до commit не оставляет эффекта, потерянный ответ после commit повторяет receipt; временный503 не создаёт новый requestId. |

D01–D11 проверяются настоящими service/SQLite и отдельными подписанными HTTP seam-тестами; delayed callbacks моделируют только соответствующую race, не физическую сеть. D12 — настоящий браузер с отдельно обозначенным synthetic fixture для отказов. D13 — reader/deploy gate; D15 — настоящий signed integration/две SQLite connections. Публичный пилот всё ещё зависит от P3-E и внешних DNS/TLS/эксплуатационных условий.

## 9. Первоисточники и предел вывода

- [Matrix: Room History Visibility](https://spec.matrix.org/latest/client-server-api/#room-history-visibility) различает право вступления и право на прошлые события; правила истории применяются к состоянию на момент сообщения. Это подтверждает необходимость отдельного исторического audience predicate, но не является предложением внедрить Matrix или скопировать его политику доступа после выхода.
- [OWASP: Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request) требует проверки прав на каждом запросе и явной матрицы разрешений. Поэтому bookmark, cursor, replay и прочитанный раньше conversation ID не являются допуском.
- [W3C: Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) связывает доступное сообщение результата с программно определимым статусом без ненужного переноса фокуса. Для D это короткие состояния «Сохраняем», «Сохранено», «Результат не подтверждён», «Доступ изменился»; не live-объявление каждого polling ответа. Это не заявление общего WCAG соответствия.

Исследования дают ограничения и паттерны. Они не доказывают удержание, привлекательность или универсальную понятность Сот. Первый человеческий критерий успеха: человек без подсказки возвращается к сохранённому входу, понимает аудиторию сообщения и способен убрать свою запись/текст, не опасаясь удалить чужой проект.
