## Контракт сохранённых приложений

`createAppSavedState` хранит один неподтверждённый запрос на аккаунт в `soty.app-saved.pending.v1:<accountId>`. Полный снимок содержит операцию, точные аргументы CAS/requestId и выбранный вход `{appId,domainId,origin,path}`. Сетевой запрос выполняется после короткого Web Lock; под блокировкой выполняются только проверка и запись локального состояния.

`dispatchAppSavedIntent` принимает либо новый `intent`, либо обязательный `expectedPending`, захваченный из показанного пользователю состояния. Повтор сверяет весь нормализованный запрос под той же блокировкой. Замена слота другой вкладкой, даже с тем же requestId, приводит к `app_saved_pending_changed` и нулю API-вызовов. Ответ очищает только совпавший слот. Смена аккаунта/экрана после отправки допускает завершение прежней локальной записи, но возвращает `stale` без ответа для нового экрана.

Замена ранее сохранённого входа требует `replace:true`; совпадающий вход и удаление отсутствующего сохранения отвергаются как no-op. Удаление отправляет только appId и параметры CAS/requestId, без domain/path. Историческая квитанция проверяется отдельно от `current`: состояние кнопки определяется `current.entry`, в том числе когда сохранение уже удалено другой вкладкой. `abandon` удаляет только локальное отслеживание и не является отменой эффекта на сервере.

`createAppSavedLibraryState` читает страницы по 20, связывает их с одним revision аккаунта, не смешивает страницы разных снимков. Истёкший курсор либо изменившийся revision требуют явного чтения заново. Список ограничен 200 строками и 2 MiB UTF-8 сериализованного содержимого; превышение — ошибка, не успешный усечённый список. Каждый ответ проверяется до применения, включая предел 256 KiB и уникальность приложений.

## Черновики и отправка сообщений

`createAppDiscussionDraftState` использует один атомарно заменяемый localStorage record и один Web Lock на аккаунт: `soty.app-discussion.drafts.v1:<accountId>`. В нём не более 32 непустых scoped slots и 1 MiB UTF-8. Scope включает аккаунт, приложение, conversationId и полный разрешённый сервером вход. Локальная запись не создаёт права чтения или отправки. `origin` участвует в локальном scope, но не добавляется к серверным аргументам.

Каждый slot разделяет изменяемый черновик `{text,replyTo,revision}` и неизменяемый pending send с собственным requestId, исходной revision и точными body/reply/entry. `prepareSend(expectedDraft,beforeCreate)` проверяет актуальность контекста внутри блокировки; callback обязан синхронно вернуть `true`. Если человек начал писать следующий текст, пока блокировка ожидалась, сохраняются оба намерения: отправляется снимок нажатия, а более новый текст остаётся черновиком. После ACK очищается только исходная draft revision. Неподтверждённый запрос не пересоздаётся при смене аудитории, потере ответа, reload или повторе.

`edit` сначала сохраняет ввод в памяти; `flush` пытается записать его локально. При запрете хранилища, отсутствии Web Locks или заполнении лимита текст остаётся в модели, `durable=false` и `hasUnsavedChanges()` остаются истинными. Новый неподтверждённый запрос без успешной записи не отправляется. Уже непустые slots и pending никогда не вытесняются автоматически. При одновременном редактировании двух вкладок сохраняется собственный текст и отдельный remoteDraft. Явные `keepMine(expectedRemoteRevision)` / `chooseRemote(...)` повторно проверяют показанную remote revision; скрытой перезаписи нет.

`hasUnsavedChanges()` означает ввод, который ещё требует локальной записи/разрешения конфликта. Уже записанный, но не отправленный черновик сам по себе не блокирует уход. Удаление черновика через `discardDraft(expectedDraft)` сверяет точный снимок и не отменяет pending. Ошибка локальной записи ACK оставляет pending для явного точного повтора, включая уже введённый следующий текст.

`listAppDiscussionDrafts` возвращает только собственные локальные slots заданных account/app/domain/path. Для восстановления текста после закрытия адреса разрешено не передавать origin; исходный origin возвращается только как часть локального scope, не как разрешённый маршрут. Старые черновики показываются отдельно и не копируются в новую аудиторию. Квитанция собственного сообщения после потери доступа может содержать `message:null`: это разрешает подтвердить pending, но не добавляет прежний body в сетевую историю.

## Чтение обсуждения

`createAppDiscussionFeed` отдельно владеет проверенным сетевым контекстом, сообщениями и курсорами. `load`, `older`, `poll`, `archives` проверяют app/conversation/entry/admin mode и скалярные формы DTO. Ответы ограничены 256 KiB. Смена выбора, invalidation или dispose отсекают поздние ответы. Подтверждённый отказ в доступе, включая native `authentication_required` / `device_revoked`, очищает контекст, сообщения и архивы и отменяет оба направления запросов. Сетевой сбой не выдаётся за отзыв прав: существующая проекция помечается stale. Явный новый `load` начинает с пустого сетевого окна. Локальные черновики не очищаются этими операциями.

Сетевое окно ограничено 500 сообщениями / 2 MiB UTF-8. Явное чтение более старой страницы может заменить заполненное окно старшим с изменением `windowRevision`, `window:'history'` и `hasNewer`; интерфейс показывает действие «К последним». Poll не удаляет незаметно уже загруженные строки. За один poll читается не более четырёх страниц по 100 событий; следующий poll продолжает с фактически полученного курсора. Архивы — одна видимая страница по 20, без скрытых счётчиков и придуманных дат.

ACK отправки не задаёт порядок: `acceptSend` обновляет только уже загруженную строку/удаление и показывает `hasNewer` для новой. Затем компонент вызывает `poll`, который устанавливает хронологию по серверному потоку. После полного catch-up последнего окна признак снимается. `acceptRemoval` немедленно убирает body по подтверждённой квитанции; до следующего чтения используется `removalConfirmed:true`, а время удаления не выдумывается. Поздний create ACK не восстанавливает удалённый текст. Серверный reset курсора очищает сетевое окно, сохраняя scoped drafts/pending.

## Проверки и граница доказательства

Авторский запуск: `node --test --test-concurrency=1 src/world/app-saved-state.test.mjs src/world/app-discussion-state.test.mjs` — **26/26 PASS**, без пропусков. Покрыты потерянный ответ/reload, точный повтор после смены слота, explicit replace, поздний ACK, конфликт вкладок, storage/lock failure с нулём dispatch, UTF-8 byte cap до достижения 32 slots, отсутствие вытеснения, scoped recovery, immutable receipt validation, поздние страницы, bounded history, старые удаления, cursor reset и порядок ACK/changes.

Два дефекта self-review закреплены сначала падавшими тестами: поздний ответ одного направления после authority denial другого; неснимаемый `hasNewer` после catch-up. Оба исправлены, 2/2 RED → GREEN. Независимый reviewer дополнительно воспроизвёл native account mismatch настоящим Apps/World service; исправлены оба readmodel, его проверка стала GREEN. Итоговый независимый receipt ведётся отдельно в `p3-engagement-independent.md`; его тестовые fixtures автором не импортируются.

Это доказательство поведения helpers и ограничений сериализованных записей, не физической сохранности диска при аварии, полного RSS браузера, браузерной доступности Web Locks или завершённой D3 UI-приёмки. Browser lifecycle, клавиатура, responsive layout, account routing и общий build проверяются интегратором отдельно. Изменений backend, commit, push, deploy или production state в этом срезе нет.
