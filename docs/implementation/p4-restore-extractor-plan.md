# P4-D2-R1 — authenticated restore into an isolated target

Дата: 01.10.2026. **Source-only подплан для review; extractor, transfer и restore ещё не реализованы и не выполнялись.** Единственное изменение этого среза — данный файл. Real keys/config/archive не читались; hosts/CLI/tests/SSH/models не запускались.

## 1. Основание и минимальный выбор

R0 принят в `dda44868fd708f87e5ac2b4f4f854fa05caca2f2`: `verifyEncryptedBackup({file,privateKeyPem})` безопасно импортируется, выдаёт прежнюю safe receipt после GCM/tar/file-close; root fixture gate 10/10. Его public API, CLI ≤64KiB и `backup_verification_failed` остаются неизменными. Устаревшее замечание D2 о top-level stdin уже закрыто R0.
Прочитаны [D2 §4–5](p4-release-recovery-plan.md), [verifier](../../deploy/connect/verify-backup.mjs), [backup](../../deploy/connect/backup.mjs), [operator](../../deploy/connect/operator-keys.ps1). Verifier допускает links, проверяет SQLite header, но не all-store completeness/integrity; producer шифрует `/data` и только один известный application-token bind. Это не готовый extractor или полный recovery bundle.
Выбор: **двухпроходный decrypt у оператора → защищённый бинарный pipe → строгий Linux sink**. RSA private key и AES content key остаются в операторском процессе. Не нужен новый crypto format, remote key unwrap, plaintext tar на диске, внешний tar extractor или второй journal. Linux выбран из-за требуемых POSIX ownership/no-follow гарантий; Windows остаётся оператором, не portable extraction target.

## 2. Конкретные порты и reuse

Предлагаемые будущие файлы: внутренний `deploy/connect/backup-format.mjs` (вынести существующие envelope/decrypt/metadata/tar primitives один раз), новый `restore-backup.mjs` (два закрытых role entrypoints), новый `restore-backup.test.mjs`. R0 wrapper импортирует общий core, сохраняя поведение/receipt/error; прежние causal tests не переписываются ради PASS.
Общий parser получает фиксированные режимы `verify` и `restore`: первый сохраняет прежнюю совместимость, второй добавляет строгую extraction policy и один awaited sink. Payload проходит кусками, без массива событий на весь архив; grammar/checksum/PAX/SQLite-header logic не копируется. R0 не приобретает plaintext callback или output stream.
Operator port: `sendAuthenticatedBackup({file,privateKeyPem,expectedSha256,expectedManifestSha256,sourceWitness,output,limits,signal}) -> Promise<{authenticated:true,archiveSha256,plaintextSha256,manifestSha256,plaintextBytes}>`. `output` — только принадлежащий вызову binary Writable защищённого канала, не путь/console; это новый привилегированный restore port, не изменение verifier API.
Receiver port: `extractOwnedBackup({input,target,expectedManifestSha256,sourceWitness,limits,signal}) -> Promise<{extracted:true,targetId,manifestSha256,plaintextSha256,plaintextBytes,entries,fileBytes,readbackVerified:true}>`. `target` — переданные trusted controller exact owned identities и свежие фиксированные `dataRoot`/`configRoot`, не путь из metadata; функция не создаёт Docker resources и не запускает приложение.
Оба ожидаемых archive/manifest hashes приходят из **protected durable backup-stage evidence**, связывающего generation ID и pre-backup checkpoint; receiver получает тот же manifest pin. `sourceWitness = {generationId,checkpointSha256,inventorySha256}` берётся из отдельно сохранённого cold-source inventory до backup. Это обязательные trusted inputs прежнего journal, не значения из входного tar, позднего sender result или R0 receipt; дополнительный RPC не требуется.
Receiver receipt **не содержит `authenticated:true`, `restored:true` или release-ready**: GCM выполнен у оператора. Existing first-transition journal принимает extraction только по обоим receipts, совпадающим plaintext/manifest hashes и числам, archive pin, actual child completion и target identity. EOF, stdout либо нулевой exit одного helper этого не доказывают.
Эти ports и hashes — закрытый control plane. Human-facing receipt ограничена whole-ciphertext SHA, counts, owned target ID и fixed stage/result; private plaintext/manifest hashes остаются в protected control channel/journal. File names, per-file/config/key digests и secret metadata наружу не выдаются.

## 3. Аутентификация, транспорт и приватность

До первого plaintext byte sender полностью проверяет strict restore profile и GCM по transaction-owned неизменяемой ciphertext copy; archive SHA и authenticated manifest SHA должны совпасть с `expectedSha256`/`expectedManifestSha256`, а generation/checkpoint/inventory — с независимым `sourceWitness`. Receiver сверяет тот же manifest pin и witness. Copy имеет private ACL, единственного владельца и закрытый creation writer. Один read descriptor сохраняется между проходами; stat/inode сами по себе не доказывают отсутствие in-place writer.
Второй проход по тому же descriptor расшифровывает исходное framing `metadataLength + metadata + tar` прямо в binary pipe, с backpressure, повторным GCM final и повторным ciphertext SHA. Изменение файла между проходами или failure final отменяет accept даже при полностью записанном tar. Receiver пишет только quarantine; `output.end()` допустим после final/совпадения digest, failure разрушает канал; sender success формируется после завершения всех собственных writes/close.
Транспорт будущего root adapter — уже одобренный authenticated encrypted operator→host channel с закреплённой host identity, без PTY/text transcoding/PowerShell pipeline для binary payload. Долговечный RSA из existing DPAPI CurrentUser поступает локальному Node только через bounded private stdin, никогда argv/env/remote/disk/log. Не передавать content key вместо этого потока.
Remote helper network-none; транспорт завершается снаружи helper и подаёт stdin exact owned process. Родитель получает stdout только как safe receipt ≤64KiB; stderr — fixed refusal, не plaintext/metadata/crypto stack. Buffers очищаются best-effort; JavaScript strings/crypto memory не объявляются гарантированно стёртыми. Private plaintext на isolated volume неизбежен и остаётся под private storage ACL; удаление volume не является доказательством физического secure erase.

## 4. Полнота одной cold generation

Минимальное producer-дополнение — bounded `restoreManifest` в **существующей encrypted metadata**: generation ID, pre-backup controller checkpoint digest, exact logical files/types/sizes/SHA256/uid/gid/mode, store identities/formats либо явное допустимое отсутствие, external dependency inventory. Полный metadata JSON по-прежнему ≤4MiB. Manifest строится при подтверждённой остановке всех writers и сверяется с архивируемыми bytes; live последовательные DB copies не получают статус cold generation.
Completeness имеет независимый источник истины: существующий fresh inventory/checkpoint фиксирует required stores, external dependencies и полный logical inventory **до backup**, отдельным обходом cold source, не копированием manifest producer. Для witness и manifest применяется одна фиксированная проекция/сериализация inventory (упорядоченные logical paths/IDs, типы, размеры, digests, uid/gid/mode, required store/dependency identities и explicit absence); её SHA сверяется по `sourceWitness.inventorySha256`. Расхождение — отказ до transfer/accept. Одновременный пропуск БД из tar и manifest не может пройти эту проверку; последующее создание fresh DB приложением ничего не исправляет и не скрывает.
Обязателен весь `/data`, включая main+WAL/sidecars, Connect/World/Notes/Capabilities+OAuth/Apps/Rooms SQLite и legacy files, connector ledger/maintenance и остальные фактические durable files. Никаких автоматических пропусков «неизвестного» store, удаления WAL, исправления malformed room source либо создания отсутствовавшей БД. Manifest entries и tar materialized entries должны совпасть точно, включая directories и пустые файлы.
Внешние app tokens, OAuth JWKS/cookie/artifact keys+key ID, issuer/audience/profiles, approved config/env provenance, trust/source/image pins, host/module journals и timer/controller config перечисляются по fresh inventory. Обязательное отсутствие или неизвестный внешний RW dependency → completeness refusal. Значения секретов только в authenticated metadata; текущий единственный `secrets` bind недостаточен. Личные operator/device signing keys не добавляются.
External files восстанавливаются в отдельный фиксированный `configRoot` по allowlisted logical IDs; metadata `Mounts.Source` никогда не становится write destination. Это защищённые operational restore files только для isolated run, **не generic plaintext config backup**; предпочтительны ограниченный tmpfs либо private dedicated mounts с exact lifecycle, не shared directory. Canonical recovery copy остаётся encrypted B. Digests/sizes/modes config проверяются так же; файлы не попадают в public receipt или общий архив plaintext.
Archived host journals — данные проверки, не команда исполнить прежний pending action или перезаписать live controller. Один generation связывает archive/manifest/независимый inventory/checkpoint; конечные archive и manifest hashes записываются действующим protected backup-stage evidence после backup и до transfer, без self-hash рекурсии.
Старый SOTYBAK1 без полного manifest может по-прежнему пройти R0, но R1 выдаст «Архив не содержит полного состава для восстановления». Дополнительные source files producer/operator понадобятся только следующим согласованным integration increment; новый формат шифрования для этого не нужен.

## 5. Строгая политика Linux sink

Prerequisite: свежий private namespace mode0700 и пустые roots на local Linux filesystem, exact root device/inode/mount identities известны controller; другой write principal/mount отсутствует. Helper — единственный writer, без Docker socket/serving mounts/egress. Не обещаем защиту от hostile host root или raced ancestor replacement сторонним writer; при таком окружении отказ, не fallback к обычному path-based extract. Windows sink явно unavailable.
Материализуются только regular `0` и directory `5`; один tar root `.` допустим. Symlink/hardlink/device/FIFO/contiguous `7`/sparse/unknown types запрещены. Existing bounded PAX/GNU long-name grammar переиспользуется; restore разрешает только явные path/size и обычные numeric owner/time metadata, отвергает linkpath, sparse/ACL/xattr и неизвестные semantic extensions, а не молча теряет их. Legit links/ACL требуют отдельного reviewed profile.
Fatal UTF-8 для имён; POSIX relative paths без control codepoints U+0000–001F/U+007F–009F, backslash/absolute/drive/`..`, без Unicode normalization/URL decode. Убираются только tar `./` aliases при canonical key; повтор effective key, file/directory collision или файл в ancestor position запрещены. Parent directory должен уже быть проверен и создан этим sink; никаких recursive mkdir по непроверенному пути. Extension records также считаются в лимит header count.
Каждый ancestor проверяется как directory на ожидаемом device, root identity повторно сверяется; final file открывается `O_CREAT|O_EXCL|O_NOFOLLOW|O_RDWR`, затем fstat regular/nlink=1/device. Directory entries не могут менять существующий чужой inode. No-follow относится и к configRoot. Нельзя ограничиться одним `path.resolve().startsWith(root)` или проверкой final component.
Files создаются 0600, directories 0700; исходные uid/gid и обычные permission bits восстанавливаются через owned descriptors, directories последними. Любые mode bits вне 0777/special metadata отвергаются. Сначала write/hash → fsync → same-file readback/hash → проверка размера → ownership/mode → metadata fsync; directory fsync входит в finish. Не нормализовать все владельцы в root: foreign UID/0600 должен пережить реальный Linux gate. Helper root с cap-drop ALL получает лишь CHOWN/FOWNER для смены владельца и последующего fchmod; parent directories остаются private до postorder finish, старый backup DAC_READ_SEARCH profile не копируется. Target не монтируется другим процессом до дальнейшего controller gate; actual full-image UID/config проверяются отдельно, probe UID10001 этого не доказывает.

## 6. Конечные пределы и cleanup

`limits` — **обязательный frozen input без production defaults**: max ciphertext/plaintext/file/extracted bytes, entries/headers/aggregate path bytes/depth, external file count/decoded bytes, wall/idle/cleanup milliseconds, helper RAM/CPU/PIDs и free-space reserve. Все значения конечны, положительны и проверены до открытия archive/target; missing/unknown/Infinity/overflow → отказ. Root фиксирует exact числа по fresh inventory и capacity в том же transaction profile до исполнения; исторические ~90MiB не задают ни size ceiling, ни RTO. Превышение не увеличивает лимит автоматически.
Неослабляемые format caps: header ≤16KiB, metadata/одна extension ≤4MiB, UTF-8 path ≤4096B/component ≤255B; explicit limits могут только сузить их. Один поток/один file body, chunk ≤64KiB, одна awaited write; без unbounded queue/concurrent restore. Все byte/count additions проверяются до allocation/write, extensions/padding/trailing bytes входят в input/header caps. Free-space gate ≥declared extracted bytes + frozen reserve — не reservation; ENOSPC всегда отказ без partial accept.
Отдельный **fixture profile, не production обещание**: ciphertext/plaintext/extracted ≤16MiB, file ≤8MiB, entries ≤256/headers ≤512, aggregate paths ≤64KiB/depth ≤16, external ≤8/decoded ≤256KiB; RAM256MiB/1 CPU/32 PIDs/reserve32MiB; wall30s, idle2s, cleanup10s. Tests могут уменьшать эти числа для causal limit+1/timeout. Общий deadline включает verify/transfer/readback и не продлевается; idle после первого byte не заменяет его. Signal/timeout прекращают writes и закрывают owned streams/descriptors, parent watchdog независим от helper event loop; после отдельного cleanup deadline остаётся pending, а не ложный bounded-success.
В том же first-transition journal **до CREATE** фиксируются owned names/spec/labels, pins/profile/deadline и restore-stage intent. Docker-assigned ID сохраняется после exact name/spec/label readback **до START**; lost CREATE ACK разрешается inspect/reconcile ранее записанного имени, не повторным CREATE или новым именем. Для target фиксируется фактически подтверждённая resource identity. Только parent останавливает/удаляет exact собственные ресурсы; library не делает recursive delete по входному пути. Kill/error/timeout не означают exit: actual child close + Docker inspect stopped/no mounts, затем exact removal/readback. Не удалось подтвердить — `cleanup_pending`, closed admissions, target не используется, чужие ресурсы не трогаются.
Lost receipt не вызывает extraction поверх непустого target: existing stage reconciles точные identities/evidence; без полного доказательства target остаётся quarantine, сначала confirmed cleanup, затем новый owned attempt. Не появляется новый job/deploy ledger. Возобновление этой стадии не разрешает START O/C/R; application restore proof — отдельная последующая стадия D2.

## 7. Refusals и конечная приёмка

Новые restore ports имеют фиксированные safe errors без path/secret/raw cause: `restore_authentication_failed` — «Подлинность архива не подтверждена»; `restore_incomplete` — «Неполный состав восстановления»; `restore_target_invalid` — «Цель не свежая или не принадлежит операции»; `restore_archive_invalid` — «Неподдерживаемый или неоднозначный состав файлов»; `restore_limit_exceeded`, `restore_timeout`, `restore_io_failed`, `restore_cleanup_pending` — короткие фиксированные пояснения. R0 сохраняет только прежний `backup_verification_failed`.

| Подшаг / gate | Минимальное проверяемое доказательство |
| --- | --- |
| R1a common core + strict dry check | Неизменённый R0 10-case gate; authentic fixtures с links допустимы старому verifier и запрещены restore mode. Bad key/tag/truncation/metadata/manifest не дают ни первого plaintext byte, ни target acceptance |
| R1b Linux sink | Synthetic encrypted all-store/config fixture → exact bytes/main+WAL/modes/owners/manifest readback на настоящем Linux. Traversal/duplicate/PAX alias/type/invalid UTF-8/ancestor link/preexisting target/limit+1 отказ; внешняя sentinel file неизменна. Не копия parser assertions, а filesystem outcomes |
| R1c operator binary handoff/lifecycle | Cipher mutation между проходами и final-tag failure после transfer, pipe disconnect/held write/ENOSPC/timeout/kill: ни accepted target, ни ложный cleanup. Реальные helper/volume cleanup и lost-receipt reconciliation по прежнему journal; foreign resource сохраняется; secret/metadata canaries отсутствуют в public outputs |
| R1d producer completeness | Quiescent fixture archive включает все stores/main+WAL и external config из независимого cold-source witness; missing/extra/different generation/unknown RW dependency отказывают. Один обязательный omission negative: producer одновременно убрал одну БД из tar и manifest — witness mismatch, 0 accepted targets, application не стартует создавать fresh DB. Legacy archive без manifest остаётся verifier-compatible, но не проходит completeness; это ещё не current server backup |
| Следующий full-image gate, не PASS R1 | Именно реальный cold B со всеми external dependencies → C opening/reconcile/restart → R на C-produced copy; exact image digests/reader3/default-off, domain/FK/FTS/proof/authority проверка. Fixture bytes/header/SQLite quick_check либо successful extractor этого не заменяют |

Минимальная последовательность implementation review: общий core/R0 parity + fixture → Linux owned quarantine → operator SSH binary handoff в existing controller stage → all-store/config producer manifest → isolated full-image proof. Пока определены source/API и обязательная форма profile; ни готовый restore, ни новый serving baseline, ни разрешение writers результатом этого документа не объявлены.

Первичные границы: GCM authenticity подтверждает [`decipher.final()`](https://nodejs.org/download/release/v24.21.0/docs/api/crypto.html#deciphersetauthtagbuffer-encoding), не `update`; [`O_NOFOLLOW`/`O_EXCL`](https://nodejs.org/download/release/v24.21.0/docs/api/fs.html#file-open-constants) не заменяют ownership ancestors и не одинаково доступны Windows; [`child_process error/exit/close`](https://nodejs.org/download/release/v24.21.0/docs/api/child_process.html#event-error) не позволяют признать failed kill подтверждённым завершением. Это документация primitives, не evidence запуска нашего helper.
