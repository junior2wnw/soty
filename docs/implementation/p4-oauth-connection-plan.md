## 1. Два рекомендуемых решения

1. **`oidc-provider@9.12.2`, Authorization Code + обязательный S256, два заранее зарегистрированных public clients.** AS обеспечивает протокол; существующий Connect подписывает осознанное согласие. В C1 нет DCR/CIMD, собственных grant types, OIDC-входа в Соты, ID Token/UserInfo, device flow, token exchange или универсального IdP. Один scope `notes.createDraft` означает создание нового приватного черновика и чтение минимального receipt только своих вызовов этого подключения. Он не означает чтение записок, cancel, derive либо публикацию. Refresh выдаётся по этому явному ограниченному consent через штатный `issueRefreshToken`, без обязательного добавления `openid`/`offline_access`.
2. **AS artifacts и связь OAuth → существующие права находятся в той же Capabilities SQLite, в additive формате v3.** Это не второй Invocation/budget/account ledger. Каждый access token связывается с отдельной существующей `cap_credentials` строкой; principal/client/grant стабильны в пределах подключения. Короткие токены не продлевают исходное право уже принятого Invocation.

Отдельная AS DB технически возможна, но требует дополнительных состояний между AS consume/revoke и Capabilities commit. Чтобы отзыв семьи гарантированно участвовал в последней проверке перед Notes effect, пришлось бы вводить ещё один cross-store reconciliation/authority seam либо третью БД в Connect → Caps → Notes fence. В одной Caps transaction можно атомарно связать AT с credential и завершить reuse → domain revoke; поздняя запись увидит тот же отозванный grant. Это основание выбора, а не утверждение, что OAuth вообще требует общей БД. Асинхронный `grant.revoked` observer не заменяет этот commit.

Альтернатива «одна продлеваемая credential на всё подключение» уменьшает число строк, но требует нового доверенного AT lease/revocation proof внутри actor и persisted authorization snapshot B2. Для этого среза она сложнее и отклоняется. Цена выбранного решения — явная bounded retention только неиспользованных истёкших OAuth credentials (§6).

## 3. Минимальный wire profile

`H` — заранее проверенный shell HTTPS origin; для изолированных тестов допускается только уже разрешённый точный loopback. Issuer `H + /oauth`. Ни одна величина не вычисляется из произвольного Host/Forwarded. На app runtime origins эти маршруты отсутствуют.

**Разные audiences сохраняются:** HTTP resource равен текущему `capabilityAudience` (сейчас это exact origin, не URI с path); MCP resource — `H + /mcp`. Текущий [HTTP validator](../../server/capabilities-actions.js) принимает origin через `validateDiscoveryOrigin`: молча заменить его на `/api/capabilities` нельзя. Каждое подключение, code/RT/AT и domain credential связывается ровно с одним ресурсом. OAuth token для MCP не открывает HTTP native endpoint, и наоборот. При необходимости человек создаёт отдельное подключение для второго ресурса.

| Маршрут | Назначение |
|---|---|
| `GET /.well-known/oauth-authorization-server/oauth` | RFC 8414 metadata точного issuer; root монтирует штатный discovery AS |
| `GET /oauth/.well-known/openid-configuration` | Совместимый metadata alias того же provider/issuer, без обещания OIDC login |
| `GET /.well-known/oauth-protected-resource` | HTTP resource metadata: exact `capabilityAudience`, issuer, один scope |
| `GET /.well-known/oauth-protected-resource/mcp` | Отдельный MCP resource metadata; не объявляет MCP methods уже реализованными |
| `GET /oauth/authorize` | `response_type=code`, exact static client, redirect, S256, state, один resource/scope |
| `POST /oauth/token` | Только urlencoded authorization_code и refresh_token; public auth method `none` |
| `POST /oauth/revoke` | Штатный RFC 7009; revocation связана с domain authority (§5), неизвестный token не раскрывается |
| `GET /oauth/jwks` | Публичная часть постоянного AS key configuration, если её публикует выбранный profile; не новые полномочия |
| `GET /oauth/interaction/:uid` и `/context` | Страница/короткое предложение доступа, привязанное к browser interaction, без callback tokens |
| `POST /oauth/interaction/:uid/complete` | Возобновляет только собственный уже подтверждённый/отклонённый interaction; не принимает account/grant/returnURL |

Штатный [discovery 9.12.2](https://raw.githubusercontent.com/panva/node-oidc-provider/v9.12.2/lib/actions/discovery.js) объявляет S256 и `authorization_response_iss_parameter_supported:true`. В actual authorization response проверяется тот же `iss`. Нельзя рекламировать эту поддержку только добавлением поля к своему JSON.

Static IDs: `soty-codex-cli` и `soty-opencode-cli`, `application_type=native`, `token_endpoint_auth_method=none`, `grant_types=[authorization_code,refresh_token]`, `response_types=[code]`. Client ID публичен и **не аттестует официальный executable**. Redirect host/path регистрируются по фактически показанному выбранным CLI callback; допускается только loopback port variation по RFC 8252, без wildcard host/path/query и без `localhost` как замены зарегистрированному `127.0.0.1`. Для Codex официальный `/callback` требует issuer identification; fallback suffix старого клиента нельзя угадать заранее. Для OpenCode исходный default приведён выше. Нет client_secret в CLI, регистрации по URL или удалённой загрузки logo/JWKS/client metadata.

Provider config задаётся явно: `responseTypes:['code']`, `pkce.required:()=>true`, static clients, resourceIndicators с allowlist и непродляемым connection expiry, revocation включённая с `revokeGrantPolicy:()=>true`, refresh rotation `true`, **`expiresWithSession:()=>false`**. Последнее обязательно: default9.12.2 при отсутствии `offline_access` равен true, а token helper требует существующий Session и совпадение текущего session grant. Иначе короткий Session600s обрывает обещанный connection24h, а новый consent того же profile может погасить sibling. Профиль привязывает право к durable connection/root/creator/absolute expiry, не browser login; новый scope не добавляется. DCR/CIMD, UserInfo, implicit/hybrid, password/client_credentials, PAR/JAR, device/CIBA, introspection для третьих сторон и экспериментальные features выключены. `findAccount` получает только уже подтверждённый Connect account; никакие email/profile claims не выдаются. AS `Session` не создаёт человеческий actor.

Стартовые сроки: interaction 10 минут, code 60 секунд, AT `min(300s, grant.expiresAt-now)`, RT/Grant не позже абсолютного connection expiry, consent по умолчанию **24 часа и 20 созданий**. Это предлагаемые пилотные пределы, не параметры RFC. Пользователь видит меньший фактический срок/остаток; refresh не сдвигает конец. Бюджет — существующий `cap_budgets`, без OAuth-аналога.

Authorize требует один resource; token/refresh могут опустить его только для уже однозначно связанного единственного ресурса. Если передан — exact match; иной ресурс, повтор параметра или массив отклоняется. Resource-проверка выполняется **до consume** (§5). Scope неизменен (`notes.createDraft`); запрос иной комбинации получает `invalid_scope`, а не расширяет grant. Public catalog остаётся public и не приобретает private view.

Внешние private API принимают bearer только в единственном Authorization header, не cookie/query. PRM challenge указывает metadata соответствующего ресурса. На `/mcp` C1 может закончиться честным auth/discovery probe; реальный initialize/tools transport и его ready claim относятся к C2. Если CLI требует работающий MCP для завершения login, его end-to-end acceptance остаётся открытым до C2, без фиктивного MCP ответа.

## 4. Consent с единственным Connect account

1. AS проверяет protocol request и создаёт короткий interaction. Host выдаёт browser-bound presentation `{interactionId,contextDigest,browserNonce,clientLabel,resource,scope,expiresAt,budget}`. Digest охватывает issuer, static client, точный redirect, resource/scope и ограничения. Browser nonce хранится как digest и связан с uid/cookie; uid сам по себе не разрешение.
2. На существующем shell origin человек видит текущий Connect account, профиль клиента, «создавать новые личные записки», срок/лимит и «не может читать или менять существующие». Два действия: разрешить/отказать. Никакого OAuth-пароля, выбора произвольного accountId или второго списка пользователей. Основной текст укладывается в одну карточку 320px, targets ≥44px; детали не заслоняют account и эффект.
3. Подписанная Connect extension `oauth.connections.approve` принимает `{expectedAccountId,interactionId,contextDigest,browserNonce}`. Реальный проверенный actor задаёт account и creator device. Пока существующая signed Connect transaction держит authority fence, одна Caps transaction CAS-переводит interaction в approved, создаёт ровно одну connection и существующие cap client/service principal/root grant/budget. Внутри `Connect.handle` повторно вызывать `withAuthorityFence` нельзя: текущий API запрещает nested handle/fence. Scope fixed, delegation выключена. Повтор exact interaction возвращает те же IDs; конфликт не создаёт ещё один grant. `deny` и owner `connections.list/revoke` — тоже signed operations, не bearer owner API. Ошибка последующего Connect COMMIT/ответа не доказывает rollback уже сохранённого Caps approval: точный retry сверяет interaction, а token issuance всё равно заново проверяет creator.
4. После этого async host completion вызывает `beginGrantBinding({interactionId,browserNonce})`: получает короткоживущий branded context и уже связанный providerGrantId либо null. Root передаёт context через свой request-local ALS только вокруг `provider.Grant.save()`. Domain `Grant.upsert` атомарно вставляет artifact и CAS-связывает его ID с connection; конкурирующий иной Grant получает conflict без orphan INSERT. Root вызывает `endGrantBinding` в `finally`. **Нет await внутри SQLite/Connect transaction.** Connection до связи не допускает token upsert; AT/RT не принимают stagedGrant context. Ошибка после COMMIT не снимает binding: повтор после crash загружает единственный сохранённый Grant. Нет имитации общей атомарности всех AS шагов.
5. Resume URL даёт только provider; `complete` сверяет тот же browser interaction/nonce и durable approval. Новая выдача после любого await заново проверяет connection/creator/grant. Code обменивается библиотекой; token endpoint не принимает заново account/device и не переносит consent из другой вкладки.

Cookies AS: Secure/HttpOnly/SameSite с узким path и постоянными signing keys, CSRF/origin защита completion, `frame-ancestors 'none'`, `Cache-Control:no-store`, `Referrer-Policy:no-referrer`. Runtime iframe не является местом consent. Cookie/прежняя AS session не разрешает автоматическое новое подключение: **каждый новый code flow** всегда подтверждается живым signed Connect actor; только refresh действующей семьи обходится без повторного UI. Публичный client ID может использовать другая программа, поэтому remembered consent не достаточен — [RFC 8252 §8.6](https://www.rfc-editor.org/rfc/rfc8252.html#section-8.6). Закрытие/отмена не выдаёт token; поздний ответ после смены account не рисует успех в другой UI.

Смена локального account **до** signed approve закрывает старый UI intent. Уже закоммиченное согласие account A не становится согласием B при позднем ответе. Сервер не обещает узнать неотправленную локальную смену аккаунта; в такой гонке результат остаётся привязанным A и доступен для отзыва владельцем A. OAuth code/AT никогда не показываются как PWA grant token.

После approval copy: «Доступ разрешён. Вернитесь в клиент». C1 не рисует «Клиент подключён»: даже token COMMIT не доказывает доставку ответа, а конкурентный reuse может немедленно отозвать семью. Последующий успешный authenticated RS request и живая connection могли бы дать более сильное evidence, но ради badge новая таблица/handshake не вводится. В «Доступах и действиях» — профиль клиента, ресурс, срок, остаток существующего бюджета, отзыв и уже существующая owner history. Offline не ставит approval в outbox; пользовательский Notes draft остаётся в своей прежней области. Provider cookies не участвуют в доступе PWA к результату `#notes/...`.

Host/PWA seam обязателен: `/oauth` и все OAuth/PRM `.well-known` routes — **network-only без SPA fallback и без offline consent cache**. Нынешний `public/sw.js` отдельно исключает `/agents` и `/api/capabilities`, поэтому этот новый namespace надо явно добавить и проверить с уже управляющим worker. Cached Notes shell по URL consent не считается отказом AS и не должен отображаться как настоящая страница подключения.

## 5. Adapter/authority contract и реальные гонки

У [adapter interface 9.12.2](https://raw.githubusercontent.com/panva/node-oidc-provider/v9.12.2/example/my_adapter.js) есть `upsert/find/findByUid/findByUserCode/consume/destroy/revokeByGrantId`. Нужен постоянный adapter, не memory example. Allowlist C1: `Session`, `Interaction`, `Grant`, `AuthorizationCode`, `RefreshToken`, `AccessToken`; `Client.find` возвращает отсутствие для неизвестного static ID, `findByUserCode` — отсутствие, device artifacts не создаются. Неожиданный model/shape/sрок отказывает до записи.

`Provider.ctx` — документированный request-local ALS getter, доступный в adapter (см. [General access to ctx](https://raw.githubusercontent.com/panva/node-oidc-provider/v9.12.2/docs/README.md)). Adapter снимает immutable request binding при входе; не сохраняет Koa ctx/req/token в глобальном registry и не принимает user-created ctx. Host completion имеет отдельный закрытый порт для Grant binding, а не поддельный token request.

- **AT upsert:** opaque [format](https://raw.githubusercontent.com/panva/node-oidc-provider/v9.12.2/lib/models/formats/opaque.js) возвращает `token.jti` как token value, [BaseModel.save](https://raw.githubusercontent.com/panva/node-oidc-provider/v9.12.2/lib/models/base_model.js) передаёт тот же ID в adapter. Проверяются client/account/providerGrant/resource/единственный scope и `payload.exp` относительно durable connection. Под свежим Connect → Caps fence сохраняются AS artifact, `SHA256(opaqueToken)` в новой cap credential и link **одним COMMIT**. Никакого raw token в Cap audit/receipt. Существующий `soty_cap_…` parser не расширяется до «любой строки».
- **Срок:** `upsert(..., expiresIn)` бывает без ttl для BaseToken. Авторитетен проверенный `payload.exp`, единицы секунд явны; отсутствие/неfinite/нецелый exp или выход за connection bound — ошибка, не бессрочная запись. Пределы для untokenized Session/Interaction также заданы явно. Repeated upsert AT не меняет immutable pins/expiry существующей credential.
- **Refresh/code consume:** одна SQLite CAS по model+ID+`consumed_at IS NULL`. Все protocol/client/resource проверки — до мутации. Проигравший concurrent consume возвращает публичный `errors.InvalidGrant`, атомарно отзывает связанную семью/domain grant и её credentials, а не generic 500. Throw выполняется после durable revoke COMMIT, чтобы исключение не откатило защиту. Consume штатно вызывается библиотекой; PKCE/code криптографию не переписываем.
- **Resource до consume:** в [refresh_token.js 9.12.2](https://raw.githubusercontent.com/panva/node-oidc-provider/v9.12.2/lib/actions/grants/refresh_token.js) rotation consume/save стоят раньше финального resource resolution. Поэтому adapter `consume` проверяет уже parsed `Provider.ctx.oidc.params.resource` и authenticated client против stored RT/code binding **перед CAS**. Missing допускается только для единственного bound resource. Иной resource → `errors.InvalidTarget`, без consume/revoke/нового RT. Это public adapter + public context seam, без импорта внутренних grant helpers. Отдельный actual wire test обязан подтвердить этот порядок на pinned library.
- **Reuse/revoke:** библиотечный consumed path вызывает destroy/revoke параллельно; все store mutations идемпотентны. `revokeByGrantId` и `Grant.destroy` в той же Caps transaction закрывают connection, исходный domain grant и OAuth credentials. **Любой AT/RT revoke через `/oauth/revoke` отключает всё это подключение**, не другие connections. Так действует согласованный профиль: [revocation.js](https://raw.githubusercontent.com/panva/node-oidc-provider/v9.12.2/lib/actions/revocation.js) вызывает [revoke helper](https://raw.githubusercontent.com/panva/node-oidc-provider/v9.12.2/lib/helpers/revoke.js), который отзывает связанные token models и при `revokeGrantPolicy:false`; этот flag не делает AT revoke узким. Поэтому используем `true`, честное UI «отключить подключение» и при необходимости новый consent, без custom revocation implementation. Existing non-OAuth service credential revoke остаётся прежним. Повтор grant upsert/RT save/AT save после family revoke не восстанавливает право. Отзыв через PWA использует тот же domain commit; AS cleanup может закончиться позже, но admission уже закрыт.
- **Последующий bearer:** host передаёт token только закрытому `oauth.authenticateBearer({token,audience})`. Порт возвращает существующий branded service actor, проверив digest/link, exact issuer/client/resource/connection, expiry и `currentCredential`/grant chain. OAuth-specific rows участвуют в повторном `currentCredential` перед effect, включая operational AS-off baseline; одной удачной AS проверки до await недостаточно. Внешний callback не может изготовить actor по `{accountId,sub}`.
- **Original vs current:** refresh создаёт новую credential и позволяет current own read/replay в той же account/client/principal/grant области. Invocation хранит прежний credentialId и абсолютный expiresAt; до нового эффекта проверяется именно он. Операционное выключение Notes не отзывает связь и не прячет прежний receipt. После revoke proof-positive reconcile по B2 может записать случившееся, но actorless internal result не возвращается клиенту без нового authorized read.

Связь с OAuth policy должна быть в общем credential resolution, а не только в HTTP middleware: иначе действие после async boundary могло бы пройти на уже отозванном AT. Sibling connection revoke не отменяет другую цепочку только из-за общего epoch; требуется свежая полная chain evaluation.

Legacy owner API не выпускает `soty_cap_` credential либо новый grant на OAuth-linked client/principal/root: `credentials.issue` и `grants.issue/derive` получают `oauth_managed_authority`. Baseline3 common resolver требует exact OAuth link для любого credential этой authority даже при AS off; отдельный обычный service principal/client сохраняет прежнее поведение. Generic owner revoke OAuth credential использует общий family revoke, ordinary non-OAuth revoke остаётся точечным. Redirect allowlist поступает domain через закрытый sync `isRegisteredRedirect({clientId,redirectUri})` из той же static client configuration root, без отдельной изменяемой копии.

Один HTTP token request не объявляется единой transaction: consume может закоммититься, а последующее token save/ответ — не состояться. При concurrent refresh reuse-защита может отозвать **даже token победителя**; обещается максимум один успешный consume, не один гарантированно действующий результат. Старый code/RT не становится снова непотреблённым; безопасный исход после lost response — re-consent, иногда недоставленный token, но не повтор права по старому code. Если уже выданный token успел создать Note до последующего отказа/revoke, Note/receipt сохраняются; OAuth failure не доказывает отсутствие эффекта.

Re-consent после отзыва создаёт новую connection/rootGrant. Новый actor **не читает старый grant-scoped receipt** и не продолжает unresolved intent автоматически; прежнюю историю видит owner в PWA. Инструкция «подключитесь заново» не означает восстановление старого результата клиента.

Для защиты от автоматического CLI retry root принял отдельную **OAuth-only область занятого ключа: account + issuer + static client profile + resource**. В прежней Caps admission transaction после current authorization и same-connection replay native coordinator проверяет существующие `cap_invocations` через неизменяемые `cap_oauth_connections` pins. Тот же request key в **другой** connection этой области всегда даёт одинаковый `invocation_request_conflict`: без body/status/receipt/Note ID и без нового эффекта, включая terminal/purged rows и другой input. Прежний intent под новый grant не переносится. Scope получается только из закрытой ссылки branded actor; пользователь не передаёт issuer/profile/connection в native args. Same-connection refresh/replay, non-OAuth service credentials и другие account/profile/resource сохраняют прежнюю независимость. Connection pins остаются вместе с историей; нового ledger нет.

Tradeoff явный: новый OAuth grant может узнать **один бит о занятости собственного opaque key** в этой общей области; публичный client ID не доказывает, что программа та же. Клиенту рекомендуются уникальные непредсказуемые keys, но сервер не утверждает, что проверил их энтропию. При conflict человек проверяет owner history перед явным новым действием с новым ключом. Гарантия относится к тому же ключу; новый key не обнаруживает смысловой дубль текста.

## 6. Caps v3: ровно OAuth storage, без новой доменной модели

Предлагаемые объекты ниже — **DDL freeze следующего шага**, не существующие таблицы. Notes остаётся v2; прежние v2 tables/triggers и catalog pins не переписываются.

| Новый объект | Минимальные поля/инварианты |
|---|---|
| `cap_oauth_connections` | `id`, account/internal client/principal/rootGrant/creatorDevice; `issuer`, static oauthClientId, resource, fixed scope, consent digest, absolute expiry, state/created/revoked; providerGrant ID сначала null, затем unique write-once. Same-account composite linkage проверяется по существующим rows; чужой root/creator запрещён. State не возвращается из revoked/expired в active. |
| `cap_oauth_interactions` | uid/hash, browser nonce hash, request digest, exact bounded presentation, expires, approved/denied/consumed state, connection FK. CAS на конкретный request, одно approval, no tokens. Отдельных user/account таблиц нет. |
| `cap_oauth_artifacts` | `(model,id_hash)` PK, bounded encrypted provider payload, checked expires/consumed, providerGrant correlation, hashed Session uid lookup; индексы expiry/grant/uid. Codec/profile pin `oidc-provider-9.12.2-c1`; не допускается произвольный JSON для будущих protocols. |
| `cap_oauth_credentials` | credential FK, connection FK, unique AT digest/artifact correlation, immutable exact audience/expiry linkage. Source of authority — существующие cap rows плюс эта проверяемая связь. Link переживает AS token cleanup, если original credential ещё referenced. |
| Индекс original credential | Expression index по `json_extract(cap_invocations.authorization_json,'$.credentialId')` для защиты retention от полного scan на каждый cleanup. В C1a EXPLAIN/large fixture проверяет реальный план; это индекс ссылок, не новая invocation table. |
| Индекс OAuth key conflict | `(account_id,request_key,client_id)` на прежних `cap_invocations`; exact query plan должен подтвердить bounded lookup, покрывающий client ID для связи с connection. Не содержит input или receipt. |

AS payload содержит `jti` и потому может содержать bearer secret даже при hashed primary key. Предлагается небольшой закрытый codec `node:crypto` AES-256-GCM: случайный nonce, AAD связывает registry/issuer/model/id hash/profile, ключ host-owned вне БД. Payload ≤16 KiB UTF-8 до encryption; каталог и receipts не содержат его. Постоянные AS cookie/JWKS/storage keys имеют разное назначение, не генерируются заново при reopen. Это защита хранения, не собственная OAuth криптография. Отсутствующий/иной ключ при включении AS означает controlled unavailable, не удаление artifacts и не «новый чистый AS». Обычный reader3/owner history/proof reconcile не требуют расшифровки AS payload. Backup с ключами — только зашифрованный; ключи не входят в Git/config diff/log.

**Зачем retention обязательна.** Сейчас [credentials.issue](../../modules/capabilities/server/access.mjs) считает все credential rows с пределом 10 000/account, а [v2 reader](../../modules/capabilities/server/schema-v2.mjs) требует существования original credential даже у terminal native receipt. AT каждые 5 минут дал бы 288 строк/сутки на одно подключение. Нельзя ни бесконечно добавлять их, ни удалять referenced credentials, ни обновлять старой строке expiry.

Предлагается один bounded cleanup batch ≤64 перед новым OAuth issuance/на timer:

- удаляются только истёкшие OAuth artifact/link/credential, у которых **нет ни одного** `cap_invocations.authorization_json.credentialId` reference; проверка и delete под одной Caps transaction;
- original credential/link для любого Invocation, включая terminal, остаются навсегда в пределах принятого pilot ledger bound; raw token artifact после expiry можно удалить. Dispatch input purge этого не меняет;
- прежние service credentials не очищаются этим механизмом. Их существующая quota 10 000 считается по service rows; OAuth transient allowance не расходует её. OAuth referenced rows ограничены числом native Invocation identities (нынешний bound 10 000/account); fresh AT для чтения не блокируется лишь потому, что этот исторический предел достигнут;
- отдельный предел **64 живых OAuth AT/account**, 16 активных connections/account, один текущий RT на family плюс consumed tombstones до абсолютного конца family; полное хранилище consumed artifacts тоже bounded. Повтор/expiry/revoke не создаёт новый ledger budget. При заполнении transient bound новый token получает controlled quota/temporarily_unavailable; revoke/cleanup/owner read не блокируются;
- consumed RT/code records не удаляются пока family может работать: иначе reuse detection потеряет факт. После абсолютного expiry они и AS sessions/grants очищаются; durable connection/cap grant/history остаются. Переполнение AS artifacts не должно откатывать durable family revoke.

Для пилота предлагаются: ≤1 024 AS artifacts/connection, ≤256 живых unauthenticated interactions глобально, ≤65 536 artifacts глобально, ≤16 KiB на payload, ≤16 concurrent AS HTTP requests и конечный deadline 10s на получение тела. Это admission limits, не гарантия физического disk/RAM. Сначала истёкшие записи очищаются bounded batch; не удалять действующий grant ради выдачи нового. До DDL freeze проверить, что selected caps позволяют обычный 24h refresh и что retained references не учитываются как transient. Квоты не вводят второй счётчик совершённых Notes effects.

Для Session/Interaction, ещё не привязанных к connection, есть **общий cap 1 024 unbound artifacts глобально**, включая вспомогательные записи rejected/completion races, с expiry не позже 10 минут после первоначального создания и индексом expiry. Grant появляется только вместе с атомарной связью, orphan Grant запрещён. Это отдельная проверка от 256 pending interactions; callback race не создаёт бесконечные Grant rows. При approve до любых новых rows проверяются прежние lifetime limits `cap_principals < 1 000/account` и `cap_grants < 10 000/account`, активные connections <16/account, плюс пилотный глобальный предел 10 000 durable OAuth connections. Один approval создаёт ровно один principal/client/rootGrant; соответственно и repeated consent/revoke churn bounded. Exact approval retry не расходует новый slot, quota не блокирует revoke и owner history. Эти числа и их SQL admission predicates фиксируются в storage contract до реализации.

## 7. Миграция, keys и обратимость

Caps lineage `soty.capabilities.sqlite.v3`, `user_version=3`; projectId/registryId и все v2 IDs неизменны. Новый `allowOAuthMigration` — strict boolean default false, отдельно от `allowNativeMigration`. Обычный v1/v2 startup не создаёт OAuth tables; actual3 читается и при выключенном OAuth. Явный 2→3 upgrade создаёт пустые OAuth objects после exact known-format проверки. Если store ещё v1, native 1→2 — предшествующее явное действие, не скрытый OAuth bootstrap.

AS включается только при actual3, корректных issuer/static clients/persistent keys; не готовая схема даёт 503/disabled без миграции. Existing native v2 behavior, включая unavailable/disabled replay и proof-first recovery, сохраняется. Reader-only rollback не обязан выдавать новые tokens, но обязан правильно удерживать/reconcile исходные native effects и учитывать сохранённые OAuth revocations при проверке credentials.

Нужны две явные integration delta: нынешний `native-notes.mjs:capsIdentity()` принимает только version/lineage2, а `server/http-app.js` запускает recovery только при Caps2. Domain меняет первую границу на **точный admitted known2 или known3** с соответствующей lineage, прежними project/registry/semantic pins; root меняет scheduler на Notes2 + known Caps2/3. Не допускается `version>=2`, live format drift или потеря native row validation на3. Регрессия — исходный v2 native proof после реальной 2→3 migration, OAuth feature-off/без AS storage key и сохранённый original credential/recovery.

Manifest/probe envelope **3 остаётся**: расширяется только capabilities reader до `[1,2,3]`; Notes `[1,2]`, Apps `[1..6]`, Rooms `[1,2]` не переименовываются. Отдельная AS DB/inventory не добавляется. Historical exact v2 migrator/DDL фиксируются из принятого `cc7f65b` до любых v3 source edits, не строятся текущим v3 migrator с подменой version.

Перед firstv3write должен реально служить SAME old image, который уже читает3 без auto migration. Нужны literal fixture, main2+committed WAL3, refusal old2/future4, byte/side-effect evidence, exact new reader, Linux RO/cold encrypted backup/restore gate. Обычный feature-off не делает старый v2 binary совместимым. Reader probe распознаёт формат и известные projections, не обещает проверку секретного payload без key.

Восстановление старого backup может вернуть состояние до token rotation/revoke. Поэтому restore проводится offline; перед открытием AS/RS все восстановленные OAuth connections/token families должны быть отозваны отдельной проверенной recovery операцией и owner re-consent. Одна смена cookie/encryption keys недостаточна: cap token digests также могли восстановиться. Нельзя включить restore image и надеяться, что истёкший browser cookie закрывает старое право. Уже созданные Notes/receipts сохраняются по согласованному Connect/Caps/Notes restore contract.

## 8. Узкие API и непересекающееся владение

Предлагаемый domain port `capabilities.oauth` (доступен только host composition):

```text
readiness() -> { schemaVersion, available }
prepareInteraction(trustedRequest) -> browser-bound presentation
approve(actor, exactSignedArgs) / deny(actor, exactSignedArgs)
beginGrantBinding({interactionId,browserNonce}) -> {context,connection,providerGrantId|null}
endGrantBinding(context) -> void
authenticateBearer({ token, audience }) -> existing branded ServiceActor
ownerList(actor, { limit, cursor }) / ownerRevoke(actor, { connectionId })
artifactStore: synchronous checked upsert/find/consume/destroy/revokeByGrantId
cleanup({ limit <= 64 }) -> bounded counts, no secret IDs
```

`artifactStore` не экспортируется как внешний RPC. Adapter wrapper превращает sync results в требуемые AS promises и стандартные `errors.InvalidGrant/InvalidTarget`; authority callbacks остаются строго synchronous в fence. ID/account/client/grant не берутся из непроверенного payload AS: есть explicit bound connection и exact request context. `prepareInteraction/beginGrantBinding` — закрытые host ports, signed extension содержит только approve/deny/list/revoke. Детальные JS signatures/immutable DDL фиксируются в [storage contract](p4-oauth-storage-contract.md) на основе уже принятого actual provider ordering test; не вводить универсальное `executeAsAccount`.

| Автор | Exclusive implementation ownership после отдельного go |
|---|---|
| Domain | `modules/capabilities/server/oauth-*.mjs`, `schema-v3.mjs`, узкий `schema/index/access/native-notes` integration, новые module tests/fixtures. Native helper меняется только для exact Caps2/3 identity и OAuth checked-key scope, без изменения B2 receipts/effects. Никаких Notes/catalog@1 changes. |
| Root | `package.json`/lockfile, `server/capabilities-oauth*.js` (provider/adapter wrapper/ingress/discovery), HTTP composition; новый `src/world/oauth-consent.ts` и его route/account/PWA integration. Root один владеет host async context и signed extension composition. |
| Reader автор, отдельный последовательный срез | Trusted deploy recognizer/guard/tests, exact Docker reader label, frozen historical v2 после domain DDL freeze. Никаких edits domain source. |
| Независимый critic | Отдельные acceptance files и review; actual AS/network/two-process races, consent account boundaries; не переписывает author tests ради PASS. |

Новые AS ingress bounds: URL ≤8 KiB, token/revoke form ≤16 KiB UTF-8, один bounded body buffer, no compression, strict methods/duplicate fields, фиксированный allowed Host/origin. Код не хранит массив тысяч tiny chunks и не выполняет fetch на присланный URL. Discovery public; interaction/token/revoke private `no-store`, raw provider errors/authorization/codes/RT/AT/PKCE verifier не логируются. Безопасный HTTP error mapping: standard invalid_request/client/grant/scope/target, access_denied; temporary store/host failure — sanitized unavailable, не восстановление authority по умолчанию.

## 9. Последовательность C1 и достаточная приёмка

**C1a — exact AS/storage seam.** После разрешения установить exact package: настоящий Provider с двумя static profiles в изолированном fixture, проверить callbacks/payload/consume order и отсутствие неучтённых models. Зафиксировать adapter/domain API + additive DDL3, retention и strict reader behavior. Первый тест — concurrent refresh + wrong-resource-before-consume. Если public hook не позволяет безопасную проверку, остановить выбор candidate и согласовать решение; не копировать OAuth grant implementation.

**C1b — reader-before-writer.** Historical2, default-off read1/2/3, real migration/reopen/corruption/unknown, known indexes/constraints; coordinated image/guard/backup этапы отдельно. OAuth issuance пока выключена. Это не повтор уже принятого native v2 checkpoint под другим названием.

**C1c — consent и fixed connection.** Подключить real signed Connect UI, provider endpoints, current bearer → существующий native API, owner revoke, bounded cleanup. Freeze исходников до независимых network/CLI проверок. Нельзя приравнять OAuth token success к Notes effect или к способности LLM выбрать tool.

| Проверяемая группа | Реальный сценарий/критерий |
|---|---|
| Protocol + clients | Raw HTTP against actual Provider: S256/issuer/client/redirect/resource. Затем выбранные CLI в изолированных homes: настроенный ID исключает DCR/CIMD, callback exact, token/refresh/revoke; отсутствие MCP implementation честно отделено от auth gate. Ни SDK surrogate, ни current docs не засчитываются вместо binary flow. |

| Resource + consume | Code/RT другого client/resource и повтор/массив resource. В частности wrong-resource refresh оставляет старый RT непотреблённым: последующий правильный запрос успешен. Plain/missing PKCE и issuer mix-up отказаны. Wrong resource token не проходит другой RS. |

Notes proof после COMMIT/revoke всё ещё settled internally, owner history сохранена. |

Другие account/profile/resource и legacy service-token scopes независимы. |
| Retention/format | >обычного суточного числа tokens, referenced terminal и uncertain credentials сохраняются; unreferenced expired очищаются порциями ≤64; EXPLAIN доказывает индекс вместо scan всех Invocation JSON. Full transient quota не блокирует revoke/cleanup, lifetime ledger cap не блокирует fresh token для read. В1/2 baseline не мигрирует сам. |
| Человек/PWA | 320×760 и 667×375, keyboard/focus, account/эффект/срок/лимит/отказ/отзыв понятны; offline approval не отправляется позднее автоматически, Notes draft не теряется. Создать через OAuth → открыть PWA → изменить/purge → старый receipt не раскрывает новый текст/существование. |

C2 потом добавляет реальные MCP profiles и headless child grant parity; D1 — 24 RU/EN задачи обеими моделями/клиентами; D2 — внешний HTTPS, backup/rollback/restore и выпуск. C1 не обещает авторегистрацию сторонних клиентов, появление в поиске всех ИИ, доступность модели или production-ready IdP.

## 10. Что в прежнем preflight больше нельзя читать как текущую реализацию

- Native Notes/Capabilities v2, host fence, public discovery и typed HTTP уже появились; старые строки §2/5 про их отсутствие исторические. C1 не повторяет их в новом ledger.
- Строковые `@1` UTF-16 правила, exact semantic digest и явный native Unicode admission сохраняются; OAuth не «исправляет» Notes schema и не normalizes body.
- Наличие Cap credential не решает OAuth consume/refresh-family race; AS library defaults не устанавливают domain budget/creator checks. Нужен описанный закрытый bridge.
- Поддержка pre-registration в официальном guide и исходниках — основание для теста, не доказательство совместимости обоих выбранных CLI. Фактические auth/model/protocol receipts ещё предстоят.

Root принял два решения §1, family-wide revoke, atomic stagedGrant binding и OAuth-only crossconnection conflict. Его actual AS ordering spike завершён; точные schema/API/retention — [storage contract](p4-oauth-storage-contract.md). Текущий результат — дизайн и историческая fixture, не domain implementation: отдельное разрешение на production source ещё необходимо.
