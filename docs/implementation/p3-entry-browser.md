# P3-B3 — фактический вход в браузере

Дата: 2026-09-30. Локальная проверка в Codex Chromium, отдельная от сетевой [независимой приёмки](p3-entry-independent.md). Публичный DNS/TLS этим не подтверждается.

## Среда и граница опыта

Полный настоящий dev server: shell `http://127.0.0.1:5420`, API/app gateway5421, новый каталог `var/p3-entry-browser/data`, отдельный исходный connector58350 с единственным разрешённым пустым QA workspace. Установленный коннектор и исходные пользовательские данные не использовались. Порт49550 оказался недоступен в Windows; процесс остановлен,58350 отдельно проверен до запуска.

Через настоящий UI подключено устройство и зарегистрирован пример «Покупки · проверка входа» на loopback56322. Пример использует реальный HTTP/WS runtime; добавленная строка списка появилась в UI. Его собственный светлый стиль не является частью оболочки Сот. Для query-проверки пример теперь обслуживает `/` с query, сохраняя полный request URL в своей трассе.

Именованный alias `entry-demo.named.localhost:5421` и две последовательные политики подготовлены **тестовым вызовом существующего сервиса** в той же новой QA базе. Это проверяет вход B3; создание/редактирование публикации через будущий C1 UI здесь не заявляется. Отдельный локальный `/entry-check` содержит обычную ссылку на boot без ticket — детерминированную ошибку входа для проверки iframe. Этот fixture находится только в `var/`, не в production.

## Проверенные цепочки

1. Карточка приложения → canonical iframe → новая cookie подтверждена nonce GET → настоящий список. Ввод и отправка новой строки работают, WS показывает «подключено».
2. «Открыть отдельно» → новая вкладка → свежий boot → тот же список. Одноразовая iframe-ссылка не копируется; успешный новый вход подтверждён реальным содержимым.
3. Верхняя приватная named-ссылка `/?tag=a%2Bb&tag=%23&empty=` → trusted `#launch/<app>/<domain>?path=...` → iframe с **тем же точным query** → список. До разрешения нет названия владельца/приложения из каталога. Прямой launch не зависит от `apps.list`.
4. Тот же named launch → отдельная вкладка → точный query сохранился.
5. После изменения epoch прежняя представленная cookie получает страницу восстановления. Нет автоматического guest-fallback. Явная кнопка «Продолжить без входа» очищает сессию и открывает активное публичное приложение с тем же query; WS подключён.
6. Встроенный `/entry-check` → boot без ticket → понятная ошибка внутри iframe, без открытия оболочки внутри него. Внешняя кнопка над приложением остаётся доступна и действительно открывает свежую рабочую вкладку. Sandbox не расширялся.
7. Остановка QA connector → обновление → «Устройство не в сети». Hash/target сохраняются. Возвращение connector → «Попробовать снова» → прежний `/entry-check`.
8. Клавиатурные Refresh/Retry переводят фокус на заголовок приложения при синхронном пересоздании экрана. После асинхронного ответа фокус остаётся там; новый ответ не забирает фокус у пользователя.
9. «Другой аккаунт» открывает штатное восстановление профиля; отмена сохраняет полный launch route. **Смена самой identity в браузере не выполнялась**; account/generation races проверены отдельными19 helper tests с настоящими deferred promises.

## Незакрытые внешние границы

-Настоящее запрещение cookie настройкой браузера, Safari/Firefox/физический телефон и screen reader здесь не проверены. Старый-cookie/new-cookie nonce mismatch проверен независимым HTTP suite, а не подменён успешным iframe.load.
-Сырой fragment исходной приватной runtime URL не приходит на HTTP сервер и не сохраняется через302 с собственным hash. Launch `path`, включая hash-SPA, сохраняется полностью; для передачи закрытой hash-SPA нужен trusted shell-link с закодированным полным path. C1 обязан использовать этот вариант.
-Публичные DNS/TLS, отдельный registrable domain, production proxy, Linux exact Apps3 reader/rollback и восстановление зашифрованной копии остаются release gates.
