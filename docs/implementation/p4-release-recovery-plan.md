# P4-D2 — первый переход и проверяемое восстановление

Дата: 01.10.2026. Статус: **source-only план для review; не выполненный backup, restore, START или выпуск**. Прочитаны исходники и сохранённые receipts. Runtime, тесты, SSH/API, production hosts и CLI не запускались; значения env, конфигурационных секретов и ключевых хранилищ не читались. Единственное изменение этого среза — данный файл. Corporate mode не активирован.

План сохраняет зависимости [master P4](../plans/soty-human-agent-platform-20260930.md#p4-первый-полный-сценарий-для-внешнего-агента) и [P4 preflight §7–9](p4-external-agent-preflight.md). Принятый локальный [C2c](p4-cli-client-result.md) не заменяет D1 с настоящими моделями или D2 на внешнем HTTPS origin. Человеческое разрешение на согласованный read-only preflight, реализацию и выпуск уже есть; checkpoints root ниже — конкретные инженерные условия выполнения, не новая blanket permission на эти работы. Новые расходы, разрушительный data restore или дополнительная область требуют отдельного решения. Этот срез остаётся только документом.

## 1. Решение и исходные ограничения

Использовать **существующий HostController, его locks, transaction journal и reconciliation**. Добавить узкий первый переход, при котором точный исходящий container разрешено только остановить. Все START нового/восстановительного приложения по-прежнему требуют обычный strict storage guard. Не добавлять второй deploy orchestrator, job ledger, общий `skipGuard` или фиктивный reader label.

Обозначения:

| Объект | Обязательное доказательство |
| --- | --- |
| **O** — исторический outgoing image/container | Точные live ID/image/config/mount/StartedAt перед действием. Его unlabelled/старый manifest не становится reader3 от выключенного endpoint, нового container label или наличия другого image |
| **C** — новый полный application baseline | Честный image reader manifest, полный startup/reopen на поддерживаемых старых, новых и смешанных данных, P4 admissions и явные миграции выключены |
| **R** — совместимый code fallback | Полный image/config, реально проверенный на **последних** форматах и authority rows, которые допускает C; та же свежая data generation при возврате кода |
| **B** — холодная зашифрованная data generation | Все связанные stores и необходимые внешние authority/config зависимости; аутентифицированный архив и настоящий isolated restore именно B |

R не подменяет автоматически O: текущие rollout/controller восстанавливают **SAME old container/image**. Если C и R совпадают байтами, это честно лишь restart/config recovery; защиты от общего дефекта кода нет. Для заявления о code fallback нужен отдельно проверенный R. Старая принятая schema3 DDL сама по себе не доказывает, что прежние row validators принимают все нынешние допустимые OAuth rows: например, проверка секундного Grant expiry позднее уточнялась без смены DDL. Если совместимого R нет, разрешённый исход после STOP — maintenance/fail-stop, не скрытый START O.

Root предложил рассмотреть source `2103d755c081f03cdad98959fe593c6151ea2eec` как R: последующий product diff C2c исправляет MCP negotiation, Connect tree тот же. Это кандидат для review/build, **не принятый runtime fallback**. Exact C/R image digests/config pins ещё должны быть получены и пройти gate; source SHA не заменяет image proof.

Последовательность: **fresh безопасный inspection → реальные C/R на изолированных данных → durable first-transition mode и точный outgoing stop-only permit → quiescent B → isolated restore B → C на исходном томе → typed handoff в новую host generation → принятый serving reader baseline → отдельные migrations → отдельное внешнее включение**. Изолированный application START и serving baseline на исходном томе — разные доказательства. Последний нельзя объявить до cold backup/restore, действительного START C и подтверждённого handoff.

## 3. Fresh inputs для инженерных gates

Root сначала выполняет read-only preflight в уже согласованной области; этот документ его не выполняет. Вывод — только выбранные безопасные поля, hashes/counts и boolean, без bodies, tokens, env dump, key PEM или полных inspect/config объектов.

2. Топология `/data` и всех остальных persistent mounts, local volume driver/options, реальные writer identities, host services/cron/backup/sync/sidecar writers. Docker overlap check ограничен наблюдаемыми containers и путями: symlink/bind aliases, host processes и удалённый storage требуют отдельного bounded inventory. Неизвестный writer запрещает cold-generation claim.

Не превращать файл в `{}`/не удалять ради PASS; fresh inventory и full-image proof отдельно устанавливают фактический исход.

Конкретный пригодный edge control этим source review ещё не подтверждён: root выбирает и фиксирует механизм текущего deployment, удерживающий HTTP/WS закрытыми во время START C; до его проверки план не исполняется. Это deployment config, не новая product maintenance система. Для открытия P4 отдельно нужны approved HTTPS origin/TLS/DNS/resource/issuer/callbacks и D1 result; не менять их при аварийном восстановлении на случайный localhost.

Есть два code/config стыка до implementation freeze. `HostController.images` привязан к Connect module tree; существующий tree повторно использует уже зарегистрированный image. Поэтому first transition берёт C/R **из explicit immutable image/config pins своей transaction**, минуя normal `applyRelease`/`validate` и lookup/reuse `images[ConnectTree]`. Старый mapping не перезаписывается, Connect module version/sequence не повышаются ради whole-app обновления. После serving C выполняется typed handoff §4, который один раз создаёт initial mapping `tree → C` в новой host generation. Нынешний `rebaseHost` такого handoff не делает. Второй стык: `candidateConfig()` сохраняет прежний env/mounts и добавляет конкретные release/origin поля; он сам не вводит P4 flags или OAuth key mount. Root заранее фиксирует точный candidate config diff/hash, не подразумевает автоматическое применение новых настроек.

## 4. Узкий first-transition adapter в существующем journal

Предлагаемый новый модуль `deploy/connect/first-transition.mjs` — policy/phase adapter вызываемый **тем же HostController**, а не CLI с собственной mutation loop или отдельным journal. До первой mutation durable transaction получает обязательный discriminator `mode:'first_transition'`, exact O/C/R/config pins, фазу и predecessor/target generation identities. Normal rollout path остаётся strict и продолжает отказывать O. `rebaseHost` может подготовить source/config generation, но не выполняет новый recovery dispatch или serving handoff.

Обязателен **ранний recovery dispatch**: после существующих locks, source pin check и минимального строгого чтения host state, но **до module recovery в `run()`, normal `settle()` и любого обычного `activate()` pending path**, контроллер проверяет transaction mode. `first_transition` направляется только в свой finite recovery; unknown mode — fail-closed. Normal module rollback/`activate(oldTree)` не должен получить этот pending transaction и вызвать `restore()` O. До handoff mode сохраняется; crash не переводит его в normal по отсутствующему промежуточному receipt. Все entrypoints, оставленные для автоматического resume, должны применять этот dispatch; неизменённый исторический controller не объявляется mode-aware по факту нового поля.

Переиспользование `action()`/`reconcileOperation()` ограничено известными Docker operations: STOP/START/rename/restart-policy с прежними exact predicates и START guards. Backup publication, isolated restore, ingress closure/release и generation handoff — **новые typed stages со своим exact evidence**, не фиктивные Docker operations и не успех по одному stdout/timeout. Для каждого заранее записывается intent; completion связывает соответствующие archive/target/config/generation hashes и проверяемое постусловие. При lost response сначала reconcile именно этой стадии. До её доказанного завершения следующий writer/admission не разрешён.

Stop-only permit — отдельный внутренний тип, **не** storage-start receipt: exact O container/image/StartedAt/config+mount hashes, transaction ID, hashes approved C/R/probe/config и выбранного backup/restore profile. Он допускает только отключение automatic restart O, один STOP и exact readback. Он не разрешает START O, включение его restart policy, старый RW rollback helper, relabel/`docker commit`, data downgrade или перепривязку root grant. Отдельный trusted image может исполнять pinned host RO probe: это не аттестация application O.

| Фаза той же transaction | Условие перехода / сохранённое доказательство |
| --- | --- |
| `prepared` | Durable `mode:first_transition` и explicit C/R pins записаны, early recovery dispatch действует; fresh config/topology совпали. C/R startup/migration/fallback rehearsed на изолированных fixtures или ранее разрешённой копии; backup decrypt/restore tooling уже работоспособно. Записаны owned helper/volume names и конечные limits. Это ещё не fresh backup реальных данных |
| `admission_closed` | Updater не конкурирует, внешние HTTP/WS admissions закрыты подтверждённым существующим ingress control; Connector jobs drained/reconciled. Не объявлять неизвестные эффекты `none` ради продолжения. Не превращать gate в новую app/job систему |
| `outgoing_stopped` | Permit повторно сверён; durable intent → restart policy `no` → exact readback → STOP → подтверждённый stopped O; проверены остальные writers. Отключение restart происходит **до STOP**, а не после backup, как в нынешнем normal forward path |
| `backed_up` | Полная согласованная generation B, все ciphertext outputs завершены fsync/rename, manifest/hash связывает external inventory и pre-backup controller checkpoint. O всё ещё stopped/no-restart; writer set не изменился |
| `restore_verified` | Именно B authenticated и реально восстановлен на fresh owned volume, полный C/R проверены там без egress/новых внешних эффектов; pinned safe receipt привязан к B/C/R/config/formats. Архивная проверка без application restore сюда не переводит |
| `candidate_started` | Original data всё ещё тот же cold snapshot; вносится только owned maintenance marker, если требуется. Fresh strict `guardStorageStart(C)` → один START C → exact readback/health/all-store admission; O остаётся stopped. Startup C уже может писать, поэтому все предыдущие gates обязательны |
| `serving_verified` | Default-off C фактически serving и принят, актуальные data/authority не потеряны. Handoff intent содержит exact running C/config, прежние tree/module sequence/releaseHash, old/target generation paths и hashes. Новый normal updater ещё не допускается |
| `generation_handed_off` | Под общим lock domain один раз опубликованы new host generation/config/initial mapping `tree → C` и matching predecessor/successor evidence; выбранный updater указывает на new generation, старая generation fenced. Exact readback подтверждает обе стороны и timer/config selection; receipt lost response не вызывает повторного mapping или START |
| `baseline_serving` | Handoff подтверждён; owner routes доступны после явного открытия нужного ingress, maintenance снят только владельцем transaction. Новая generation содержит active C и сохранённую module sequence. Теперь C — **SAME old compatible reader** следующего обычного обновления |

Для известных CREATE/STOP/START/update/rename сохраняются прежние exact identity/reconciliation правила. Новый backup/restore/ingress/handoff не наследует готовый reconciler от совпадения слова «phase»: его собственные evidence и readback обязательны. Пока исход неизвестен, journal остаётся pending/recovery-required и никакой второй writer не стартует. После отключения restart policy даже failed STOP не означает «система не менялась»: если O ещё жив, policy остаётся `no`, admission закрыт, действие требует восстановления по recorded state. Нельзя автоматически вернуть ему restart policy через stop-only permit.

**Generation handoff:** старый `images[tree] → O` остаётся неизменным; старый journal сохраняется вместе с terminal first-transition/handoff evidence, а не переписывается как будто всегда обслуживал C. Connect module tree/sequence/releaseHash сохраняются. Новый journal получает `images[tree] → C` **только при initial create**; при resume существующее точное совпадение подтверждает тот же handoff, любое отличие запрещает overwrite. Запись intent, публикация target generation, переключение выбранного updater и final confirmation имеют отдельные postconditions в той же transaction. Новая generation не начинает normal work до подтверждённого ownership handoff; retired generation entrypoint обязан отказать до Docker mutation, включая случай запуска прежнего timer/config. Нужны actual crash/idempotency/old-generation-refusal tests: нынешняя реализация `rebaseHost` этих гарантий не предоставляет. При незавершённом handoff обслуживающий C не перезапускается ради «повторения релиза»; восстанавливается только control-plane ownership по exact readback.

Если backup/restore не прошёл после STOP, остаётся maintenance/fail-stop до устранения причины; один успешный storage guard не отменяет обязательный restore gate перед первым START C/R на исходных данных. O не стартует. Если C уже законно запущен после всех gates и успел записать данные, R получает **эти последние файлы** после остановки C и fresh guard. Существующий `restore()` на O нельзя вызывать как recovery этого режима: adapter обязан выбрать записанный совместимый R или fail-stop. Неизвестный outcome открытия ingress/leave может означать новые записи; он никогда не разрешает автоматическое восстановление B поверх них.

## 5. Что входит в одну cold generation и настоящий restore

**Quiescence — остановка всех writers связанных stores**, а не только `maintenance=true` или zero Connector jobs. Notes/Capabilities/OAuth доступны другим routes; даже AS-off startup запускает native proof reconciliation при Notes2/Caps2/3 и может запускать OAuth cleanup. Поэтому «feature off» не равно read-only. После graceful drain остановка всех relevant processes и подтверждённое отсутствие внешних writers создают согласованную точку. Pending native effects сохраняются для proof-first reconciliation после восстановления; ожидание нулевого количества всех исторических uncertain records не требуется и не разрешает их стирать.

B включает весь `/data`: Connect accounts/authority, World, Notes, Capabilities вместе с OAuth, Apps, Rooms SQLite **и legacy files**, connector ledger/requests/events/maintenance, identity/account-transfer/прочие фактически существующие durable данные. Сохраняются main+WAL и необходимые sidecars; нельзя копировать только main, вручную удалять WAL или выдавать live последовательные копии разных DB за одну transaction. SQLite Online Backup делает согласованный snapshot отдельной БД; он не создаёт общую commit boundary Notes↔Capabilities↔Connect. [SQLite backup](https://www.sqlite.org/backup.html), [WAL lifecycle](https://www.sqlite.org/wal.html).

Дополнительно нужны все external durable dependencies из fresh inventory: RO application-token bind; реальный `SOTY_OAUTH_KEYS_FILE` (JWKS/cookie/artifact keys и artifactKeyId); approved config/env provenance, issuer/audience/static profiles; release/trust/source/image pins, host/module journals и выбранный timer/controller config. Содержимое секретов — только внутри authenticated encryption. Неизвестный extra RW mount или отсутствующий обязательный key/config файл — отказ полноты. Не добавлять в серверный backup личные operator/device signing keys только потому, что они существуют на другом устройстве.

Минимальная доработка существующего SOTYBAK1: bounded allowlisted external-file inventory в encrypted metadata либо связанный authenticated companion archive; сохранить действующий crypto format, если его достаточно. Manifest перечисляет exact logical files/modes/sizes/digests и связывает один generation ID с data archive и pinned controller checkpoint. Journal контроллера продолжает писать свои фазы: в B находится согласованный checkpoint **до backup**, затем рабочий journal отдельно фиксирует hash B и результат restore. Не обещать самоссылочный архив, содержащий собственный финальный hash. Архивные host journals не исполняются автоматически в isolated restore или поверх текущего controller state.

Нужен **один новый restore helper** `deploy/connect/restore-backup.mjs`; он не управляет выпуском. Он использует проверку SOTYBAK1 и защищённый поток в fresh owned target. GCM должен быть полностью authenticated **до доверия plaintext для извлечения**: допустим двухпроходный путь по одному неизменяемому/pinned archive — verify, затем decrypt/extract с повторной аутентификацией и quarantine до успеха. DPAPI private key остаётся на операторской стороне; plaintext не сохраняется общим tar или в логах, protected pipe/transport и конечный объём согласуются заранее. Расшифрованная SQLite на isolated volume неизбежна; её ownership/modes/storage access и lifecycle явно ограничены.

Текущий tar verifier принимает некоторые link types и не является безопасным extractor. Новый helper обязан ограничить суммарные bytes/entries/path lengths, отвергать duplicate/absolute/traversal paths, devices и неожиданные symlink/hardlink entries; не следовать ссылкам из target. Если inventory требует legit links, это отдельный reviewed формат, а не автоматическое снятие запрета. Существующие metadata4MiB/header16KiB/stream64KiB ограничения не превращаются в unlimited archive. Unknown fields/paths и недостаток места отказывают до publication target. Verify CLI сегодня имеет top-level stdin execution: для reuse требуется узко выделить library API и CLI guard, не импортировать его с побочными действиями.

Restore proof выполняется на network-none, непубликуемом, exact owned volume/container, без serving mounts, Docker socket и device/executor подключения. До application START проверить извлечённые files/main/WAL hashes, store identities, SQL/FTS/FK/row invariants соответствующими readers. Затем C открывает копию штатно, с выключенными новыми admissions; допустимые startup migrations/reconciliation на **копии** фиксируются отдельно. R должен открыть результат C, включая final supported formats, сохранить proofs/receipts/budgets/revocations/used-key namespace и пережить cold restart. Никаких реальных token grants, повторного dispatch/Note create, внешних API/model расходов. Для read-only recovery keyless профиль допустим; если нужен восстановленный AS, наличие правильных encryption keys доказывается отдельно без внешней выдачи tokens.

Каждый helper/volume принадлежит transaction до CREATE/START, имеет CPU/RAM/PID/байтовые/deadline bounds и exact cleanup reconciliation, как существующий storage probe. Timeout не объявляет helper stopped/removed по одному сигналу или закрытию stdout. После ошибки сохраняются safe ID/outcome и pending cleanup, чужие ресурсы не удаляются. Исторический backup test с foreign UID проверяет RO archive, но не заменяет этот restore lifecycle.

## 6. Readers before writers и отдельное восстановление данных

Для первого C baseline: `SOTY_NATIVE_NOTES_ENABLED` и `SOTY_OAUTH_ENABLED` выключены; `allowNativeMigration=false`, `allowOAuthMigration=false`. Ordinary host сейчас не передаёт migration flags. Непустой `SOTY_CAPABILITY_AUDIENCE` отдельно включает HTTP/MCP surface, поэтому не считать все внешние endpoints выключенными только по native flag; первый baseline держит их закрытыми явным approved config/ingress. Если исторический OAuth уже существует, issuer/resource/key provenance сохраняется; keyless AS-off owner/history/proof recovery не требует выпуска новых credentials.

После настоящего serving reader3 baseline, handoff и соответствующего root gate: остановить writers, получить новую B при изменившихся данных, проверить её restore; затем explicit Notes1→2 и Caps1→2, отдельным шагом Caps2→3. Миграции per-store atomic, общей 2DB transaction нет; crash между шагами оставляет допустимые mixed states, которые C/R обязаны читать. `allowOAuthMigration=true` требует уже Caps2/3 и не является командой автоматического fresh1→3. Каждый шаг проверяет stable store/registry/project IDs, original credential/receipt/proof linkage и формат; новые API admissions остаются выключены до общей приёмки. Не нужно добавлять миграционную env-переменную в обычный startup ради этого пути.

**Операционный rollback:** закрыть конкретную capability/внешний admission, остановить candidate, guarded START R на последних файлах, сохранить владельцу данные/историю и proof-first reconciliation. Endpoint-off не отменяет состоявшиеся эффекты и не меняет original credential expiry; retained unknown не становится `none`.

**Data restore:** отдельное разрешённое disaster-recovery действие, новая volume generation, сохранённый исходный том, явные RPO/RTO и оценка потерянных writes. Нельзя восстановить только Notes либо только Caps, откатить receipts/consumed refresh tokens/revocations/occupied request keys незаметно или вернуть старые grants к жизни. Совпадающие store IDs у двух возрастов одной базы не доказывают их синхронность. При потерянном response на внешнее действие состояние внешнего мира тоже не откатывается архивом. По умолчанию после data restore admissions закрыты, authority/эффекты reconciled, затем отдельное решение об открытии. Это не ветка обычного `HostController.restore()`.

## 7. Минимальное владение и конечная приёмка

| Срез | Необходимые файлы/граница |
| --- | --- |
| Root image/config gate | Proposed honest reader3 manifest уже в candidate build; gate именно этого digest и дальнейшие admission/publication без rebuild. Explicit C/R pins/config diff вне normal Connect-tree reuse. Ни одного label изменения O |
| Один first-transition mode | NEW `deploy/connect/first-transition.mjs` + focused test; узкая композиция `host-controller.mjs`/config и typed generation handoff рядом с `rebase-host.mjs`. Durable mode/early dispatch до module recovery/normal settle, прежние locks/journal, известные Docker action/reconcile; новые stages имеют собственные evidence. Normal rollout остаётся прежним |
| Backup/restore completeness | Narrow `backup.mjs` external inventory/helper ownership, reusable bounded verifier; NEW `restore-backup.mjs` + focused test. `operator-keys.ps1` получает только необходимый protected restore invocation, без plaintext key export/нового key store |
| Independent review | Отдельные causal negatives и один exact-image Linux restore/recovery rehearsal. Existing synthetic reader3 receipt не повторять ради количества и не выдавать за это доказательство |
| Actual release | Root в уже разрешённой области последовательно закрывает read-only preflight и конкретные gates конечного transaction/внешних D2 client/PWA scenarios; safe receipt и exact source/image/archive pins. Новые расходы/разрушительный restore/дополнительная область решаются отдельно |

Конечный обязательный набор, с первым RED и исправлением отдельно:

1. **Old guard boundary.** Unlabelled/старый envelope O в normal rollout отказывает до STOP. Durable mode при restart dispatches first-transition recovery **раньше** module recovery/normal settle; pending activation не вызывает O restore. Stop-only permit может отключить restart/остановить только bound O; START/enable-restart/старый RW helper им запрещены. Подмена container label ничего не разрешает.
2. **Real image + data gate.** Полные C/R, не только Node helper, читают старые/current/mixed data и реальные legacy shapes; unknown future/повреждённые обязательные rows отказывают без «ремонта ради PASS». Malformed legacy room даёт точный on-demand отказ с сохранением source, не необоснованное обещание падения всего startup. Proposed manifest уже входит в exact tested digest; rebuild после gate не наследует acceptance.
3. **Cold completeness.** Host/sidecar writer, изменившийся mount, missing external OAuth key/config, active Connector job или недостаток space ломают gate. Pending native unknown сохраняется. Fresh B соответствует всем stores одной остановленной generation.
4. **Archive/extractor.** Bad tag/truncation/missing store/WAL, duplicate/path traversal/link/oversized metadata/aggregate overflow не публикуют restore target. Foreign UID/modes и actual data hashes сохраняются; raw secrets в stdout/stderr/receipt отсутствуют.
5. **Actual isolated restore.** Именно свежая B → owned volume → domain integrity → C startup → R startup на результате C → cold restart, с network-none, 0 внешних effects/admissions и сохранёнными identity/proof/receipt/budget/authority. Проверка старого архивного header не считается PASS.
6. **Crash/lost response + handoff.** Отдельные seams restart-disable, STOP, backup publication, restore extraction, C START, ingress release и каждой publication/selection/confirmation стадии handoff. Новые стадии требуют собственных evidence; exact reconciliation не создаёт второй helper/writer и не заявляет exit по сигналу. Same Connect tree не возвращает O через normal `validate` reuse; initial new mapping `tree → C` создаётся один раз, old mapping/journal и module sequence сохранены. Повтор exact handoff идемпотентен, mismatch/запуск retired generation отказывает до mutation, новый controller не начинает работу раньше ownership confirmation. После возможного admission никогда автоматически не восстанавливается B.
7. **Migration/fallback.** Явные Notes2/Caps2/3 COMMIT boundaries, допустимый mixed reopen, R на последних3 AS-off, proof-positive после revoke/purge и retained original authority. O никогда не получает новые файлы для RW startup.
8. **Recovery distinction.** Code fallback сохраняет latest volume. Попытка обычным rollback восстановить прежний B после новых writes отказывает; explicit data restore требует отдельного решения и нового target, исходные данные остаются доступными для расследования.
9. **External D2.** Только после preceding gates и неизменённых зависимостей master: actual HTTPS discovery/consent/HTTP/MCP, те же два pinned CLI и owner PWA/revoke, defaults-off → явное включение → bounded отказ/recovery. Этот пункт не закрывается локальным restore или deterministic C2c transport.

Не назначать сейчас числа archive/RTO из исторического размера: они являются обязательными входами fresh preflight и замораживаются до прогона. Результат каждого среза — конкретный исход/hash/предел, а не «backup verified значит можно deploy». Сейчас все новые adapter/extractor/image/restore/release gates остаются **не выполнены**.
