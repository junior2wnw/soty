Нынешний verify branch читает keystore без byte cap и передаёт JSON через текстовый PowerShell pipeline: этот путь **не** является готовым key/binary handoff.

R1b `/archive` PUT переносит только reviewed code и также не является data channel.
4. Будущая узкая область: необходимая restore-ветка `operator-keys.ps1`, один локальный bootstrap `deploy/connect/restore-operator.mjs` над private sender API и один согласованный framed Docker-stream primitive. ## Ciphertext copy и локальный ключ

5. До расшифрования создать новую transaction-owned ciphertext copy в новом private namespace на известном локальном Windows filesystem. Bounded absolute paths; отвергать UNC/device/ADS, reparse в проверяемой цепочке и final target. Original/download не менять и не читать двумя проходами inplace; plaintext archive/temp file не создавать.
6. Directory и file получают owner=current operator SID и protected DACL с единственным разрешённым SID, без broad/inherited ACE. Создание file — CreateNew с явным security descriptor; не сначала записать bytes и лишь потом закрыть ACL. Проверить фактические owner/access rules у directory и открытого file; `mode0600`, ReadOnly attribute и ACL одного родителя недостаточны. [.NET create-with-ACL](https://learn.microsoft.com/en-us/dotnet/api/system.io.filesystemaclextensions.create?view=net-9.0), [protected DACL](https://learn.microsoft.com/en-us/dotnet/api/system.security.accesscontrol.objectsecurity.setaccessruleprotection?view=net-9.0).
   `DirectoryInfo.Create(ACL)` ничего не делает при existing directory и не доказывает CreateNew/freshness. Для namespace выбрать `CreateDirectoryW` с explicit security descriptor под заранее проверенным trusted sole-writer parent; existing path, даже empty/правильного SID/DACL, означает отказ без delete-and-recreate. До payload проверить identity directory/file по открытым handles (volume serial + file index), отсутствие reparse, initial empty membership, затем ровно один ciphertext file; control evidence хранится снаружи. Повторно сверить identities и ACL под keeper; неподдержанные security/identity primitives — отказ, не fallback к одному имени/родительскому ACL. Это предпосылка доверенного parent, не защита от hostile того же SID. [Exclusive directory creation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createdirectoryw), [handle identity](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileinformationbyhandle).
7. Копировать bounded chunks≤64KiB, total≤approved archiveBytes, сверить trusted archive SHA, `Flush(true)` и фактически закрыть creation writer. Затем открыть keeper `FileStream(Open, Read, FileShare.Read)` и повторно проверить copy hash под ним до sender launch. Промежуток writer→keeper защищён fresh private sole-writer setup, а не атомарностью двух открытий. [Flush](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.flush?view=net-9.0).
8. Keeper не разрешает write/delete sharing; несовместимый уже открытый writer — отказ. Удерживать handle до фактического завершения local sender child, а не timeout/kill/receipt. При неподтверждённом завершении supervisor сохраняет guard/unknown status; не закрывает его в безусловном finally и не удаляет copy. После аварии самого supervisor OS освобождает handle: новый запуск обязан заново установить предпосылки, а не обещать прежний lock. [CreateFile sharing](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [FileShare.Read](https://learn.microsoft.com/en-us/dotnet/api/system.io.fileshare?view=net-9.0).
9. Keeper и Node read FD — разные handles. Pinned libuv по умолчанию разрешает Read/Write/Delete sharing, поэтому Node open/stat самостоятельно не доказывает неизменность; совместимость отдельного Read keeper и Node reader требуется проверить на actual Windows. DACL не защищает от hostile operator SID/administrator/kernel; strings/KeyObject не получают обещания secure erase. [Node24.21 libuv Windows open](https://raw.githubusercontent.com/nodejs/node/v24.21.0/deps/uv/src/win/fs.c).
10. DPAPI остаётся локальным CurrentUser с существующей entropy; proposed synthetic profile: bounded read encrypted blob≤64KiB до Unprotect, затем немедленный size check clear bytes≤64KiB до UTF-8/JSON parse. Выбрать только backup private PEM, а не пересылать весь keystore. Private control JSON вместе с path/pins/limits≤64KiB, PEM дополнительно≤64KiB; overflow — отказ, не расширение. Это будущие admission limits, не проверка размера настоящего keystore. [DPAPI Unprotect](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.protecteddata.unprotect?view=windowsdesktop-9.0).
11. PS запускает один local Node с UseShellExecute=false и RedirectStandardInput=true; control bytes пишет через `StandardInput.BaseStream`, без WriteLine/PowerShell text pipe. Clear PEM не попадает в argv/env/disk/stdout/remote; transient byte buffers стираются после потребления, память строк — без гарантии стирания. Наличие нужных .NET overloads/actual runtime — отдельный Windows gate, без fallback к слабой ACL. [Process stdin](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.standardinput?view=net-9.0), [BaseStream](https://learn.microsoft.com/en-us/dotnet/api/system.io.streamwriter.basestream?view=net-9.0).

## Каналы и что означает их завершение

12. Топология: **PS private control stdin → local Node sender; sender-owned Writable → отдельный SSH child stdin → remote owned controller → Docker attach stdin → receiver**. Payload — неизменённые binary framing bytes. Local Node stdout и SSH stdout — разные bounded control-receipt каналы; ключ/полный plaintext никогда не являются их диагностикой. Приёмник материализует только согласованные private data/config roots, не промежуточный plaintext tar.
13. SSH executable/host key/identity pin берутся из ранее принятого operator channel; no PTY/agent forwarding, strict host checking, один owned process на фазу. Local spawn shell=false недостаточен для обещания remote argv API: SSH exec передаёт command string. Data-сессия запускает exact trusted `.mjs` file из approved stage; command состоит из фиксированных literal prefix/suffix и validated transaction ID32lowerhex, без произвольных paths/quoting/bash -c/секретов. Новые subsystem/config/server framework не нужны. [RFC4254 §6.5](https://www.rfc-editor.org/rfc/rfc4254.html#section-6.5), [ssh exit status](https://man.openbsd.org/ssh.1).

   **Code stage заранее:** старый QA `p4-restore-sink-root-send5.mjs:31,54` запускает `node --input-type=module -` и отдаёт весь stdin коду; совместить его с plaintext stdin нельзя. Для первого handoff выбрать один private transaction-owned source stage вне live checkout/modules и serving mounts, готовый **до backup и первой payload write**. `update-engine.mjs:214–228` не запускать ради этого: его stage ведёт к rename live module/activation, а не изолированной подготовке restore tooling; no fake Connect version/tree bump.
   Доставка — отдельная предварительная **code-only** сессия по существующему pinned SSH send-once pattern: reviewed bounded bootstrap и exact captured closed source closure идут только её stdin. Source/base64 не размещаются в SSH/Docker Cmd; EOL/import/minify rewriting нет. До spawn в том же approved transaction journal записать stage intent/namespace/closure hashes/bytes; bootstrap делает exclusive private directory и regular files wx, fsync/actual close, затем full membership/size/hash/nofollow check против заранее reviewed pins, не против manifest, которому stage сам назначил доверие. Ни PEM, ни recovery plaintext в этой фазе нет.
   До `sourceReady` нужны exact stage receipt **и actual preparation SSH close0**; lost ACK — read-only reconciliation этого namespace, без повторной доставки/activation. Data entrypoint/receiver closure должны целиком существовать и быть проверены до payload; launch сверяет pinned private stage заново, а receiver code готов в owned RO stage до его START/attach. Только data-сессия использует stdin как binary. Это reuse source-capture/owned lifecycle pattern, не повтор старого QA bundle и не готовый transport proof; actual Windows→stage→file-entrypoint gate root ещё необходим.

14. Минимальный `ownedWritable` — свежая оболочка над исключительно своим SSH stdin: binary HWM1..65536, autoDestroy/emitClose=true, один pending write. `_write` callback означает фактическое потребление chunk нижним write callback и необходимый backpressure/drain на успешном пути, с наблюдением до write. На terminal failure drain может быть подавлен native destroy: больше не ждать drain, но дождаться supplied write callback и actual owned close. Native close может предшествовать удержанному callback; сам close не разрешает wipe/reuse. Не передавать sender обычный stdout или произвольный Duplex. [Node24.21 Writable](https://nodejs.org/download/release/v24.21.0/docs/api/stream.html#writablewritechunk-encoding-callback), [pinned implementation](https://raw.githubusercontent.com/nodejs/node/v24.21.0/lib/internal/streams/writable.js).
15. После проверенного второго прохода `_final` ровно один раз half-closes SSH stdin и ждёт writable completion. `_destroy` обязан дождаться фактического закрытия своего underlying input channel и завершения pending write callbacks; immediate destroy callback/manual close event запрещены. SSH stdout/stderr продолжают дренироваться. AutoDestroy Duplex не гарантирует этот порядок; если channel/callback не завершился, hard parent watchdog даёт unknown/cleanup_pending, а не фиктивный close.
16. Sender `finish+close` доказывает только контракт его owned output. SSH process `close` отдельно подтверждает завершение SSH и его stdio; `exit`, `error`, успешный kill или EOF этого не заменяют. Local Node не должен объявлять завершённую cleanup, пока его SSH child неизвестен; принудительное завершение Node не доказывает закрытие дочернего SSH. [Node24.21 child_process](https://nodejs.org/download/release/v24.21.0/docs/api/child_process.html#event-close).
17. На Linux journal перед CREATE хранит names/spec/intent, после exact inspect — owned container ID; затем attach `stream=1,logs=0,stdin=1,stdout=1,stderr=1` до единственного START. Receiver — main process, Tty=false/OpenStdin=true/StdinOnce=true, network-none, только owned mounts и LogConfig:none. Существующий parser используется один раз receiver; транспорт не добавляет decrypt/parser/ledger.
18. Для API1.45 принять предусмотренный handshake200/101 на том же запросе, обработать upgrade head, декодировать incremental bounded 8-byte stdout/stderr frames; вход stdin — raw bytes. Proposed control stdout≤64KiB, stderr≤16KiB, bounded headers+wire budget и deadlines фиксируются до implementation. Raw error/TAP/metadata не выводить; публично только fixed stage/status/counts. `/logs` fallback отсутствует. [Moby26 API1.45](https://raw.githubusercontent.com/moby/moby/v26.0.0/api/swagger.yaml), [attach handler](https://raw.githubusercontent.com/moby/moby/v26.0.0/api/server/router/container/container_routes.go).
19. Moby StdinOnce/non-TTY может ждать остановки container, но этот wait игнорирует его exit code. Handshake, EOF, закрытие attach или SSH exit0 не заменяют exact terminal inspect (Running=false, ExitCode=0, OOMKilled=false), полный receiver receipt и сохранённый target identity. Idle после первого payload byte не следует путать с временем первого локального auth pass; scheduling/deadlines требуется согласовать до START. [Moby26 daemon attach](https://raw.githubusercontent.com/moby/moby/v26.0.0/daemon/attach.go).
20. Итог принимается существующим journal только по **обоим** private receipts с одинаковыми plaintext/manifest hashes и byte count, trusted archive pin/sourceWitness/target, actual local Node/SSH close и actual receiver exit/receipt. Public projection не раскрывает plaintext/manifest/config/per-file hashes. Потеря ACK/receipt или разрыв — unresolved quarantine, no повтор CREATE/START/transfer в тот же target; read-only reconciliation/подтверждённая owned cleanup отдельно. EOF не означает authenticated/restored, приложение не START автоматически.

## Компактная будущая приёмка root

21. **Windows copy/ACL/share:** synthetic ciphertext + fresh private namespace с operator SID/DACL; actual Node read проходит под keeper, write/truncate/delete/rename и несовместимый прежний writer отказывают. Проверить actual descriptor/readback и guard lifetime при held child, затем контрольное освобождение после actual close; reparse/ADS/broad ACE/wrong owner отказывают до handoff.
22. **Private binary key boundary:** synthetic DPAPI blob/key и payload с non-ASCII path/all-byte values; точный binary read, caps+1/malformed/wrong key/pin дают fixed refusal и0 first-pass output/end. Canary values не появляются в argv/env/stdout/errors/artifacts; используются только synthetic secrets, настоящий keystore/B не открывается.
23. **Actual pipe lifecycle:** удержанный write callback после native close, false→drain, held final и late abort; один chunk не стирается до потребления. Normal half-close не теряет final bytes/control receipt, stdin completion не считается SSH completion. Timeout/failed kill/unknown close не дают PASS и не освобождают предпосылки как будто процесс завершился.
24. **Owned SSH→Docker:** отдельный synthetic root-run на точных Windows/Node/SSH/Engine versions, attach-before-START, nonempty upgrade head/tiny frames/backpressure, exact plaintext equality и receiver receipt. Ключ не отправляется remote; library и R1b proofs переиспользуются по pins, без повторения всей unrelated matrix. Это первый actual transport proof, не модель Linux из локального mock.
25. **Failure admission:** last-pass auth failure после уже переданных bytes, early EOF/truncated frame, lost ACK, receipt при живом/nonzero helper или отсутствующий SSH close сохраняют RED/unknown quarantine без retry. Проверить exact owned cleanup и внешний sentinel; отдельно доказать success conjunction. Настоящий B, cold completeness, full-image restart/rollback и first production transition остаются следующими gates root.

Граница источников: Microsoft Win32/.NET9 documentation и pinned Node24.21/Moby26/API1.45 объясняют выбранные primitives; они не подтверждают установленный Windows/.NET/SSH/Engine профиль, реальные DACL/share semantics, доступность DPAPI или completed channel. Никакие runtime/tests/SSH/keys/models в этом preflight не запускались и не читались.
