## Результат

Молчащее, но подключённое стороннее приложение продолжает работать. Отключённый браузер или зависший источник не занимают поток бесконечно. Проверка транспорта не продлевает срок прав и не повторяет действия пользователя. Исправление действует на платформу, а не только на пример.

## Неизменяемые границы

Сохраняются32 общих/24 public потока на коннектор,48KiB chunk/один ожидающий ACK,4MiB внешний buffer,1MiB message,30s head/ACK deadlines, точные origin/target/binding/epoch, абсолютный1h account-session и неподлежащее воскрешению public lease. Таймеры не обещают жёсткий wall-clock срок при заблокированном event loop.

Нет heartbeat бизнес-сообщений в iframe, внедрения credentials, отключения авторизации, бесконечного idle или автоматического повтора side effects. Полностью принятый валидный frame подтверждает транспортную активность его отправителя; исходящий трафик, внешний канал и ACK не подтверждают другого endpoint. Это не проверка здоровья бизнес-логики.

При streaming нельзя удерживать ACK текущего chunk до получения всего большого frame: следующий chunk может ждать именно этот ACK. Неполный frame и ожидающая безопасная запись heartbeat имеют собственные абсолютные сроки, которые поступление единичных байтов не продлевает.

## Первичные основания

[RFC6455 §5.4–5.5](https://www.rfc-editor.org/rfc/rfc6455.html#section-5.4) разрешает control frames между фрагментами сообщения и допускает ответ только на последний из нескольких Ping. Из этого следует необходимость учитывать границы frame и не требовать ответа на каждый собственный Ping при живом endpoint. [WHATWG WebSockets](https://websockets.spec.whatwg.org/#ping-and-pong-frames) не предоставляет JavaScript API для control ping/pong; платформа не может требовать такого метода от каждого мини-приложения.
