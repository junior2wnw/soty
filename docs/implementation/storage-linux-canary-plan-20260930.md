## Ограничения каждого контейнера

`Image` — точный существующий ID; `Entrypoint=['node']`, `WorkingDir='/'`, `User='0:0'`. Не копировать Config/Env/mounts serving container. Перед запуском проверить defaults выбранного image: отсутствие runtime hooks `NODE_OPTIONS`, `NODE_PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `ENV`, `BASH_ENV`; остальные default keys должны быть проверенным набором обычного Node image. Docker наследует эти defaults, поэтому пустой request Env не доказывает пустой effective Env.

## Deadline и неопределённые ответы

Не более одного запущенного canary process одновременно; максимум 8 контейнеров и один том за запуск. API output ≤64 KiB, probe JSON ≤4 KiB. Individual container deadline 20 s, весь сценарий ≤180 s; host polls возвращают управление с коротким интервалом. При deadline допустима остановка только уже идентифицированного running task container, затем подтверждённый cleanup.

CREATE/START/STOP/KILL отправляются один раз. Потерянный ответ сверяется по записанному exact name/ID и label, без повторного START/KILL или второго writer. Неопределённый KILL не вызывает ещё один STOP: если running сохраняется, resource остаётся для reconciliation. Неопределённый исход блокирует следующие фазы и удаление тома. Нельзя считать отсутствие HTTP-ответа отсутствием ресурса или автоматически удалять одноимённый чужой объект.

До cleanup неожиданно завершившегося synthetic helper stderr читается только с его exact ID, `tail=32`, Docker response cap64KiB и retained classifier cap16KiB. В receipt попадают только byte counts/hash, фиксированные error classes и OOM boolean. Raw stderr, пути, source/SQL/marker не сохраняются. Ошибка чтения диагностики фиксируется безопасным кодом и не отменяет cleanup.

Root сначала проверяет этот план и конкретный script. До его сообщения о принятии canary не запускается. Успешный canary дополнит Linux gate; fresh encrypted backup, реальный isolated restore и совместимый rollback остаются отдельными release gates.
