# Соты: общий план по текущему диалогу Codex

Этот документ сжимает все промты текущего диалога в один рабочий план.
Он нужен не как отчет, а как проверяемая инструкция для Codex, агента в Сотах
и будущих проходов по проекту.

Каждый пункт ниже должен проверяться одним из способов:

- доказательство в UI;
- доказательство рантайма агента;
- автотест или selftest;
- лог деплоя;
- явное подтверждение пользователя для опасных действий.

## Главная цель

Соты должны стать чатовым супер-аппом: человек открывает соту с другом,
устройством или собой, видит понятное поле сот, пишет сообщение, прикладывает
файлы, включает приватный режим агента кнопкой, запускает действие или мини-апп
и получает результат без засорения общего чата.

Клава, которая ставится на компьютер пользователя, должна быть универсальным
удаленным рантаймом: команды, файлы, браузер, экран, ввод, длительные задачи,
переустановка Windows, создание и деплой мини-апп, подключение к программам и
будущие сценарии вроде входа в сделки.

## Нельзя нарушать

- В поле сот при первом запуске видна только постоянная сота `Я`.
- Агент не является обязательной видимой сотой фронта; это отдельный runtime.
- Кнопки `Клава` в обычном UI быть не должно.
- Вызов Клавы в чатах не выполняется магическим словом. Только явный приватный
  режим агента или capability `agent.invoke`.
- Мини-аппы не закрываются крестиком, их можно только свернуть и развернуть.
- Правая панель `IDLE` не нужна, ее не возвращать.
- Файлы должны прикрепляться к сообщению, а не жить в отдельном поле `files`.
- Сервер должен оставаться в основном relay/control-слоем, а тяжелые файлы и
  работа должны по возможности идти через peer/device-маршруты.
- Нельзя чинить инсталлеры, скачивание, переустановку Windows и агента набором
  одноразовых костылей.
- Все опасные действия требуют явного подтверждения: стирание USB, перезагрузка
  под установку Windows, сделки, системные изменения, доступ к приватным данным.
- Секреты, токены, приватные логи и персональные данные нельзя класть в память,
  документы, финальные ответы и публичные артефакты.
- Все технологичное и универсальное должно постепенно уходить в ядро, а в Сотах
  оставаться продуктовая интеграция, UI и понятные адаптеры.
- UI Сот в будущем может отделиться в отдельный проект, поэтому текущий код
  должен оставаться модульным, читаемым и легко переносимым.

## UI и UX

### Поле сот

- Расположение сот было правильным, менять геометрию без причины нельзя.
- Нужно улучшать именно отображение: размер, плотность, контраст, качество
  граней, читаемость подписей, стабильность размеров.
- Пустое поле должно удобно панорамироваться.
- Если пользователь начинает тащить занятую соту, это должно работать как
  панорамирование поля, если жест похож на drag, а не на tap или long press.
- Long press по соте открывает меню действий.
- Действия, которые раньше были отдельными кнопками вокруг сот, должны жить в
  меню по удержанию.
- У соты агента нет действия удаления.
- Визуально поле должно оставаться ретро, но выглядеть качественно: меньше
  случайной грязи, стабильные размеры, нормальная читаемость.

### Выделение текста

- По всему приложению случайное выделение текста должно быть запрещено.
- Выделение разрешено только там, где это реально нужно:
  - в окне диалога и истории сообщений;
  - в поле ввода сообщения;
  - в выводе удаленной консоли;
  - в поле ввода удаленной консоли;
  - в обычных `input` и `textarea`.
- Кнопки, соты, меню, панели, заголовки, технический chrome и декоративные
  элементы не должны выделяться.

### Чат

- История сообщений не должна смешиваться между агентами, устройствами,
  аккаунтами и диалогами.
- Сообщения должны оставаться привязанными к конкретному диалогу и устройству.
- Файлы приклеиваются к сообщению одним баблом.
- Можно отправить сообщение только с файлами, без текста.
- Для агента за раз до 10 файлов.
- Для обычных чатов искусственного лимита на количество файлов быть не должно,
  если это не ограничение транспорта или безопасности.
- Клава должна видеть метаданные вложений и понимать, что файлы относятся к
  конкретному сообщению.
- Старое отдельное поле `files` удалено и не должно возвращаться как основной
  UX.

### Кнопки, панели и статусы

- Кнопка Download/Update показывается только когда она реально нужна.
- Если агент уже установлен, здоров и актуален, мертвая кнопка Download не
  должна висеть в UI.
- Если кнопка Download есть, она обязана скачивать, а не молча ничего не
  делать.
- После установки агента состояние UI должно обновляться автоматически, без
  обязательной ручной перезагрузки PWA.
- Компактный статус печати/работы остается в заголовке диалога.
- Правая панель `IDLE` удалена: она не несла понятной пользы и занимала место.

### Desktop PWA window chrome

- В установленной desktop PWA нужно использовать `window-controls-overlay`,
  чтобы убрать пустую стандартную titlebar-полосу и отдать верхнюю область
  интерфейсу Сот.
- Нативные системные кнопки ОС нельзя считать полностью заменяемыми HTML:
  браузер обязан оставить критичные window controls видимыми как overlay.
- Внутри доступной titlebar-area Соты рисуют собственный компактный верхний
  chrome и свой крестик закрытия окна.
- Верхняя область должна быть drag-region, а интерактивные кнопки - no-drag.
- В обычной вкладке браузера этот chrome не должен появляться.
- Если браузер/PWA не включает overlay фактически, это не чинится web-кодом.
  Тогда нужен локальный native window chrome helper через агента.
- На Windows helper должен работать точечно: искать только окно Сот, убирать
  `WS_CAPTION` у его HWND, возвращать proof `pid/hwnd/caption/frameless` и
  уметь ставить per-user watcher для следующих запусков.
- У Chrome `chrome_proxy`/старых ярлыков PWA верхняя полоса может быть
  нарисована самим Chrome внутри client area. В этом случае одного
  `WS_CAPTION` мало: helper должен дополнительно уметь прятать только
  matched Soty window выше рабочей области на высоту client titlebar и
  возвращать proof `clientTitlebar.hidden=true`.
- Persist route на Windows: сначала пробовать per-user Scheduled Task, а если
  текущий пользовательский контекст получает `Access denied`, сохранять watcher
  через `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`. Это локальная
  настройка конкретного пользователя и не требует SYSTEM/админа.
- Собственный topbar Сот в native-helper режиме включается локальной настройкой
  `native-window-chrome=1`, чтобы не показывать двойной верхний бар в обычной
  PWA, где системная полоска еще не снята.
- Helper нельзя запускать против всех окон браузера и нельзя считать SYSTEM
  сессией правильным местом для интерактивного window styling.
- На macOS правильный путь - отдельный native helper/wrapper с AppKit или
  проверенный accessibility/fullscreen route; это не должно быть web-костылем.

### Мини-аппы и удаленная консоль

- Мини-аппа открывается в нижней части диалога.
- Мини-аппа может запрашивать режим размера:
  - компактный;
  - половина диалога;
  - большая часть диалога;
  - полный экран;
  - плавающий размер.
- Управление размером должно быть безопасным контрактом, а не произвольной
  властью iframe над приложением.
- Крестик закрытия мини-аппы удален полностью.
- Единственная обязательная кнопка chrome мини-аппы: свернуть/развернуть.
- Кнопка `свернуть` должна находиться в углу заголовка окна.
- Если у мини-аппы много кнопок или текста, содержимое должно прокручиваться
  пальцем и мышью.
- Удаленная консоль агента является мини-аппой аккаунта `агент`.
- Глобальная установка пользовательских мини-апп пока выключена для всех.
- Для аккаунта `агент` включена мини-аппа удаленных команд.

## Клава и вызов в чате

### Вызов

- В любой выбранной соте Клава вызывается кнопкой приватного режима агента.
- Слова `Клава`, `Klava` и `агент` не запускают агента в обычных сообщениях.
- Мини-аппы вызывают агента через capability `agent.invoke`, тоже приватно.
- Нужно учитывать, что PWA часто свернута, а ввод через удаленное управление
  может быть медленным: длинные тексты лучше отправлять короткими командами или
  через более быстрый канал, если он доступен.

### Агент как runtime

- Клава - это отдельный runtime/connector, а не обязательная фронтовая сота.
- В приватном режиме агент видит текущую соту как контекст, но его сообщения не
  отправляются второй стороне.
- Мини-аппы и удаленные команды должны подключаться через capability-контракт,
  а не через отдельную видимую соту агента.

### Выбор устройства

- Перед действием по устройству нужно доказать, какое устройство выбрано.
- Нельзя угадывать скрытое или неактивное устройство.
- Если пользователь явно говорит `гого`, действие можно вести на `гого` только
  после проверки, что именно это устройство выбрано или однозначно найдено.
- Если цель неоднозначна, нужно задать один конкретный вопрос или остановиться.

## Инсталлер, Download/Update и автообновление

### Что должно работать

- Новое устройство открывает Соты, нажимает Download/Update и получает рабочий
  установщик.
- Установщик machine-scope должен запросить UAC.
- Инсталлер не должен падать из-за пустых аргументов `RelayId`, `Revision` или
  похожих параметров.
- Старые сломанные shims и испорченное Node-окружение должны чиститься.
- После установки агент должен стартовать, зарегистрироваться, стать видимым в
  UI и дать health proof.
- Автообновление должно работать без ручной пересылки старых cmd-файлов.

### Текущие ожидания рантайма

- Ожидаемая версия агента: `0.4.77`.
- Для managed machine-agent нормальное состояние:
  - `scope=Machine`;
  - `managed=true`;
  - `relay=true`;
  - `sourceWorker=true`;
  - `autoUpdate=true`, если режим поддержан;
  - `appka=true`, если включены возможности мини-апп.
- Если локальный Codex на пользовательской машине отключен в
  server-relay-only режиме, исполнитель команд все равно должен быть доступен
  через правильный bridge/runtime.

## Универсальный удаленный агент

Клава должна быть не набором отдельных скриптов, а capability-runtime.

Базовые capability:

- shell/script;
- длительные jobs;
- файлы и артефакты;
- браузер;
- экран, мышь, клавиатура;
- аудио;
- действия в приложениях и API;
- действия, связанные со сделками и критическими операциями;
- генерация и установка assets, включая wallpaper;
- переустановка Windows;
- создание, деплой и регистрация мини-апп;
- диагностика и самообновление.

Правила безопасности:

- Любое критическое действие требует подтверждения.
- Все команды идут к проверенному устройству.
- Результат действия должен иметь readback: статус, файл, лог, версию,
  health-ответ или скрин.
- Большие/долгие операции должны быть возобновляемыми и наблюдаемыми.
- Клава должна улучшать универсальный pipeline, когда находит новую развилку,
  а не только решать один конкретный ноутбук.

## Мини-аппы и `АППКА`

### Что такое мини-аппа

Мини-аппа - это фронтенд-поверхность, подключенная к аккаунту, диалогу или
устройству в Сотах.

Она может быть:

- same-origin внутри Сот;
- размещена на домене;
- размещена на другом сервере без домена;
- размещена на локальном/удаленном устройстве пользователя;
- подключена через kernel/device bridge.

Мини-аппа получает контекст через безопасный контракт Сот, а не сырые relay
секреты.

### Как пользователь должен создавать `АППКУ`

Пользователь может написать агенту:

`сделай для меня такую-то аппку`

Клава должна:

- понять, что речь именно о мини-аппе для нижней части диалога;
- уточнить цель только если без этого нельзя безопасно сделать результат;
- выбрать доверенное устройство/хост для сборки и размещения;
- создать frontend-проект или использовать готовый;
- развернуть его на выбранном устройстве, домене или сервере;
- зарегистрировать мини-аппу в текущем аккаунте/диалоге;
- показать ее в Сотах на другом устройстве пользователя;
- не включать глобальную публикацию для всех без явного разрешения.

### Телефон

- На телефоне создание мини-аппы нужно продумать, но пока выключить.
- Лучший базовый вариант: телефон формулирует задачу, а сборка и хостинг идут
  на доверенном компьютере пользователя или на указанном сервере.
- Это минимизирует нагрузку на сервер Сот и не превращает телефон в тяжелый
  build-runner.

## Действие "Переустановка Windows"

### Цель

Из Сот нужно выбрать ноутбук `гого`, штатно нажать действие
`Переустановка Windows`, сопровождать процесс и довести до финальной точки:
ноутбук готов к перезагрузке в установку Windows, а пользователь понимает, что
произойдет дальше.

### Универсальный pipeline

Перед работой:

- проверить выбранное устройство;
- проверить, что агент на нем здоров;
- проверить питание, сеть, свободное место, диск, прошивку, BitLocker и
  критичные риски;
- собрать модель, CPU, RAM, диск, поколение Windows и драйверные риски;
- спросить подтверждение на разрушительные шаги.

Выбор образа:

- Windows 11 Pro для более мощных машин, если пользователь не попросил иначе;
- Windows 11 IoT LTSC для слабых машин, если пользователь не попросил иначе;
- образ должен быть проверен SHA256;
- скачивание должно быть возобновляемым;
- ISO и scripts лучше кэшировать на сервере или доверенном хосте, но не делать
  сервер узким местом.

Подготовка:

- не запускать дублирующиеся prepare jobs;
- делать durable job с понятным статусом;
- готовить USB или локальный путь только после подтверждения;
- сохранять нужное состояние Сот, драйверы, Wi-Fi и пользовательские данные в
  согласованном объеме;
- возвращать понятный прогресс в чат/мини-аппу.

Улучшение:

- Каждая новая развилка должна улучшать общий скрипт или capability.
- Если агент упирается в модель устройства, диск, UEFI/Legacy, TPM, BitLocker,
  сеть, язык системы, права или UAC, это должно стать универсальным обработчиком
  или понятным шагом диагностики.
- Цель - чтобы следующий агент мог сделать то же самое быстрее и безопаснее.

## Память и обучение

- Память на сервере должна пополняться только безопасными, очищенными фактами.
- Повторяемые успешные маршруты должны становиться правилами/доками/skills.
- Одноразовые события остаются кандидатами и не должны автоматически становиться
  жесткими правилами.
- Клава использует память как подсказки, а не как приказ.
- После реального улучшения pipeline нужно обновлять документацию и тесты.

## Репозитории и ядро

- Универсальная технология соединения агента, device bridge, mini-app contract,
  capabilities, auth/trust и transport должны жить в ядре.
- Соты должны использовать эти контракты и не дублировать технологическую
  логику, если она уже вынесена в ядро.
- В репозитории Сот остаются:
  - UI;
  - продуктовые фичи;
  - адаптеры;
  - стили;
  - интеграция с сервером Сот;
  - документация, специфичная для продукта.
- Каждая значимая правка должна быть коммитом, пушем и деплоем на `dev`, если
  пользователь попросил залить.

## Текущий аудит

Сделано и должно сохраняться:

- агент отделен от основного полотна сот;
- при первом запуске фронт создает только соту `Я`;
- режим агента включается на выбранной соте приватно;
- кнопка `Клава` удалена из обычного chrome;
- действия сот перенесены в меню по удержанию;
- правая панель `IDLE` удалена;
- live/status перенесен в заголовок диалога;
- файлы прикрепляются к сообщению;
- для агента действует лимит 10 файлов за сообщение;
- старое отдельное поле `files` удалено;
- крестик мини-аппы удален;
- крестик удаленной консоли удален;
- у мини-аппы и консоли осталась обязательная кнопка свернуть/развернуть;
- сервис-воркер был поднят до актуальной версии, чтобы PWA обновлялась;
- вызов Клавы убран с магических слов и переведен на явный режим/capability;
- dev-деплой и health executor уже проверялись.

Сделано в текущем проходе:

- глобальное выделение текста отключено;
- выделение разрешено только в диалоге, composer, output/input консоли и
  стандартных текстовых полях;
- кнопка свернуть удаленной консоли закреплена в углу заголовка;
- кнопка свернуть мини-аппы закреплена в углу заголовка;
- selftest проверяет отсутствие `terminal-close`;
- selftest проверяет CSS-правила выделения и угловые collapse-кнопки;
- этот мастер-план добавлен как рабочий документ.

Требует отдельного real-world proof:

- полноценный live-proof в уже открытой старой PWA может быть заблокирован
  устаревшим состоянием Chrome/PWA, поэтому нужен свежий public proof после
  деплоя и, при необходимости, проверка live-окна пользователя;
- drag-to-pan от занятой соты нужен отдельный pointer regression test;
- переустановка Windows на `гого` требует отдельного подтвержденного запуска до
  финальной точки перезагрузки;
- создание `АППКИ` с телефона пока намеренно выключено;
- глобальная установка мини-апп для всех пользователей пока намеренно выключена;
- перенос технологического слоя в репозиторий ядра должен проверяться отдельно;
- отдельный визуальный pass по полю сот и движениям стоит делать после
  стабилизации функционала.

## Чеклист приемки

Перед тем как считать текущий срез готовым:

- `pnpm typecheck` проходит;
- `pnpm build` проходит;
- `pnpm agent:selftest` проходит;
- на свежей странице production/dev ровно один Agent record;
- на свежей странице production/dev ровно одна видимая сота агента;
- `.side-panel` отсутствует;
- `.terminal-close` отсутствует;
- `.terminal-collapse` является угловой кнопкой;
- `.mini-frame-collapse` является угловой кнопкой;
- `getComputedStyle(document.body).userSelect` не разрешает обычное выделение;
- текст сообщений в диалоге можно выделять;
- composer можно редактировать и выделять;
- executor на SSH dev здоров;
- публичный HTML указывает на новый bundle;
- `/sw.js` имеет актуальную версию cache;
- untracked/чужие файлы не тронуты.
