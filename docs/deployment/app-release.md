# Повторяемое размещение приложения в Сотах

Процесс подходит новому проекту и обновлению существующего. Обычное приложение
не требует повторного выпуска Сот или отдельного коннектора на каждый проект:
один принадлежащий тому же владельцу коннектор обслуживает несколько loopback
портов в одной проверенной границе доверия. Раздельные коннекторы нужны при другом
владельце, другом workspace/доступе или необходимости изоляции.

Для агента есть устанавливаемый [skill](../../skills/soty-app-deploy/SKILL.md).
Исходные рабочие папки с незавершёнными изменениями не заменять ради публикации.

## Короткий путь

1. Определить работающий Soty origin, действующую именную зону, владельца,
   app ID при обновлении, устройство, свободный loopback-порт и начальную страницу.
   Прочитать актуальные настройки и проектную инструкцию.
2. Собрать приложение из закреплённой revision, выполнить его проверки,
   запустить HTTP-сервис на устройстве с коннектором. Сохранить прежние тома и секреты.
3. Подготовить строгий манифест:

       node scripts/soty-app-release.mjs init --project /path/project --name Project --port 8111 --entry-path /

   Команда сохраняет .soty/app.json, повторяется для того же намерения и
   отказывается перезаписать другой манифест или выйти через symlink/junction.
4. Через интерфейс владельца подключить устройство, если ещё не подключено,
   добавить проект, закрепить имя и выбрать доступ. Не подключать чужой коннектор
   заново и не менять ownership в SQLite. Срок одноразового файла подключения —
   пять минут; origin должен точно совпадать с текущими Сотами. После привязки
   удалить обе временные копии. Действующее подключение переиспользовать.
5. Настройки приложения → Источник → «Размещение с агентом» →
   «Скачать данные размещения». Файл содержит только адреса, порт/путь,
   revision/digest источника и публикации. В нём нет токенов, ключей, grants и
   connector identity. Снимок не даёт разрешения на публикацию.
6. Подготовить план из свежего файла (не старше десяти минут):

       node scripts/soty-app-release.mjs plan --project /path/project --deployment /private/soty-deployment.json --output /private/run-unique

   При нескольких включённых адресах добавить --domain-id конкретного адреса.
   План фиксирует именной вход и путь. applied=false означает только подготовку.
7. Проверить реальный опубликованный адрес:

       node scripts/soty-app-release.mjs verify --plan /private/run-unique/release-plan.json --probes /private/probes.json --output /private/run-unique/http-check.json

   Дополнительные проверки — JSON-массив, например:

       [{"path":"/api/health?probe=release","status":200,"contains":"ready"},{"path":"/assets/app.css","status":200}]

   Не помещать секреты в query или файл checks. TLS проверяется штатно.
   Перенаправления не маскируются успешным ответом другого сервера.
8. В настоящем браузере открыть карточку в Сотах, пройти вход и чтение/запись
   проверочного объекта, перезагрузить; проверить ограничения доступа и
   сохранность старых данных. Проверить полный экран → возврат на том же iframe.
   HTTP-проверка отмечает httpOnly=true и не подтверждает весь выпуск.

Для ограниченной публикации CLI требует проверку авторизованным браузером.
Не публиковать приложение для всех ради обхода этого ограничения. Основная
страница, страница с query и boot ожидают 200. Приложение с другим контрактом
ответа требует отдельного браузерного сценария; дополнительные probes дополняют
основные проверки, а не отменяют их.

## Gateway и собственная авторизация

По умолчанию isolated использует Soty gateway. Его sandbox, CSP, фильтрация
credentials и отсутствие workers сохраняются. Он подходит обычным приложениям
и не переносит browser storage между origins.

Доверенное приложение со своей серверной авторизацией, защищёнными cookies,
OAuth или своим API может требовать native. Сначала проверить приложение и
модель доступа. Затем указать --mode native; дополнительные точные доверенные
оболочки добавить повторяемым --frame-origin https://... .
Генератор создаёт native-ingress.caddy с фиксированным loopback upstream и точным
digest текущего источника. Он не применяет Caddyfile и не меняет DNS.

Каждый запрос проходит /_soty/ingress-check. В конфигурации обязателен
uri /_soty/ingress-check? — query удаляется только из копии для проверки доступа,
параметры исходного приложения сохраняются. Cookie Сот удаляется перед передачей
приложению; cookies приложения сохраняются. Добавочная frame-ancestors policy
сохраняет собственный CSP приложения. Проверить также его X-Frame-Options/CSP,
Origin/CSRF и callback URL: прокси не исправляет несовместимую авторизацию сам.

При изменении источника прежний native pin закрывает маршрут. Перед переключением
подготовить новую привязку по свежему снимку и проверенную обратную конфигурацию.
При обновлении того же порта/пути digest источника обычно не меняется; он не
заменяет immutable revision/image приложения. App ID, domain ID и данные
сохраняются. Создание нового app ID не является обновлением существующего.

## Одна настройка зоны для многих проектов

Основная зона берётся из актуальных hosting-настроек. Для неё нужны wildcard
DNS и Caddy route:

    node scripts/soty-app-release.mjs zone --origin https://4-2.xn--p1ai --output /private/named-zone.caddy

Snippet требует существующего глобального on_demand_tls с
ask http://127.0.0.1:18182/api/apps/tls-allow. Для новой зоны проверить это
один раз, сохранив корень, id, www, старые зоны и точные native hosts.
Имена из реестра открываются через wildcard gateway; неизвестные и вложенные
имена отклоняются. DNS запись сама не регистрирует приложение.

On-demand TLS имеет реальные ограничения CA. Для большого потока выпуска
сертификатов рассмотреть wildcard-сертификат через DNS challenge и согласованное
хранилище; это отдельное изменение после проверки возможностей DNS-провайдера.

## Применение и откат

Сначала зашифровать исходную конфигурацию и проверить расшифрование/manifest.
Читать секреты только в памяти, выводить выбранные безопасные поля. Подготовить
кандидат, выполнить Caddy adapt/validate и локальные проверки queried entry,
assets, API и отказа при неверной source pin/сессии. Сравнить исходный SHA перед
атомарной записью; после reload сверить действующую и дисковую конфигурации.
Не заменять весь файл шаблоном и не перезагружать произвольный найденный процесс.

Для выпуска самих Сот использовать [guarded maintenance rollout](../../deploy/connector/README.md):
immutable image, storage readers, точные mounts/config fingerprint, один writer,
свежий drain и проверенный prepare receipt. Служебный receipt не заменяет
поручение пользователя; при наличии поручения лишнее подтверждение не нужно.
Не использовать recovery вместо обычного обновления.

Откат оставляет текущую базу и возвращает совместимый процесс/маршрут.
Миграция данных требует отдельной backup/restore проверки и плана совместимости.
Не удалять app/domain IDs ради повторного запуска.

Оставить: source revision + image digest, публичный URL и точную ссылку Сот,
hashes конфигурации, receipts данных/браузера/доступа и команду отката.
Отдельно назвать неподтверждённые сценарии.
