# Повторяемое размещение приложения в Сотах

Процесс подходит новому проекту и обновлению существующего. Обычное приложение
не требует повторного выпуска Сот или отдельного коннектора на каждый проект:
один принадлежащий тому же владельцу коннектор обслуживает несколько loopback
портов в одной проверенной границе доверия. Раздельные коннекторы нужны при другом
владельце, другом workspace/доступе или необходимости изоляции.

Для агента есть устанавливаемый [skill](../../skills/soty-app-deploy/SKILL.md).
Исходные рабочие папки с незавершёнными изменениями не заменять ради публикации.
Сначала выберите [существующий контракт входа](app-authentication.md): для
approved workspace2 и совместимого коннектора — поддерживаемый Source SDK;
собственный confidential BFF/RP выбирают отдельно. Native/standalone адрес сам
по себе не требует RP регистрации. Для пустого окна/WS/auth —
[диагностика](app-troubleshooting.md). Общая
[матрица готовности](app-release-readiness.md) различает проверку кода,
размещение конкретного приложения и готовность всей платформы.

## Короткий путь

Для любого обычного приложения цель — один maintained recipe:
**подготовить → проверить автоматически → применить разрешённое намерение →
подтвердить реальную работу**. Новый агент начинает с актуального managed skill,
его sourceRepository и текущих capabilities/tools/list; старый чат не обязателен.
Он переиспользует доступный init/plan/verify и receipt/readback, не придумывает
endpoint, новый протокол входа или сотни ручных согласований. Только реальное
недостающее owner consent/новое чувствительное действие требует участия человека;
уже разрешённые чтения и проверки выполняются самостоятельно. Изменение Root,
Caddy и DATA writer — отдельная платформенная ветка, не цена каждого нового app.
Окончательный app/operator plan до stage прогоняй локально его фактическим
schema/contract validator со всеми требуемыми ID/hash зависимых receipts.
Проверка шаблона или несвязанные pure tests не заменяют проверку финального DTO.

Если результат применения неизвестен, продолжение начинается с того же intent/
journal и readonly inspect; transaction и operation не подменяют друг друга.


1. Определить работающий Soty origin, действующую именную зону, владельца,
   app ID при обновлении, устройство, свободный loopback-порт и начальную страницу.
   Прочитать актуальные настройки и проектную инструкцию.
2. Собрать приложение из закреплённой revision, выполнить его проверки,
   запустить HTTP-сервис на устройстве с коннектором. Сохранить прежние тома и секреты.
3. Подготовить строгий манифест:

       node scripts/soty-app-release.mjs init --project /path/project --name Project --port 8111 --entry-path /

   Команда сохраняет .soty/app.json, повторяется для того же намерения и
   отказывается перезаписать другой манифест или выйти через symlink/junction.
4. Через интерфейс владельца подключить устройство, если ещё не подключено,
   добавить проект, закрепить имя и выбрать доступ. Не подключать чужой коннектор
   заново и не менять ownership в SQLite. Срок одноразового файла подключения —
   пять минут; origin должен точно совпадать с текущими Сотами. После привязки
   удалить обе временные копии. Действующее подключение переиспользовать.
5. Настройки приложения → Источник → «Размещение с агентом» →
   «Скачать данные размещения». Файл содержит только адреса, порт/путь,
   revision/digest источника и публикации. В нём нет токенов, ключей, grants и
   connector identity. Снимок не даёт разрешения на публикацию.
6. Подготовить план из свежего файла (не старше десяти минут):

       node scripts/soty-app-release.mjs plan --project /path/project --deployment /private/soty-deployment.json --output /private/run-unique

   При нескольких включённых адресах обычного проекта добавить --domain-id.
   У Source v2 план выбирает подтверждённый Source entry; у пары с --mode native —
   её точный Native alias. Переданный другой domain ID отвергается.
   План фиксирует именной вход и путь. applied=false означает только подготовку.
7. Проверить реальный опубликованный адрес:

       node scripts/soty-app-release.mjs verify --plan /private/run-unique/release-plan.json --probes /private/probes.json --output /private/run-unique/http-check.json

   Дополнительные проверки для native — JSON-массив, например:

       [{"path":"/api/health?probe=release","status":200,"contains":"ready"},{"path":"/assets/app.css","status":200}]

   Не помещать секреты в query или файл checks. TLS проверяется штатно.
   Перенаправления не маскируются успешным ответом другого сервера.
   У isolated первый запрос без bootstrap-сессии может получить HTML-вход
   gateway даже на API/asset пути. Поэтому 200 сам по себе не подтверждает
   ответ приложения. Его API, assets и содержимое проверять в браузере после
   bootstrap; использовать contains, когда endpoint действительно доступен
   без сессии. Не принимать HTML-вход за успешный JSON health.
8. В настоящем браузере открыть карточку в Сотах, пройти вход и чтение/запись
   проверочного объекта, перезагрузить; проверить ограничения доступа и
   сохранность старых данных. Проверить полный экран → возврат на том же iframe.
   HTTP-проверка отмечает httpOnly=true и не подтверждает весь выпуск.

Для ограниченной публикации CLI требует проверку авторизованным браузером.
Не публиковать приложение для всех ради обхода этого ограничения. Основная
страница, страница с query и boot ожидают 200; у пары Source/Native вместо boot
проверяется точный JSON текущей Native policy. Приложение с другим контрактом
ответа требует отдельного браузерного сценария; дополнительные probes дополняют
основные проверки, а не отменяют их.

## Gateway и собственная авторизация

По умолчанию isolated использует Soty gateway. Его sandbox, CSP, фильтрация
credentials и отсутствие workers сохраняются. Он подходит обычным приложениям
и не переносит browser storage между origins.

Доверенное приложение со своей серверной авторизацией, защищёнными cookies,
OAuth или своим API может требовать native. Сначала проверить приложение и
модель доступа. Затем указать --mode native; дополнительные точные доверенные
оболочки добавить повторяемым --frame-origin https://... .
Генератор создаёт native-ingress.caddy с фиксированным loopback upstream и точным
digest текущего источника. Он не применяет Caddyfile и не меняет DNS.

Каждый запрос проходит /_soty/ingress-check. В конфигурации обязателен
uri /_soty/ingress-check? — query удаляется только из копии для проверки доступа,
параметры исходного приложения сохраняются. Cookie Сот удаляется перед передачей
приложению; cookies приложения сохраняются. Добавочная frame-ancestors policy
сохраняет собственный CSP приложения. Проверить также его X-Frame-Options/CSP,
Origin/CSRF и callback URL: прокси не исправляет несовместимую авторизацию сам.
`forward_auth` удаляет Upgrade/Connection/Sec-WebSocket-* из своей HTTP-копии;
WebSocket к приложению сохраняется. Для небезопасных методов и WS проверяется
exact app Origin (включая отсутствие Origin и любой регистр Upgrade token).
Проверка — настоящий 101 + обмен сообщениями и отрицательные ACL/pin/Origin cases.

Для каждого Native snippet содержит отдельный exact GET
`https://NATIVE_ALIAS/_soty/ingress-check`: он направляется прямо в Root gateway,
минуя Native upstream и `forward_auth`. Заголовки surface/app/primary/target
задаются генератором, query и WebSocket upgrade удаляются из этой копии.
Для обычного Native primary и Native digest равны. Его проверка DATA сохраняет
прежние app/target и ingress session; пользовательские surface/primary
сбрасываются, чтобы нельзя было выбрать публичную policy вместо проверки DATA.

## Source в Сотах и отдельный Native вход

Подтверждённая пара сохраняет один app ID и два разных origin/порта: Source
entry внутри Сот и Native entry для отдельного браузерного входа. Source v2
экспортируется как `soty.app-deployment.v2`: `source.launchEntry` и
`nativeEntry` содержат только точные адреса и закреплённые target/policy поля.
Экспорт может описывать закрытую пару или `null` entry для диагностики;
он не подтверждает доступность и не выдаёт доступ.

Для Native плана нужны публикация anyone, оба bound/active alias и текущий
Source launch entry. Манифест `.soty/app.json` должен соответствовать
утверждённым Native port/entryPath, а не Source порту. Обычная команда
`plan --mode native` формирует `soty.app-release.v2`: публичный origin и probes
ведут в Native, `shellLaunchUrl` сохраняет Source entry. Старые сохранённые
адреса и глубокие пути не переписываются этим планом. Source-only v2 без пары
не может выпустить Native ingress.

Поле `nativeGuard` плана даёт настройки поддерживаемого Native SDK:
`rootCheckUrl`, app/origin и primary/Native digests. Root check использует
HTTPS Native alias с exact GET выше, без cookies или токенов в URL.
Оно подтверждает только текущую публичную политику. Native по-прежнему обязан
проверять свою Human session, роли и CSRF на HTTP/WS, а также продлевать
ограниченную lease для длительных соединений. Caddy проверяет WS handshake;
сам по себе он не закрывает уже открытый stream при отзыве публикации.

`verify` пары требует JSON не больше 4096 байт с точными app/origin,
primary/Native revisions/digests, policy epoch, admission hash и lease до 1 s.
HTML с кодом 200 или другой pin не проходит. Этот HTTP receipt не доказывает,
что Native SDK загружен или что Human login/данные проверены. Старый v1 HTTP
receipt также не объявляет Native guard готовым. При откате на ordinary Native
свежий v1 план сохраняет тот же exact policy GET маршрут; проверка DATA остаётся
обычной. Неподдерживаемая старым Root typed policy закрывает SDK доступ.

При изменении источника прежний native pin закрывает маршрут. Перед переключением
подготовить новую привязку по свежему снимку и проверенную обратную конфигурацию.
При обновлении того же порта/пути digest источника обычно не меняется; он не
заменяет immutable revision/image приложения. App ID, domain ID и данные
сохраняются. Создание нового app ID не является обновлением существующего.

### Новый Source-адрес без временной публикации старого порта

Поддержка атомарной активации объявлена как
`apps.inspect.source.sourceEntryActivation === true`; публичный
`GET /api/apps/capabilities` также возвращает boolean `sourceEntryActivation`.
Это возможность API, а не разрешение владельца или готовность Source.

Сначала закрепить имя штатным `apps.domains.claim`, оставив новый Source alias
bound, но неактивным. Установленный профиль должен точно задавать его
`embedOrigin`. В `apps.source.prepare` передать дополнительное закрытое поле:

```json
{ "sourceEntryAction": { "action": "activate", "domainId": "dom_0123456789abcdef0123456789abcdef" } }
```

Владелец проверяет возвращённые `sourceEntry: { origin, domainId }`, target и
то же `sourceEntryAction`. Подготовка проверяет только приватный канал
коннектора и MAC readiness Source; она не публикует адрес и не является
полноценным просмотром Source iframe до переключения.

При `apps.source.promote` передать **то же** `sourceEntryAction` вместе с
подтверждением `authenticated-workspace` для точного Source target. У пары
сохранить независимый Native `whole-port` ACK. Активация допустима только для
утверждённого Root-signed workspace Source v2 и `launchPolicy: "anyone"`.
Новый адрес, target, admission, policy epoch и receipt фиксируются одной
транзакцией; остальные активные адреса и действующая аудитория сохраняются.
Лимит — 100 активных адресов. Receipt v2 содержит действие и точный Source
адрес. Повтор исторического receipt не включает адрес, закрытый позднее.

Не включать Source alias отдельной публикацией под старым ordinary target
ради прохождения проверки: это открывает новый origin для старого целого порта.
Без capability действие не отправлять и не заменять его таким обходом.
Прежние запросы без действия сохраняют прежний контракт: необходимые alias
уже должны быть активны. Старый Root отвергает новое поле без эффекта.

Ошибки не требуют автоматического повторного promote:

- `invalid_source_entry_action` — неверная форма действия или неподдерживаемые
  профиль/политика; дополнительные поля, включая `origin`, отвергаются.
- `app_source_entry_domain_required` — точный Source alias отсутствует,
  не принадлежит этому приложению/владельцу, закрыт или отличается от профиля.
- `app_source_entry_action_mismatch` — действие отличается от подготовки либо
  адрес уже активирован; перечитать текущие данные и заново согласовать намерение.
- `app_native_entry_domain_required` — при сохранении отдельного Native входа
  его точный alias обязан оставаться опубликованным; без нового действия эта
  ошибка также применяется к неактивному Source alias.
- `invalid_publication_domains` — превышен лимит активных адресов; чужие адреса
  и прежние публикации автоматически не удаляются.

В журнале сохранять исходный requestId и различать непринятый запрос и
неизвестный результат. После потери ответа проверять тот же receipt;
смена адреса/target требует нового проверенного намерения и requestId.

Совместимость выпуска: DDL и публичный Source SDK не меняются. Receipt остаётся
v2 с добавочными `sourceEntryAction`/`sourceEntry`; прежний reader пары читает
его закреплённые target/Native поля и текущую публикацию. Возможность старого
runtime читать новый DATA проверить отдельно на синтетическом снимке перед
откатом. Отсутствующая capability означает отсутствие поддержки действия.
Незавершённое намерение с `sourceEntryAction` нельзя переотправлять старому
backend или переписывать в ordinary publish. Сохранить новую UI и журнал
ожидающего результата; для сверки/продолжения вернуть совместимый backend.

## Одна настройка зоны для многих проектов

Основная зона берётся из актуальных hosting-настроек. Для неё нужны wildcard
DNS и Caddy route:

    node scripts/soty-app-release.mjs zone --origin https://4-2.xn--p1ai --retain-origin https://xn--n1afe0b.online --retain-origin https://soty.pochinit.online --output /private/named-zone.caddy

Snippet содержит один HTTPS catch-all, host expression для выбранных зон и
отказ 421 вне этих зон. Он требует существующего глобального on_demand_tls с
ask http://127.0.0.1:18182/api/apps/tls-allow. Для новой зоны проверить это
один раз, сохранив корень, id, www, старые зоны и точные native hosts. Если уже
есть catch-all, аккуратно объединить его правила, не создавать второй адрес.
Не оставлять старые literal wildcard sites для этих зон: они заставляют Caddy
запрашивать wildcard-сертификат и могут перекрыть сертификат точного native host.
Без DNS challenge используются отдельные сертификаты зарегистрированных имён.
Имена из реестра открываются через wildcard gateway; неизвестные и вложенные
имена отклоняются. DNS запись сама не регистрирует приложение.

On-demand TLS имеет реальные ограничения CA. Для большого потока выпуска
сертификатов рассмотреть wildcard-сертификат через DNS challenge и согласованное
хранилище; это отдельное изменение после проверки возможностей DNS-провайдера.
Текущий реестр также ограничивает владельца 100 app IDs, включая отозванные.
Перед массовой партией выполнить [capacity preflight](../../skills/soty-app-deploy/references/capacity.md).

## Применение и откат

Сначала зашифровать исходную конфигурацию и проверить расшифрование/manifest.
Читать секреты только в памяти, выводить выбранные безопасные поля. Подготовить
кандидат, выполнить Caddy adapt/validate и локальные проверки queried entry,
assets, API и отказа при неверной source pin/сессии. Сравнить исходный SHA перед
атомарной записью; после reload сверить действующую и дисковую конфигурации.
Не заменять весь файл шаблоном и не перезагружать произвольный найденный процесс.
У Caddy adapt `file_server.hide` может содержать имя конфигурационного файла;
финальное сравнение делать по реальному serving path, не по другому имени
кандидата. Произвольные расхождения при этом не игнорируются.

Для выпуска самих Сот использовать [guarded maintenance rollout](../../deploy/connector/README.md):
immutable image, storage readers, точные mounts/config fingerprint, один writer,
свежий drain и проверенный prepare receipt. Служебный receipt не заменяет
поручение пользователя; при наличии поручения лишнее подтверждение не нужно.
Не использовать recovery вместо обычного обновления.

Откат оставляет текущую базу и возвращает совместимый процесс/маршрут.
Миграция данных требует отдельной backup/restore проверки и плана совместимости.
Не удалять app/domain IDs ради повторного запуска.

Оставить: source revision + image digest, публичный URL и точную ссылку Сот,
hashes конфигурации, receipts данных/браузера/доступа и команду отката.
Отдельно назвать неподтверждённые сценарии.

Контракты: [App operations](../../modules/apps/README.md),
[source/publication contract](../research/apps-contract-20260928.md).
Прокси: [Caddy forward_auth](https://caddyserver.com/docs/caddyfile/directives/forward_auth),
[response headers](https://caddyserver.com/docs/caddyfile/directives/header),
[certificate subjects](https://caddyserver.com/docs/automatic-https),
[host expression](https://caddyserver.com/docs/caddyfile/matchers#host).
