# Обложки приложений Сот

В интерфейсе используется отдельный генеративный арт. Названия, иконки, статусы, кнопки и доступность остаются настоящими HTML-элементами. Обложки не содержат текст и не заменяют работающий экран картинкой.

В этой поставке приняты шесть отдельных изображений: `notes`, `chess`, `tavysh`, `hive`, `focus`, `pulse`. Первые два соответствуют встроенным приложениям. Остальные — примеры визуального языка и готовые изображения для явной привязки к существующим приложениям. Наличие изображения не добавляет приложение в каталог и не означает, что приложение подключено.

## Новое приложение: подготовка одной командой

Создайте определение по образцу `scripts/app-art/examples/new-app.json`, подставив настоящий `appId`. Имя картинки (`key`) — стабильный локальный идентификатор; его не получают из изменяемого названия приложения.

```powershell
node scripts/app-art/cli.mjs prepare --definition ./new-app-art.json
```

Команда проверяет данные, локально сохраняет определение и связь `appId → key`, создаёт воспроизводимый job в `scripts/app-art/jobs/<key>/job-<hash>.json`. В `job.prompt` находится готовый запрос к генератору. Новые приложения по умолчанию имеют `kind: "app"`: им один раз назначается случайный публичный `publicKey` вида `art-<32 hex>`, который команда возвращает в результате. Название приложения и локальное имя определения не входят в URL картинки. В интерфейсе ничего вручную менять не нужно.

`prepare` не публикует ожидающую обложку, описание, `alt`, app ID или prompt в клиентский manifest и не отправляет данные генератору. До принятия изображения карточка использует обычную локальную палитру. Новый публичный ключ сохраняется между переименованиями и версиями арта.

Если определение обложки уже существует, можно сразу подготовить новый вариант и связать его с настоящим приложением: `prepare --key hive --app-id app-<32-hex-symbols>`. Для определения без `appId` тот же флаг передаётся вместе с `--definition`.

Для нескольких новых приложений передайте безопасный снимок каталога, как в `scripts/app-art/examples/app-catalog.json`:

```powershell
node scripts/app-art/cli.mjs prepare --catalog ./app-catalog.json
```

Принимаются только выбранные поля `appId`/`id`, `name`, `description`, `coverKey` и объект `art`. Конфигурация, переменные окружения, подключения и ключи авторизации не читаются. Из `art` можно задать `key`, `purpose`, `subject`, `alt`, `palette`, `focalPoint` и необязательный `compactFocalPoint`. Если определения ещё нет, его локальный ключ вычисляется из `appId`, а композиция — из назначения приложения. Точное предметное описание в `subject` даёт более выразительный результат. Эти данные остаются в локальных registry/jobs. Каталог всегда создаёт `kind: "app"`, поэтому private description и `art.alt` не становятся публичной подписью.

## Отдельные обложки поля

Карточки и поле используют независимые профили. Определение с `"profile": "field"` готовит квадратный арт для настоящей SVG-маски соты; это не переключает старые карточки на квадрат и не меняет их URLs. В квадрате оставьте воздух вокруг предмета: важные концы силуэта должны помещаться в центральных 70%, нижняя треть остаётся спокойной для HTML-подписи. В `styleReference` можно указать утверждённый локальный PNG внутри `output/`, например `output/soty-field-v2-20261006/01-mine.png`; путь остаётся в приватном job.

```powershell
node scripts/app-art/cli.mjs prepare --definition ./new-field-art.json
# Встроенный image_gen получает точный job.prompt и локальный style reference.
node scripts/app-art/cli.mjs import --key local-art-key --source ./generated-square.png --visual-approved
node scripts/app-art/cli.mjs bind --profile field --app-id app-<32-hex-symbols> --key local-art-key
node scripts/app-art/cli.mjs validate
```

Источник должен быть квадратным, минимум 960×960 px. Resize не увеличивает исходник: принятый профиль создаёт WebP 160/320/640/960 px с бюджетами 20/60/140/250 KB. Перед `--visual-approved` оператор смотрит отдельный предмет в реальной соте на большом экране и телефоне, проверяет важные концы, отсутствие текста, рамок и лишних объектов. Автоматическая проверка размеров не заменяет художественную приёмку.

Явный публичный `coverKey` для существующего общего арта задаётся `profile --key field-hive --cover-key hive`. Для частных определений `kind: "app"` разрешён только opaque alias; безопаснее использовать точную привязку app ID. Resolver `resolveFieldAppArt({ appId, coverKey }, { screenWidth })` отдаёт `src`, `srcset`, `sizes`, `focalPosition`, `compactFocalPosition`, `palette` и `fallback`. Привязка по ID имеет приоритет. Никаких выводов по названию приложения или его URL нет; незнакомый ключ использует обычную локальную обложку или нейтральный fallback.

Поле хранит только минимальный `public/app-art/field-profile.json` и равную ему source-копию `src/world/app-art-field-profile.json`. `manifest.json` карточек остаётся отдельным. В обоих публичных профилях нет prompts, purpose, исходных app IDs и локальных путей; новые private apps получают случайный публичный ключ и пустой alt. Как и карточные обложки, готовый арт публичен и не является механизмом доступа. Изменение, импорт и откат профиля требуют сохранённой private history; свежий checkout проверяет оба готовых профиля через `validate --public` и не очищает их при отсутствии operator data.

Для различимой HTML-подписи можно явно выбрать локальный значок: `icon --key field-canvas --icon brush`. Разрешён конечный набор `cells`, `brush`, `bars`, `activity`, `note`, `chess`, `music`, `app`; название и URL приложения не выбирают значок автоматически. `FieldAppArt.icon` необязателен. Изменение значка добавляет отдельный неизменяемый layout receipt к выбранному арту, сохраняет raster-файлы, generation receipt и version. Оно не вызывает генерацию. Значок можно также указать в новом определении с `profile: "field"`.

Фантазийные лица для проверки интерфейса находятся только в `src/world/fixtures/portraits/` и подключены dev-only `ui-fixture.ts`. Они не связаны с настоящими профилями и не используются как production пользователи, сообщения или online-сигналы.

## Реальная генерация

Генерация выполняется встроенным инструментом Codex `image_gen`, по одному вызову на отдельный арт. Передайте ему точный `job.prompt`, `transparent_background: false`, без скриншота как цели редактирования. Ключи API и платный CLI не нужны. Для новых обложек применяется исходный визуальный язык утверждённого рендера `output/soty-ideal-renders-20261005/01-graphite-home.png`: графит, светлая бумага, стекло, керамика, мягкий студийный свет.

CLI **не вызывает генератор**. Он автоматизирует подготовку, связь с приложением, оптимизацию, проверку, принятие и откат. Это честная граница текущей автоматизации: новая обложка появляется после настоящего вызова встроенного генератора и визуальной проверки выбранного результата.

Проверьте исходный результат и композицию в карточке: правильный предмет, отсутствие букв/цифр/кнопок/логотипов, чистый нижний участок для HTML-названия, аккуратная обрезка на узком экране. Принимается абстрактный арт, пригодный для общего статического размещения, без секретных экранов, личных фотографий и деталей закрытого проекта. Визуальную проверку выполняет человек или Codex по изображению; проверки размеров и хешей её не заменяют.

## После генерации: импорт одной командой

```powershell
node scripts/app-art/cli.mjs import --key example-canvas --source 'C:\local\selected-cover.png' --visual-approved --reviewer codex
```

Если для ключа есть несколько подготовленных запросов, укажите `--job scripts/app-art/jobs/<key>/job-<hash>.json`. `--generation-id` позволяет записать идентификатор фактического результата. Пример определения содержит фиктивный нулевой ID только для документации; не привязывайте его в рабочей сборке.

Импорт принимает только локальное неподвижное PNG/JPEG/WebP от 960 × 640, с отношением сторон 1.2–2.0 и размером до 32 MiB. Переориентированные EXIF-файлы нужно нормализовать перед принятием. Он не скачивает картинки, не принимает tracking URL и не вызывает сторонние сервисы.

Выбранный исходник и полный `provenance.json` сохраняются только в `output/app-art-history/<local-key>/v001-<source-hash>/`. Локальный `index.json` хранит текущие принятые версии. История содержит точный prompt, SHA-256 источника и каждого результата, версию рецепта и Sharp/libvips, генератор, зафиксированную визуальную проверку. Происхождение указывается как встроенный Codex `image_gen`; исходный утверждённый рендер использован как визуальное описание, а не как встроенный экран приложения.

В `public/app-art/<publicKey>/v001-<source-hash>/` записываются только WebP 320, 640, 960 и 1440 px без EXIF/ICC/XMP/IPTC, если исходник позволяет эти размеры. Публичный manifest содержит только готовые изображения: ключ, номер версии, безопасные поля палитры и фокуса, URL и геометрию WebP. Для новых приложений `alt` пустой: доступное название уже есть в настоящей карточке. Полные prompts, исходники, provenance, hashes назначения/запроса, локальные имена и пути генератора в публичном manifest отсутствуют.

Одинаковый исходник с тем же job не создаёт лишнюю версию. Новый исходник получает следующий номер; старые файлы не перезаписываются. Manifest переключается только после записи всех файлов. Повреждение или прерывание импорта до переключения сохраняет предыдущую рабочую обложку. Незавершённая версия может оставаться в истории, но не становится текущей.

Pipeline одновременно обновляет два одинаковых минимальных manifest: `public/app-art/manifest.json` как готовый статический JSON и generated `src/world/app-art-manifest.json` для синхронного импорта resolver. Клиент импортирует source JSON, поэтому Vite обрабатывает его как модуль и не предупреждает об импорте файлов из public. `validate` сверяет точное равенство байтов и SHA-256 обеих копий. Ручное редактирование generated JSON не требуется.

После import/bind/rollback или изменения crop-метаданных пересоберите frontend и выпустите готовые файлы обычным release-процессом проекта. Resolver получает manifest из сборки: копирование одного public JSON на работающий сервер не обновляет уже загруженный bundle. В local dev изменение generated source автоматически подхватывает Vite. UI-код для нового приложения менять не нужно.

В dev Vite подхватывает изменение source manifest; для собранного приложения нужен обычный rebuild, поскольку эти безопасные метаданные включаются в клиентский bundle. Публикация и расходы остаются отдельными действиями.

## Привязка существующего арта и откат

```powershell
node scripts/app-art/cli.mjs bind --app-id app-<32-hex-symbols> --key hive
node scripts/app-art/cli.mjs rollback --key notes --version 1
node scripts/app-art/cli.mjs validate
node scripts/app-art/cli.mjs list
node scripts/app-art/cli.mjs queue
```

`bind` локально связывает готовое изображение с настоящим стабильным ID. Клиентский manifest содержит SHA-256 lookup от app ID, а не сам private ID. Синхронный resolver вычисляет тот же lookup; API `{ appId }` остаётся прежним. Переименование приложения не меняет обложку. Сопоставления по названию и внешние cover URL отсутствуют. `rollback` переключает указатель на старую принятую версию из локальной истории, предварительно проверив файлы. Он ничего не удаляет.

Публичные WebP являются частью общей статической поставки. Случайные ключи и lookup-хеши убирают приватные имена и идентификаторы из метаданных, но не заменяют авторизацию приложения и не делают сам статический арт конфиденциальным. Закрытые экраны и данные приложений в этот pipeline не входят.

`queue` показывает только то, что ещё нужно подготовить или сгенерировать. `queue --all` включает принятые jobs. После успешного импорта job остаётся неизменяемым доказательством, но выходит из текущей очереди. Если определение поменялось, старый job не разрешает импорт нового изображения — сначала нужен свежий `prepare`.

Для нового варианта существующего приложения выполните `prepare --key notes`, затем генерацию и импорт. Для обновления всего визуального языка измените `styleVersion` и определения в registry и выполните `prepare --all --refresh`. `prepare --all` без `--refresh` пропускает уже принятые изображения текущего стиля, экономя повторную генерацию.

Для исходных утверждённых публичных примеров используйте `--prompt-file scripts/app-art/templates/prompts/notes.txt` и соответствующие файлы других приложений. Эти canonical templates содержат только общий арт для шести известных примеров. Новые рабочие prompts сохраняйте в игнорируемых `scripts/app-art/prompts/` и jobs; полные принятые запросы остаются в приватных неизменяемых receipts.

Для точечного редактирования уже принятого изображения передайте его локальный исходник в job:

```powershell
node scripts/app-art/cli.mjs prepare --key pulse --prompt-file scripts/app-art/templates/prompts/pulse-v2.txt --reference-image output/app-art-history/pulse/v001-8f459b0a0dcf/source.8f459b0a0dcf.png
```

После просмотра исходника вызовите встроенный `image_gen` с тем же `job.prompt` и `referenced_image_paths`, указывающим этот исходник. Импорт нового результата получает следующий номер версии. Job и receipt фиксируют actual input path и SHA-256; перед импортом hash проверяется повторно. Эти данные остаются в локальной приватной истории. Pulse v2 — реальный пример такого обновления: удалено растение слева, сохранены пять столбцов и студийный свет, v1 остаётся доступен для отката.

## Обрезка карточки без новой генерации

`focalPoint` задаёт базовую позицию объекта; необязательный `compactFocalPoint` — позицию для узкой карточки. Координаты обоих полей лежат между 0 и 1. Если compact-позиция не задана, используется базовая.

Измените только `compactFocalPoint` в определении уже принятого приложения и выполните `prepare --definition app-art.json`. Если описание для генерации не менялось, команда возвращает `prepared: []`, `ready` и `layoutUpdated`: генератор не вызывается, номер изображения, source/WebP, их SHA-256 и первоначальный generation receipt остаются прежними. В приватной истории появляется отдельный неизменяемый `layout.<hash>.json`, привязанный к номеру версии, source hash и generation receipt. Публичный manifest получает только две безопасные координаты. Повтор того же layout update не создаёт лишних receipts.

Для текущего Pulse v2 это воспроизводится командой:

```powershell
node scripts/app-art/cli.mjs prepare --definition scripts/app-art/examples/pulse-layout-v2.json
```

У Pulse compact-позиция `{ "x": 0.745, "y": 0.45 }` сохраняет пять столбцов в карточке с отношением сторон 1.1. Для остальных текущих обложек compact-позиция совпадает с базовой. Новое приложение настраивается тем же полем, без условий по названию/ключу в UI.

## API интерфейса

```ts
import { resolveAppArt, installAppArtFallback } from './app-art.mjs';

const art = resolveAppArt('notes'); // встроенное приложение
const connectedArt = resolveAppArt({ appId: actualApp.appId });
const explicitArt = resolveAppArt({ coverKey: 'hive' });

card.style.setProperty('--art-base', art.palette.base);
card.style.setProperty('--art-accent', art.palette.accent);
if (art.src) {
  const image = document.createElement('img');
  image.alt = ''; // декоративная обложка; название карточки уже доступно
  image.width = art.width;
  image.height = art.height;
  image.loading = 'lazy';
  image.decoding = 'async';
  image.style.objectPosition = `${art.focalPoint.x * 100}% ${art.focalPoint.y * 100}%`;
  const dispose = installAppArtFallback(image);
  image.srcset = art.srcset;
  image.sizes = art.sizes;
  image.src = art.src;
  card.prepend(image);
  // Вызовите dispose() при уничтожении долгоживущей карточки.
}
```

Результат: `{ key, status, src, srcset, sizes, width, height, alt, palette: { base, accent, ink }, focalPoint: { x, y }, compactFocalPoint: { x, y }, version }`. Обе позиции есть всегда; runtime ограничивает числовые координаты диапазоном 0–1, а неверные compact-значения заменяет соответствующей базовой координатой. Неизвестный/ожидающий ключ возвращает `src: null`, `status: 'fallback'` и устойчивую локальную палитру. Для private apps выбирайте арт через `{ appId }` либо через возвращённый opaque `publicKey`; локальное имя определения не отправляется клиенту. Ошибка загрузки скрывает только `img`; настоящая карточка, её текст и действие продолжают работать. Можно передать callback вторым аргументом `installAppArtFallback(image, callback)`.

Адаптивный UI может установить `--art-position` и `--art-compact-position` из этих двух полей и выбирать нужную переменную в CSS media query. Условий по конкретному приложению в компоненте не требуется.

## Проверки и обслуживание

```powershell
pnpm install
node --test scripts/app-art/*.test.mjs src/world/app-art.test.mjs
node scripts/app-art/cli.mjs validate
```

Используется проектный `sharp` 0.34.5, без Python и сетевого API. Resize и WebP-конверсия воспроизводимы при одинаковых версиях recipe, Sharp и libvips. Новый генеративный вызов не обещает идентичные пиксели: воспроизводимый результат обеспечивается сохранённым исходником и принятой версией.

Бюджеты на картинку: 320 px — 60 KB, 640 px — 140 KB, 960 px — 250 KB, 1440 px — 420 KB. Принятые шесть изображений укладываются с большим запасом; текущие 640 px занимают 7–21 KB каждое. Source PNG остаются в приватной локальной истории для воспроизводимости. `validate` проверяет SHA-256 и receipt по локальной истории, фактические размеры/формат, бюджет, очистку метаданных, локальность URL, минимальный whitelist публичного manifest и отсутствие исходников/receipt/прочих файлов в public tree.

В `.dockerignore` исключены `scripts/app-art/` и весь `output`: registry, jobs, prompts и history не отправляются в Docker build context. Финальный Docker image копирует собранный `dist`, и сервер раздаёт только этот каталог. Реальный Vite build в security-тесте проверяет, что private name, purpose, alt, appId, локальное имя, generator basename и полные prompts не оказываются ни в public-файлах, ни в bundle. Метаданные вложенных объектов палитры/фокуса также пропускаются через явный whitelist.

Первоначальные шесть source/receipts перенесены из старого public layout без изменения байтов и WebP URLs командой `migrate-history`. Она проверяет абсолютные пути внутри workspace и SHA-256 до native move; повторный запуск безопасен. После переноса нужен rebuild для очистки старых копий в `dist`.

Registry, jobs, prompts и история могут содержать закрытые описания и другие рабочие данные. Храните их в локальной рабочей среде оператора, исключайте из публичной публикации и коммитов. Приложение в production работает по минимальному manifest без этой истории. Для изменения уже выпущенного арта оператору нужна сохранённая локальная история; при её отсутствии CLI сообщает точный блокер и не удаляет текущие готовые обложки.

В Git остаются код, документация, `registry.example.json`, canonical `templates/prompts/`, минимальные source/public manifests и готовые WebP. Локальные `registry.json`, `jobs/`, `prompts/` и `output/app-art-history/` игнорируются. Для восстановления рабочего места оператора нужны согласованные копии registry, jobs и history из его приватного хранилища; полное описание приложения невозможно и не нужно восстанавливать из публичного bundle. Эти файлы не должны содержать пароли или ключи API.

Свежий Git checkout запускает UI без private registry/history. Проверить уже выпущенные обложки можно независимо:

```powershell
node scripts/app-art/cli.mjs validate --public
```

Этот режим проверяет строгий whitelist всех уровней display manifest, равенство source/public JSON, привязки, версии, размеры и форматы реальных WebP, budgets, отсутствие встроенных метаданных и совпадение SHA-256 с 12 hex в имени каждого WebP, включая прошлые версии. Он честно возвращает `operatorHistoryVerified: false`; полная проверка provenance доступна обычным `validate` на рабочем месте оператора. Prepare/import/bind/rollback без приватного registry либо принятой history завершаются до изменения public manifests и сохраняют текущие обложки. `registry.example.json` — безопасный исходный шаблон для отдельного нового каталога, а не замена утраченной истории уже выпущенных изображений.

Повторный импорт идентичных исходных байтов проверяет receipt, источник и каждую текущую rendition прежде, чем вернуть `unchanged: true`. Для idempotence должны совпадать также style/definition/prompt и полная job identity, включая edit reference. Новый job остаётся в очереди до приёмки его результата даже при совпадении текста запроса с прошлым. Повреждённый либо отсутствующий файл требует восстановления точной принятой копии; CLI не выдаёт ложный успех и не перезаписывает immutable версии. Edit preparation проверяет accepted source по receipt/hash; rollback проверяет тот же набор integrity/acceptance условий до смены выбранной версии и применяет текущий configured compact crop отдельным layout receipt, сохраняя source/WebP/generation bytes. Два локальных определения не могут занимать один публичный ключ: для намеренного общего арта нескольких приложений используйте `bind`.

Готовые cover-файлы являются публичными статическими ресурсами. Opaque publicKey и хеш привязки убирают названия и исходные app IDs из каталога, но не заменяют авторизацию: человек с URL может загрузить обложку. Для private apps создавайте абстрактный общий арт без конфиденциальных надписей, изображений людей, клиентских документов или других секретных деталей. Полное описание и generator provenance остаются локальными.

Одновременные изменения блокируются `.pipeline-lock`. После аварийного завершения убедитесь, что ни один процесс `app-art` не работает, и удалите только оставшийся пустой каталог `scripts/app-art/.pipeline-lock`; затем повторите команду. CLI не удаляет lock другого активного процесса и не перезаписывает старые версии.
