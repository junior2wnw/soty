# Единая геометрия сот — 28 сентября 2026

Проблема в проверенном коде: flat-top polygon применялся к прямоугольникам 83×94, 150×168, 135×124 и другим независимым парам. Это разные формы, хотя CSS называл их одинаково. У старого мобильного поля высота соты была 50 px, а вертикальный шаг — 44 px: соседние соты пересекались. Внутренний `inset:3px` дополнительно искажал пропорции вложенного шестиугольника.

Изучены первоисточники: [Red Blob Games — Hexagonal Grids](https://www.redblobgames.com/grids/hexagons/), [авторская реализация преобразований](https://www.redblobgames.com/grids/hexagons/implementation.html), [W3C CSS Box Sizing — aspect-ratio](https://www.w3.org/TR/css-sizing-4/#aspect-ratio), [W3C CSS Masking — clip-path](https://www.w3.org/TR/css-masking-1/#the-clip-path), [W3C WCAG 2.2 — Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html). Ниже отдельно обозначены выводы для проекта; это не утверждение, что источники предписывают конкретный дизайн Сот.

## Десять решений и способы проверки

1. **Одна ориентация и один размер.** Правильная flat-top сота определяется радиусом `R`: `W=2R`, `H=√3R`. В исходном материале осевая сетка преобразуется единой матрицей. В проекте оставлен один `--hex-width`; высота следует из `aspect-ratio`. Независимые пары ширины и высоты удалены. Проверка: 500 разных радиусов, шесть равных сторон и одинаковый апофем; браузерная метрика `width / height ≈ 2/√3`.

2. **Общая система координат.** Используется axial `(q,r)`, третья кубическая координата равна `−q−r`. Центры: `x=1.5Rq`, `y=√3R(r+q/2)`. Эти формулы и набор шести соседей следуют авторской реализации Red Blob Games. Мобильная ширина меняет размер всей сцены или количество колонок, а не одну ось. Проверка: 1000 преобразований центр→пиксели→центр и точки около центров; кольца имеют `6n` элементов, диск — `1+3n(n+1)`.

3. **Зазор измеряется между гранями.** Наш вывод: для одинакового перпендикулярного зазора `g` радиус сетки центров должен быть `Rp=R+g/√3`. Тогда расстояние соседних центров равно `√3R+g` во всех шести направлениях. Ширина нарисованной соты остаётся `2R`. Проверка охватывает 254 пары размеров/зазоров, включая прежний проблемный мобильный размер.

4. **Контур острова выводится из его сот.** Семь позиций — центр и шесть соседей. Контур строится по внешним рёбрам сетки радиуса `Rp`; общие рёбра удаляются. Это наш алгоритм композиции, основанный на общей осевой модели. Произвольный вручную нарисованный polygon острова удалён. Проверка: у цветка один замкнутый контур из 18 рёбер; каждое равно `Rp`. Название занимает отдельную полосу над контуром.

5. **Внутренний бортик также правильный.** Наш вывод из апофема: для толщины `d` внутренний радиус равен `R−2d/√3`. Отступ по вертикали — `d`, по горизонтали — `2d/√3`. Одинаковый inset по обеим осям не подходит. Проверка: 400 случайных допустимых отступов сохраняют отношение сторон, а расстояние от каждой внешней грани до внутренней равно `d`.

6. **Содержимое не рассчитывает на обрезание.** По CSS Masking, clipping меняет отрисовку, но не обычную геометрию размещения содержимого. Поэтому центральная безопасная область задана явно: 66% ширины и 60% высоты внутренней соты. Для её углов проверено неравенство `√3|x|+|y| ≤ √3Rinner`, а также горизонтальные грани. Полные имена доступны через доступное имя кнопки/подсказку; короткая подпись визуально ограничена одной строкой. Количество на малой соте ограничено `99+`, полное число остаётся доступным.

7. **CSS не может исправить две уже заданные оси.** Согласно CSS Sizing, preferred aspect ratio участвует в вычислении автоматического размера. Поэтому недостаточно добавить `aspect-ratio` поверх старого `width/height`: старые высоты, произвольные inset и масштабы отдельных островов удалены из исходных правил. Нет каскада поправок поверх старой геометрии. Константы polygon, ratio и safe fractions передаются в CSS из `hex.mjs`.

8. **Фото сохраняет собственные пропорции.** Исходное фото не превращается в заранее обрезанную шестигранную картинку. DOM `<img>` заполняет регулярный внутренний полигон с `object-fit:cover`; загрузка, ограничения формата и приватный memory-cache остаются прежними. Инициалы получают размер относительно конкретной соты, а не ширины viewport. Проверка: маленькие аватары в шапке, сообщениях и списках; большие в профиле; новый загрузчик и пустое состояние используют ту же форму.

9. **Плотность не уменьшает надёжность нажатия.** WCAG 2.2 AA задаёт минимум 24 CSS px либо допустимый интервал/исключение. Проектные основные плитки значительно крупнее: 70 px ширины в старом мобильном поле и 128–144 px для личного пространства. Для интерфейса сохранены native button, roving keyboard navigation поля и равноправный список. Это не заявление, что каждая вторичная кнопка приложения имеет 44 px. Состыкованные кнопки имеют настоящий polygon hit region: прозрачный угол прямоугольника не перехватывает соседнюю соту. Клавиатурный focus обозначается внутренним контрастным бортиком 4 px; внешний outline не используется, поскольку его обрезал бы clip-path.

10. **Проверяем свойства, а не снимок одной формулы.** Тесты независимо измеряют стороны, центры, углы safe box, периметр и фактические границы разных наборов плиток на ширинах 320/390/768/1440. Ошибочные радиусы и отступы дают явную ошибку. Pure-модуль не зависит от DOM, сети или состояния приложения. В браузере дополнительно нужны реальные размеры, отсутствие перекрытий, длинные названия и четыре поверхности: общий мир, личный мир, карточки/диалоги, старое поле.

## Реализация и проверка

- `src/geometry/hex.mjs` и `hex.d.mts`: формулы, сетка, кольца, контур, безопасная область.
- `src/geometry/dom.ts` и `hex.css`: геометрические CSS variables и один контракт формы.
- `src/ui/hex-tile.ts`: доступная кнопка с независимой поверхностью и `.soty-hex-safe`.
- `src/world/hex-field.ts`, `dom.ts`, `icons.ts`: реальные данные, правильные острова, пустые состояния и знак сот.
- `src/ui/hex-field.ts`, `src/style.css`: старое поле на общей осевой геометрии, пересчёт координат при resize.
- `src/entry.css`: загрузчик на той же геометрии.

Проверено 28 сентября: `node --test src/geometry/hex.test.mjs` — **10/10 PASS**, `npm run typecheck` — **PASS**. - В 14 состояниях измерены 2364 прямоугольника форм; это сумма измерений по размерам, включая соты за границей viewport старого поля, а не число разных компонентов. Максимальное абсолютное отклонение `width/height` от `2/√3` — **0,000535** при допуске **0,003**; остаток соответствует субпиксельному округлению браузера.
- Максимальная ошибка фактической позиции соты острова относительно вычисленной осевой позиции — **0,014 px**. Расстояние между гранями — **5,987–6,011 px** на планшете/десктопе; при равномерном масштабе 0,8/0,9 оно становится около **4,8/5,4 px**. Соты не выходят за геометрическую границу своего острова.
- В прежнем поле фактическая ширина — **70 px** на телефоне и **78 px** на планшете/десктопе, зазор **5,972–6,004 px**. Старая вертикальная коллизия больше не воспроизводится.
- Для 16 измеренных областей нажатия главной центр попадает в свою native button, прозрачный угол — не в неё. После клавиатурного Tab виден внутренний фокус: `inset:4px 4.6188px`, цвет из семантического `--sw-focus`.
- Все 24 измеренные безопасные области главной и их дочерние элементы остаются внутри доступного места. Полная подпись остаётся доступным именем даже при визуальном сокращении.

Браузерная проверка обнаружила две ошибки, невидимые для чисто математического теста. Тема задавала аватарам `position:relative` и вытесняла прежнее одноклассовое правило размещения: специальная роль `.soty-hex.soty-hex-placed` теперь явно устанавливает абсолютное размещение. Общее `max-width:100%` сжимало старые соты до ширины их координатного контейнера `.hex-map` — 1 px: это ограничение удалено из исходного общего правила формы, размером управляет `--hex-width` и расчёт layout. Итоговые кадры сняты после обоих исправлений.

Финальный поиск по `src` и `public` не нашёл независимых шестигранных CSS polygons: остаются общий `HEX_POLYGON`, его контрольное значение в тесте и генерируемые SVG-вершины. Квадратные `aspect-ratio:1` относятся к иконкам, QR и шахматной доске; `skewX/scaleY` в прежнем `thinking-kick` — анимация индикатора, а не соты. Псевдоэлемент загрузки, знак записок и значки возможностей используют общий ratio/polygon. Карта слотов общего мира очищает ID, отсутствующие в новом результате; порядок оставшихся элементов сохраняется внутри текущей страницы.

Артефакты: `output/geometry-validation-20260928/metrics.json`, пары `home-*.png`, `world-*.png`, `legacy-*.png`, `profile-390.png` и `profile-1440.png`. Старые кадры до исправлений заменены финальными. Временный размер окна Chrome сброшен, вкладка интегратора не изменялась.

Предел проверки: это Chromium на изолированной локальной базе, без подмешивания декоративных пользователей. В свежем профиле Chrome нет заполненных прежних комнат, поэтому содержимое populated legacy tiles не проверялось на выдуманной браузерной фикстуре; безопасная область такого компонента проверена математически и в исходном CSS. Отдельная межбраузерная приёмка Firefox/WebKit здесь не заявляется.
