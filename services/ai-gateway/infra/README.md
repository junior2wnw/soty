# Развёртывание на DEV

Источник фактических ключей и upstream на 25.09.2026 — работающий контейнер `soty-online-chat` на SSH `dev`. Timeweb `soty` уже передаёт запросы на DEV. Обнаруженный revision исходного приложения: `d9585cd2285e2f2288f607c86356848a6c9cc127`; это новее исторической опоры `2904528`.

Новый стек изолирован от работающих проектов: `inference-commerce`, loopback `18540` для сайта/API и `18542` для PostgreSQL. Docker volume с БД не общий со старыми Сотами. Настройки находятся вне Git в `$HOME/.config/inference-commerce`, каталог 0700, файлы 0600. В контейнере реестр импортированных fingerprints доступен только на чтение. Secret-файл должен быть читаем UID 1000 контейнера; не делать его общедоступным.

```sh
export RUNTIME_DIR="$HOME/.config/inference-commerce"
docker compose --env-file "$RUNTIME_DIR/runtime.env" -f infra/compose.yaml up -d --build
```

Перед первым запуском в закрытом runtime.env задать `POSTGRES_PASSWORD`, `DATABASE_URL`, `API_KEY_PEPPER`, upstream credentials. `stage-legacy.py` создаёт их на DEV из действующего источника, не копирует секреты в репозиторий и не выводит их. Запускать этот скрипт с машины, где разрешён SSH alias `dev`; он не меняет исходный контейнер.

`CONNECTOR_LIVE_ENABLED=true` разрешает инференс; `HEALTH_PROBES_ENABLED=true` — служебные проверки. `HEALTH_PROBE_RESERVE_URUB` должен быть явной положительной оценкой верхней границы стоимости одной пробы. Если оценка не задана, worker сообщает `probe_cost_unknown` и не тратит деньги. Настроечный период 10 с — цель проверки, а реальные timestamps отражают завершённые наблюдения. Общий служебный бюджет — 50 ₽/сутки; внутри него пробам выделено не более 10 ₽/сутки, чтобы мониторинг не израсходовал весь допуск клиентов. Глобальная параллельность проб — 2; реальная нагрузка заменяет лишние проверки. После исчерпания подлимита оценки продолжаются с `monitoring_budget_exhausted`, новый успешный клиентский запрос обновляет состояние. Серверные попытки максимум 2, стратегия `fallback` либо `race`; смена модели требует отдельного opt-in.

Цены `GONKA_RETAIL_INPUT_URUB_PER_MILLION` и `GONKA_RETAIL_OUTPUT_URUB_PER_MILLION` — целые микрорубли, назначенные оператором. Они не выдаются за рыночную котировку. Без них цена unknown. Фактическое состояние и статистика загружаются из БД и live-наблюдений; стартовые цифры рендеров не являются seed production.

Успешная проверка JSON и фактический валидный вызов инструмента сохраняют квалификацию конкретного маршрута на срок до 24 часов. После перезапуска эта квалификация восстанавливается для разрешённого auto-переключения, но не превращается в свежую проверку доступности: `checkedAt` и зелёный статус требуют нового наблюдения. Некорректный JSON, произвольные пояснения и оборванный документ не исправляются вырезанием удобного фрагмента.

После canary проверять старые URL и все типы credentials, stream, JSON и tools; root Сот с комнатами/историей не заменять новым кабинетом. Caddyfile.example — пример, не самовольная смена DNS. Откат: вернуть **только inference handlers** предыдущему upstream; не откатывать БД с новыми отзывами ключей и начислениями. Старый контейнер оставить доступным до завершения миграции.

Production backup требует отдельного зашифрованного off-host хранилища и проверки восстановления. Локальный volume и шифрованный снимок исходных секретов не заменяют PostgreSQL WAL backup. Платежи и финансовый запуск остаются отключёнными до реальных реквизитов/провайдера и сверки тарифа.

## Ручная зашифрованная копия и восстановление

На Windows-контроллере с разрешёнными SSH alias `dev` и `soty`:

```powershell
python infra/backup-postgres.py --verify-restore
```

Скрипт получает `pg_dump` в память, шифрует AES-256-GCM, отправляет **только шифротекст** на отдельный Timeweb в `/var/backups/inference-commerce`, повторно скачивает его и проверяет расшифровку/контрольную сумму. Ключ защищён Windows DPAPI текущего пользователя вне репозитория; его нет на DEV и Timeweb. Нужны сохранность Windows-профиля и отдельный документированный путь восстановления контроллера: потеря этого DPAPI-контекста означает потерю доступа к копии.

`--verify-restore` создаёт одноразовую БД с генерируемым именем `inference_restore_*`, проверяет баланс проводок/кошельков и пределы резервов, затем удаляет только эту тестовую БД. Она не обслуживает API и не отправляет запросы поставщикам. Исходная БД не заменяется. Копирование ограничено 256 МиБ БД для начального пилота; при росте нужен потоковый backup.

Это **ручной backup**, его RPO равен времени с последнего успешного запуска. Расписание, WAL-архив и RPO 60 секунд не объявляются работающими. Запуск первого backup/restore и его факт фиксируются в release receipt отдельно.
