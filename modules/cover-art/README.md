# Target-scoped cover storage

One backend engine for Apps and Root World. This package is a Source candidate until its parent schema, Connect authority ports and UI are integrated and checked. It does not migrate/open a production database, expose HTTP/MCP, invoke a generator or create schedules.

## Root integration contract

1. During the owning **explicit atomic migration**, add `coverSchemaStatements(kind)` and `coverSchemaSeed(kind,stableInstanceId)`. Apps audience9/10/11 becomes12/13/14 preserving base6/7/8; RootWorld5 becomes6 together with DM. Keep M02World4 separate. Include the exact new objects in the owning schema recognizer, image reader/storage admission and Docker reader labels. The engine refuses old marker/user_version and exact fragment drift; it never creates missing tables on startup.
2. Choose a stable nonsecret store instance ID matching the seed, e.g. a prefix plus hash of the existing project ID. It is part of every intent digest and must survive restart. It is not supplied by RPC clients. Construct the store **after migration commit**, outside another DB transaction. Startup audit compares persisted byte/reservation/draft/receipt counters with actual target rows.
3. Pass the existing target `DatabaseSync`, and a synchronous `withAuthority` preserving the current Connect → World → Apps lock order. `readTarget` is synchronous and reads current owner, enabled state, immutable Source target revision, policy epoch and actual viewer rights in that same DB/fence. For World, profile revision serves as both target revision and policy epoch. Never build an actor from args. Do not hold a World writer lock and then call an Apps operation from inside it.
4. Share one `createCoverDecoder()` instance across Apps/World in the configured cover worker process. Runtime `sharp` must actually be packaged before advertising the write feature. Decoder slots remain occupied until native work settles; queue timeout only drops unstarted work. Additional replicas need a shared/partitioned total admission budget; per-process concurrency is not a deployment-wide global bound.
5. `onCommit` runs synchronously in the engine's target DB transaction. Apps needs no change to Source/launch state; publish cover revision separately. World updates `profiles.avatar_revision=revision+1` for custom, NULL for none/inherit, and `profiles.revision=revision+1`; `projectOwner` returns the current WorldProfile. Errors roll back asset/pointer/receipt/compatibility together. After-commit notifications must not try to undo a durable receipt.

All read/write methods use actor as a **host argument**, separate from client payload. Register only the named intended methods, not the whole store: `legacyCommit`, `collect`, `audit` and schema helpers are host-only. Existing capability grants still apply. No provider => `generationAvailability().available=false`; do not register an executing generation capability. `index.d.ts` contains only a future durable-provider interface, not a fake ready connection.

## Concrete avatar compatibility

World6 migration creates new fragments, calls `migrateLegacyAvatarTable(db,{now})` inside its existing writer transaction, then commits the complete World6 marker/schema. The helper copies the old PNG/JPEG/WebP bytes and MIME **exactly**, keeps profile and avatar revisions, records origin legacy without provider, drops the old table and creates the exact `profileAvatarViewSql()` read view. It does not set user_version or begin/commit. New empty stores also run it against their freshly created empty legacy table, or install the same view directly after equivalent validation.

Route `world.profile.avatar.set` to `createLegacyAvatarAdapter({store}).set(actor,args)` **before** the old World operation dispatcher enters BEGIN. Replace that write branch in Root's integration; do not leave the old INSERT/DELETE targeting the new view. Legacy args and profile-revision CAS remain exact, and the helper uses the same common version/head/quota/receipt writer. New reads/batches continue querying `profile_avatars` under the existing World full-profile and room-thumbnail authorization. Do not broaden room thumbnail access to full avatars.

The legacy adapter's opaque internal receipt does not become a fictitious client request-id API. On a lost old-client response, use its existing signed readback/CAS recovery. The new upload/commit/restore protocol has explicit durable request IDs and typed receipts.

## Upload/crop protocol

Request IDs: `cover1.<13-digit-server-time>.<32-lowercase-hex>`. Read `serverTime` via status/head context; do not require a person to fix local clock. Persist exact request before dispatch; reuse it after unknown outcome. A retained receipt returns historical outcome plus **current** head before CAS/quota checks; it never re-applies an old pointer. Expired literal IDs cannot become new operations after retention: logical time and request floor only increase.

`prepareUpload` accepts a selected bounded raster (PNG/JPEG/WebP <=320KiB, <=1,048,576 decoded pixels), MIME, target/current expected revisions and crop. Client normalizes the original locally before upload; raw20MiB phone photos do not go through the model. The real server decoder verifies format/pages, re-encodes bounded square renditions, strips metadata, preserves app alpha and flattens the profile image. Save the exact asset/draft scope; preparing does not publish.

For compatibility with existing avatar consumers, this first backend slice **bakes the selected crop into canonical bytes**. Current and room avatar readers therefore show the real chosen frame without needing a new rendering protocol. Commit reports `cropApplied:true` and identity crop; the UI must not apply the input crop a second time. Reframing a retained own picture uses `prepareFromVersion` internally, then the same commit. It recompresses bounded saved pixels, never invokes a provider; it cannot recover pixels outside the originally saved canonical frame. This is a purposeful refinement of the earlier metadata-only crop proposal, required for old-avatar compatibility.

`prepareFromVersion` fingerprints the canonical request (source version ID, normalized crop, expected target/policy/cover revisions, owner, device and store), independently of source bytes. The shared preparation writer rechecks current management authority and matches that immutable fingerprint **before** reading the source. An exact retained receipt still replays after source GC; a changed crop/version/expected revision/device conflicts, and revoked access still denies it. New recrop requests require a live retained own source. Replay never decodes or creates another draft.

App recipe limits:160/320/640/960 roles <=20/60/140/250KB, no upscale. Profile image/thumbnail <=512px/96KiB and192px/8KiB. Real widths may be smaller. `commit` scopes draft to store/kind/target/owner/device/target revision/policy epoch/cover revision; `restore/remove` use fresh CAS. Owner-only `versions` returns up to20 safe metadata records with honest restorable status, allowing undo after reload without keeping a client-only history. `none` intentionally hides a compiled default; `inherit` resets to it. Rename/theme/reload never generate.

## Limits, retention and private delivery

Server-owned defaults: app owner128MiB/global2GiB; profile owner2MiB/World global256MiB; drafts4 per owner/2 per target/64 per store, TTL30min; decoder2 active per worker/1 per owner, queue16/2 per owner, queue deadline30s; mutation12/min; receipts30days with owner4096/store262144; history current+2 prior, previous choice protected24h, current always; GC32 rows/4MiB per pass. Logical bytes include ready drafts and reservations; they do not equal physical SQLite/WAL size. Deployment needs its own disk reserve/backup policy.

The last previous choice is protected for 24h **from replacement**, including quota-pressure collection. Each head transition records its old active ID and replacement time; version creation times, original MIME/bytes and receipt outcomes stay immutable. SQL guards deny premature previous-version purge or deletion. The head previous ID is an intentional bounded-history tombstone, without an FK: after its protection and metadata retention expire, GC may reclaim that row. Startup audit requires a live scoped previous row while protected, and validates its scope/sequence whenever it still exists. The head lineage trigger binds each new previous pointer to the prior active ID and replacement time to the transition's update time.

The engine runs one bounded `collect()` after a successful version transition; host also calls it on open/maintenance when useful. A maintenance failure after a durable commit returns `maintenancePending:true`, not a false rollback; host records that bounded diagnostic and retries maintenance, while the immutable receipt remains valid. Allocation preflight performs bounded cleanup only when expired work or actual quota pressure exists. It never erases current/protected/live-draft bytes. No hidden cron. A full safe retention window rejects new allocations; it does not delete receipts to make a new request look first-time. `audit()` is an independent SQL recount; no write-test simulates private production data.

Private bytes are returned only by the signed UI read adapter with current target authorization. Viewers see current cover only, owners may see retained history. Normal directory/tool DTOs carry safe refs/revisions, never base64 or prompts. Dynamic reads use no-store; do not put private renditions in public/app-art, public immutable URLs, external CDN, logs or model context. A public anonymous image route is a separate Root HTTP design and must recheck current listed/public state per request.

## Verification boundary

`test/cover-art.test.mjs`, `codec.test.mjs`, `legacy-avatar.test.mjs` run actual Node SQLite/Sharp in guarded synthetic temp stores, including formats12/13/14, profile bytes/view, prepared CAS, policy revocation, in-flight decode, replay, restart, quotas, GC and receipt expiry/clock rollback. The fixture authority adapter reads current SQL state but is not a real signed Connect bridge; Root must add integration tests for its fresh rights/actual call/persistence/reload. These tests do not prove production schema admission, physical devices, visual acceptance, provider dispatch or billing.
