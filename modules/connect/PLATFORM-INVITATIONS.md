# Приглашения для входа в Соты

Сервер Connect хранит отдельную политику: `inviteOnly:false`, `defaultQuota:3`.
Лимит относится только к новым аккаунтам Сот. Приглашения сотрудников,
контактов, сообществ, перенос и подключение устройств не используют эту квоту.

Администраторы задаются доверенным host config `platformAdminAccountIds`;
по умолчанию список пуст. Root adapter принимает соответствующий список через
`SOTY_PLATFORM_ADMIN_ACCOUNT_IDS` (через запятую). Никакой аккаунт не становится
администратором первым входом, через клиентский JSON или владение приложением.
Изменение конфигурации требует штатного перезапуска host.

## Контракт интерфейса

Все операции идут через существующий подписанный Connect challenge/proof.

- `platform.admission.get {}` → `inviteOnly`, `defaultQuota`, `revision`,
  `manageAllowed`. При `false` интерфейс показывает настройку только для чтения.
- `platform.admission.update {requestId, expectedRevision, inviteOnly,
  defaultQuota}` → новая политика. Нужен текущий администратор; квота 0–100.
- `platform.invites.issue {requestId, token}` → `invitation` с `id`, временем
  создания и сроком. Клиент генерирует ровно 32 случайных байта через
  `crypto.getRandomValues` и кодирует base64url без padding (43 символа).
  Сохраняет token и requestId локально до подтверждения, повторяет те же
  аргументы при потере ответа. Сервер хранит только SHA256 токена; восстановить
  исходную ссылку из списка нельзя. Не помещать токен в логи или query URL.
  Будущий UI может передать его через fragment и убрать fragment после чтения.
- `platform.invites.list {}` → только свои приглашения (последние 200),
  `quota`, `used`, `remaining`. Данные получателя и токены не возвращаются.
- `platform.invites.revoke {requestId, invitationId}` → своё приглашение с
  `revokedAt`; погашенное приглашение отозвать нельзя.
- Существующий `bootstrap {label, encryptionPublicJwk, invitationToken?}`
  проверяет приглашение только при создании нового аккаунта. Повторный вход
  известного устройства сохраняет прежний accountId и не тратит приглашение.

Приглашение живёт 7 суток. Активное приглашение резервирует один слот;
погашенное расходует его постоянно. Отозванное или истёкшее непогашенное
возвращает слот. Уменьшение квоты не отзывает ранее выпущенные приглашения:
оно ограничивает новые. При выключенном режиме новый вход разрешён без токена;
явно переданный токен всё равно проверяется и погашается.

Выпуск, квота, сохранение receipt и погашение с созданием аккаунта используют
одну существующую SQLite транзакцию Connect. Новый challenge нужен для повтора
сетевого запроса; тот же requestId и точные аргументы возвращают исходный receipt.
Изменение аргументов при прежнем requestId даёт `platform_request_conflict`.
Отзыв прав администратора проверяется и до выдачи старого admin receipt.

Ошибки интерфейса: `platform_admin_required`, `platform_policy_conflict`,
`platform_invite_quota_exhausted`, `platform_invitation_required`,
`platform_invite_unavailable`, `platform_invite_already_redeemed`,
`platform_invite_token_reused`, `platform_request_conflict`.

## Выпуск и совместимость

В существующий профиль `openConnectPanel` встроены остаток приглашений,
создание, ссылка/QR, статусы, отзыв и административная настройка. Режим и квота
показываются для изменения только при `manageAllowed:true`. Старый сервер
показывает сообщение о необходимости обновления без неработающих переключателей.

Root accountClient включает `capturePlatformInvitation:true`. Fragment
`#soty-invite=...` удаляется до маршрутизации; повтор после потери ответа хранится
только в sessionStorage этой вкладки до успешного bootstrap. Известный профиль
очищает приглашение без погашения. Созданные ссылки сохраняются в этой вкладке
отдельно для аккаунта; другой браузер видит статусы, но не исходные токены.

Изолированный сквозной стенд: `node modules/connect/test/support/platform-invites-server.mjs`,
затем `http://127.0.0.1:5197/?role=owner`. Это отдельная временная SQLite,
настоящий Connect, WebCrypto, IndexedDB и профиль UI. Его fixture admin route
существует только в специально запущенном локальном test server, не в Root.
Playwright CLI выполняет `platform-invites-browser.js`, затем
`platform-invites-compat-browser.js` из той же папки. Проверены два аккаунта,
три приглашения, запрет четвёртого, QR, reload, bootstrap/очистка fragment,
отказ обычному пользователю в admin update, отзыв, известный аккаунт и old server.
Живой выпуск и включение не выполнены.
Schema4 / reader2 / module0.2.0 намеренно запрещают открытие БД старым reader1,
который иначе обошёл бы admission. Старые записи сохраняются. Перед выпуском
нужно остановить все прежние writers, сохранить штатную защищённую резервную
копию и подготовить совместимый reader2 для отката. Обычный auto-update с0.1
отклоняется как требующий миграции. Конфигурацию администратора сверяют с точным
существующим личным accountId, затем проверяют `.get`; режим остаётся OFF,
пока администратор отдельно не изменит его.
