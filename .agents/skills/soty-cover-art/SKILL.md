# Обложки приложений Сот

Результат — узнаваемая обложка в настоящей соте, читаемое HTML-название поверх неё и сохранённая версия с возможностью возврата. Этот пакет доступен через `/skills/index.json`; его текст не выдаёт прав на приложение или генератор.

1. Составь список по всем объектам нужного живого поля и доступным каталогам: собственные, предоставленные и публичные приложения, встроенные возможности. Для каждого сохрани настоящий stable ID, тип объекта, назначение, текущую обложку и действие: сохранить / создать / проверить / применить. Один аккаунт или один owner-каталог не доказывает охват всех приложений; проверяй остальные доступные аккаунты только в пределах разрешённого доступа. Название и адрес не являются идентификатором. Не создавай отсутствующие приложения ради обложек.
2. Сохрани принятый визуальный язык. Выбери один предмет или простую композицию, которая выражает функцию приложения и узнаётся в маленьком размере. Материал, свет и силуэт важнее множества декоративных деталей. В одном наборе сохраняй общую режиссуру, различая приложения предметом и акцентом.
3. Подготовь квадратный мастер не меньше 960×960. Важное помещается в центральных 70%, ниже остаётся спокойное место для настоящей подписи. Не рисуй шестиугольник, рамки, кнопки, название или статус внутрь картинки. Для нового изображения используй доступный генератор; для готовой картинки сохрани её смысл и происхождение.
4. Проверь мастер в реальной маске Сот: обычная и малая сота, светлая и тёмная тема, HTML-подпись. Не принимай обрезанные смысловые детали, неразличимые соседние обложки и изображение, которое мешает читать название. Изменение кадра не требует новой генерации.
5. Примени один существующий путь: [редактор и подписанные операции](references/runtime.md) для выбранной владельцем картинки; [операторский app-art](references/operator.md) для общего стандартного арта. Сохрани прежнюю версию. Проверь доступ → запись → чтение → перезагрузку; подготовленный файл сам по себе ещё не внедрён.
6. После reload проверь именно нужное живое поле: все видимые приложения и встроенные возможности, готовность изображений и отсутствие fallback. Передай краткий результат с точной областью и числом проверенных объектов: что сохранено, что создано, где мастер/версия и как вернуть прежний выбор. Непроверенные аккаунты и каталоги не включай в «все». Не объявляй художественную приёмку человека по автоматическому валидатору.

Различай типы сот по настоящему `entity.kind`, а не по форме, названию или инициалам: `app` — обложка приложения, `builtin` — встроенная возможность, `person` — профиль человека и его аватар, `community` — сообщество, `device` — устройство. Сота человека без фото может выглядеть как шестиугольник с инициалами; это не пропущенная обложка приложения. Не привязывай к ней app-art и не меняй чужой аватар. Сообщества и устройства учитывай отдельно; их оформление требует поддерживаемого пути и соответствующего поручения. Случайный недоступный ID или чужое закрытое приложение не расширяет доступ.

Для разовой генерации в Codex используй встроенный `image_gen`, если он доступен. Один заказ на набор означает ограниченный разовый набор, по одному целевому мастеру на приложение. Не запускай фоновое обновление, платный API или передачу личных референсов из одного факта наличия этого skill. Внутренний генератор Сот может быть не подключён: проверяй фактическую возможность, не обещай её по этому документу.

Личные фото и закрытые изображения не помещаются в публичный static каталог. Настройки доступа приложения и личность пользователя сохраняются. Новые обложки загружаются лениво и не должны задерживать открытие поля.
