# Native-подключения и границы доверия

Основание: проверка полного бизнес-приложения и прямое поручение пользователя 17.10.2026 сохранить повторяемый порядок. IDs, порты, конкретные credential-файлы и сервер одного проекта здесь намеренно не закрепляются.

## Права и реальные ресурсы

Проверь действующий Native контракт. Если человек уже разрешил вход, а документация данного сервиса предусматривает имеющуюся учётную запись, выполни обычный Native login без повторного запроса пароля человеку. Секрет читается только локально и не попадает в вывод. Для документного сервиса предпочитай узкий grant на конкретный новый документ, минимальный срок и отдельное разрешение публикации. Root SSO не заменяет Native grant.

Создай или найди точную сущность нового приложения, сохрани безопасные IDs и повторно прочитай их. Новое приложение не получает отзывы прежнего бизнеса или права других проектов. Native public-read подключение не называется managed-source SSO или доступом к административной записи.

Если sandbox мешает опубликованному виджету, допустим неизменённый официальный JS с provenance/SHA и узкий same-origin GET-прокси только прикреплённой публичной сущности. Фиксируй origin, пути, параметры, лимит ответа и timeout; не проксируй произвольный URL, auth/admin или запись. Проверь публичные ссылки виджета и его настоящий пустой/наполненный результат. Не публикуй тестовый отзыв ради проверки.

Документ проверяется по Native page/version/hash, сохранению и повторному чтению. Закреплённый публичный API-документ может иметь собственное представление в приложении; оно показывает фактический документ и проверяет его pin. Native HTML-reader, PDF-экспорт и собственное представление имеют отдельные результаты. Не объявляй неудачный экспорт готовым файлом и не обходи отзыв доступа локальным кэшем.

## Закрытый Native listener

Обычный isolated gateway остаётся первым вариантом. Native выбирается по действительной необходимости и проверенной модели доверия, из свежего экспорта и точного domain ID. Допустим закрытый loopback listener за серверной проверкой доступа Сот на каждый запрос, когда это явно выбранная авторизация приложения: fixed app/source digest, действующая owner/member ACL, отсутствие публичного обходного пути и отказ без сессии. Не подставляй human identity из app ID или заголовка.

Если backend намеренно принимает запись только от закрытого gateway, нельзя просто убрать Origin на открытом прокси. Перед такой адаптацией gateway обязан проверить реальные ACL и точный Origin небезопасного метода, включая отказ при отсутствующем Origin; только после этого допустима согласованная передача в закрытый listener. Публичный listener не получает административную запись. Нужны настоящие owner write → reload → восстановление fixture и anonymous/foreign-Origin отрицательные проверки.

Caddy применяется с CAS текущего файла, валидацией, проверенной зашифрованной резервной копией и подходящей текущему режиму запуска перезагрузкой. Не менять живую платформу, другие хосты или выдачу прав ради успеха проверки. Дополнительный CSP сохраняет собственные политики backend.

Проверяй активную вкладку, точный адрес и настоящее содержимое, а не только iframe.src или boot 200. Полный экран → возврат, отдельное окно, Native cookie/CSRF, PWA и передача файлов — разные сценарии. Блокировку браузера не обходи отключением защиты; используй только разрешённые штатные средства, сохраняй конкретное ограничение и альтернативную передачу уже подготовленного результата владельцу.
