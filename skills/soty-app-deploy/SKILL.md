# Разместить приложение в Сотах

Доведи существующий проект до работающего входа в Сотах. Сохрани его данные,
устойчивые IDs и действующий доступ. Повторное размещение того же проекта —
обновление имеющегося приложения, а не создание копии.

## Начать

1. Установи scope: проект/репозиторий, желаемое имя, владелец и аудитория,
   текущий Soty origin и сервер. Возьми известное из сессии и свежего состояния;
   обратимые технические решения прими сам. Не угадывай неизвестного владельца
   или разрешение открыть приватный сервис всем.
2. Найди актуальный репозиторий Сот и прочитай его AGENTS.md, если есть.
   Установщик записывает путь копии источника в agents/install-receipt.json,
   поле sourceRepository. Используй его для навигации и проверь наличие/Git;
   при устаревшем пути найди текущую рабочую копию.
   Прочитай docs/deployment/app-release.md и hosting-настройки. Снимок площадки —
   docs/deployment/platform-current.md; проверь его живым чтением перед изменением.
   Пути/IDs из старого отчёта служат навигацией, не доказывают текущее состояние.
3. Проверь git status. Не сбрасывай пользовательский checkout. Используй чистую
   подходящую копию/ветку; сохрани принятые изменения.
4. Для нового приложения применяй обычный isolated gateway. Если проект уже
   имеет собственные cookies/OAuth/приватные API, сначала прочитай
   [сохранение данных и авторизации](references/existing-data.md) и выбери native
   только после проверки его доверия и защиты. Эти режимы не взаимозаменяемы.

## Исполнить

1. Проверь существующий app ID через UI/подписанные операции владельца.
   Переиспользуй принадлежащий ему коннектор в той же границе доверия. Отдельный
   коннектор нужен при смене владельца/доступа/workspace, а не на каждую карточку.
2. Собери проект из одной revision, запусти loopback HTTP-сервис и проверь его
   реальные entry, assets, API, query и при необходимости WebSocket. При обновлении
   переиспользуй прежние volumes/секреты. Не копируй пустую базу поверх прежней.
3. Из корня репозитория Сот вызови:

       node scripts/soty-app-release.mjs init --project PROJECT --name NAME --port PORT --entry-path /

   Команда пишет строгий .soty/app.json без commands, URLs, credentials и grants.
   Если манифест уже другой, сравни намерение и исправь конкретную разницу;
   не удаляй файл ради прохождения проверки.
4. В интерфейсе владельца подключи устройство только при отсутствии действующей
   привязки. Одноразовый файл получают scripts/export-device-link.mjs с точным
   текущим origin. Не печатай код. Передай по доверенному каналу и после
   успешного claim удали обе временные копии. Привязка к другому владельцу —
   причина проверить аккаунт, не разрешение присвоить устройство.
5. Добавь проект через apps.register/UI, затем закрепи имя и выбери доступ.
   Для уже существующего app ID меняй источник штатным prepare/promote
   контрактом. Сохраняй requestId только для повтора того же запроса; при
   revision/epoch conflict перечитай и сравни, не перезаписывай чужое изменение.
6. Получи свежие «Данные размещения» в Настройки → Источник →
   «Размещение с агентом», либо сформируй тот же whitelist из подписанного
   apps.inspect. Схему и команды см. [контракт](references/contract.md).
7. Подготовь новый каталог выпуска:

       node scripts/soty-app-release.mjs plan --project PROJECT --deployment SNAPSHOT --output NEW_RUN

   Укажи конкретный domain ID при нескольких адресах. Для native добавь
   --mode native и только точные разрешённые --frame-origin. Сохраняй безопасные
   планы отдельно от секретов. applied=false означает, что ничего ещё не применено.
8. Проверь wildcard DNS/TLS текущей зоны. Уже работающую инфраструктуру не
   перенастраивай для каждого проекта. Для новой зоны/Caddy или native route
   используй [операции и проверки](references/operations.md). Не выпускай Соты
   повторно только ради новой карточки.
9. Если поручение включает публикацию, выполни её после конкретной подготовки
   и проверки отката. Иначе оставь готовый план для финального разрешения.
   Не требуй новое подтверждение уже порученной публикации.

## Проверить готовность

- CLI verify: точный HTTPS origin, entry с query, boot, реальные assets/API;
  он не следует redirect и не передаёт credentials. Для restricted используй
  авторизованный браузер, сохраняя выбранную аудиторию.
- Настоящий браузер: карточка Сот → правильный именной iframe → вход →
  чтение/запись проверочного объекта → reload. Старый entry видит тот же объект.
  Проверь также открытие отдельно, полный экран и возврат без смены iframe.
- Анонимный пользователь не читает закрытые данные; неверная предъявленная
  сессия не становится анонимным публичным входом. Для native неверный source
  digest закрывает ingress.
- При сохранении данных сравни прежние строки/IDs/права или проверенный экспорт,
  а не только количество записей. Offline drafts/outbox старого origin
  остаются доступны, пока перенос отдельно не проверен.
- Подтверди текущий serving image/revision, mounts, единственного writer,
  disk/active config и working rollback. Тесты и HTTP 200 не заменяют браузер.

## Сбои

После конфликта получи свежий снимок. После неизвестного результата signed
mutation повтори тот же requestId или перечитай подтверждённую историю.
После двух одинаковых ошибок останови слепой retry и проверь гипотезу: origin,
владелец, порт, readiness, DNS, query auth, CSP, callback, pin или актуальность
источника. Источник недоступен — не объявляй данные потерянными.

Не отключай TLS/браузерную защиту, не ослабляй общий sandbox, не экспортируй
private keys, не публикуй токены и не включай корпоративный режим из упоминания
Сот или компании. Не запускай старые one-off скрипты обмена доменов.

## Результат

Для массовой партии сначала прочитай [capacity.md](references/capacity.md):
текущая установка ограничивает владельца 100 app IDs, а leaf TLS имеет лимиты
issuer. Сотни/тысячи проектов требуют проверенного capacity и DNS-01 профиля;
не обещай неограниченное размещение из наличия одной wildcard A-записи.

Выдай рабочую ссылку приложения и ссылку внутри Сот, что создано/проверено/
внедрено, сохранность данных, существенные ограничения и место отчёта с точным
откатом. Если путь закрыт, оставь подготовленные артефакты и конкретный блокер;
не называй частичное размещение готовым.
