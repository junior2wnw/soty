# Разместить приложение в Сотах

Доведи проект до рабочего приложения. При обновлении сохрани его app ID,
пользовательские данные и доступ. Обычное подключение приложения не требует
обновлять сервер Сот, общий вход, DNS/TLS или Caddy.

## Обычный путь

1. Найди существующее приложение и коннектор владельца через текущий UI/API.
   Уточняй только неизвестные владельца и аудиторию. Не создавай коннектор
   на каждую карточку и не запрашивай повторно уже разрешённую публикацию.
2. Собери проект из одной версии и проверь работающий entry, assets/API и
   нужный WebSocket. Используй общий вход Сот через поддерживаемый Source SDK:
   для relay или уже допущенного workspace2 проверь фактическую поддержку Root,
   коннектора и SDK. Разделяй данные по проверенным issuer/subject; Native-адрес сам по себе
   не требует отдельного BFF/RP. Контракты: [вход](references/authentication.md).
3. Если приложение уже зарегистрировано и работает, используй его текущую
   карточку и не создавай новый манифест или выпуск ради повторного открытия.
   При создании через поддерживающий автоматическую регистрацию контур проверь
   job-bound результат и текущий app ID. Для неподдерживаемого контура или
   новой настройки источника используй действующий коннектор и соответствующий
   [контракт размещения](references/contract.md). `plan` не запускает приложение
   и не подтверждает публикацию; живую инфраструктуру переиспользуй.
4. Проверь карточка → приложение → вход → запись проверочного объекта → reload
   и серверный readback. Если есть отдельный адрес, проверь и его. Изменённая
   авторизация требует проверки двух людей, смены профиля и отзыва: старое окно
   получает прежнего человека или отказ, никогда данные нового профиля.

Если используется локальный CLI, актуальный checkout можно найти по
`agents/install-receipt.json → sourceRepository`; проверь наличие и Git, receipt
может устареть. При работе через подключённый инструмент используй его текущую
схему и права. Не ищи секрет вместо отсутствующего доступа и не выдумывай endpoint.

## Исключения — только когда они относятся к задаче

| Ситуация | Прочитать |
|---|---|
| Существующие cookies/OAuth/приватные API и данные | [Сохранение данных](references/existing-data.md), [вход](references/authentication.md) |
| Native, закрытый listener, iframe или скачивание | [Native-подключения](references/native-bindings.md) |
| Новая зона, ingress или обновление самих Сот | [Операции](references/operations.md) |
| Большой build, restore, очистка или откат | [Восстановление](references/recovery.md) |
| Пустое окно, поток, WS, вход или неизвестное сохранение | [Диагностика](references/troubleshooting.md) |
| Массовое размещение и ограничения площадки | [Ёмкость](references/capacity.md) |

Используй штатные CLI/publisher. Не добавляй отдельный оператор, копии внутренних
helpers и пакеты скриптов для каждой фазы; не повторяй уже встроенные проверки.
Обновление UI/документов и backend — самостоятельные выпуски, когда их контракты
совместимы. Исключения не превращаются в обязательные шаги каждого приложения.

Для первого полного выпуска бизнес-сайта действует пользовательский стандарт:
вход/защищённое управление, приватный feedback, Поведай, Переметрика, agent API/MCP
и гид с настоящим видео. Применимость и реальные права проверь по
[матрице модулей](references/standard-modules.md). Явный иной хостинг, запрет
публикации или узкий scope важнее стандарта; наличие инструмента не даёт прав.

## Необходимые границы

- Сохрани старые volumes/секреты/IDs. Не заменяй базу пустой; обязательные миграции
  выполняются до optional workers. Конфигурационные backup хранятся зашифрованно.
- Вход в ingress не устанавливает личность человека. Проверяй текущий профиль,
  собственные роли приложения и устойчивый issuer/subject; local user 1 не общий.
- При неизвестном исходе записи используй её readonly receipt/check/inspect.
  Не выдавай новый requestId и не повторяй неизвестную запись. При конфликте
  перечитай актуальную версию. После двух одинаковых ошибок проверь причину.
- HTTP200, load iframe и скачанный SDK не доказывают доступ и готовность данных.
  Для применимого подключения проверь право → вызов → сохранение → reload.
  CLI doctor и Root MCP apps_diagnose не выдают новых прав и не делают live inspection.
- Не ослабляй TLS, sandbox и ACL, не печатай ключи/коды/cookies/токены, не включай
  корпоративный режим из упоминания компании. Новое чувствительное согласие
  получает человек после доступной подготовки; прежнее разрешение не спрашивай снова.

Выдай рабочую ссылку и путь внутри Сот, что создано/проверено/опубликовано,
сохранность данных, существенные ограничения и точный способ возврата.
Частичное выполнение и автоматические тесты не заменяют фактическую приёмку.
