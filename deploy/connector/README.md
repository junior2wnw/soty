# Soty connector maintenance rollout

This is a separate Soty-only path. It does not import or execute deploy/traffic/rollout-server.sh. It never prints Docker inspect/config/Env/logs, and never writes an env-file. Original Config, HostConfig and requested network endpoint settings are cloned in memory; Image, exact image revision label and transaction ownership labels change. An explicitly reviewed optional application policy adds only its one pathname setting and one read-only nonsecret mount; the complete expected result remains fingerprinted. Anonymous data volumes are explicitly reattached by their inspected volume name. Candidate config is compared again after Docker creation/start, so unexpected daemon defaults fail closed.

No real Docker or production proof is claimed by the unit suite. Before using this code, root/controller must review an exact integrated image (including server/connector-maintenance.js) and run it against disposable synthetic Docker containers/storage, including fault cases. Candidate application image must have org.opencontainers.image.revision equal to the exact reviewed commit. Existing application tokens, auth, traffic, mounts, resource settings, ports, client and 3D processes remain outside rollout mutation scope.

## Operator CLI

Run on the server host with its existing Docker Unix socket and Node24, after supervisor review. Arguments contain IDs/hashes, never credentials:

```
node deploy/connector/cli.mjs prepare --original-id ORIGINAL64HEX --original-image sha256:ORIGINAL64HEX --candidate-image sha256:CANDIDATE64HEX --revision COMMIT40HEX --transaction UNIQUE16TO40HEX --journal /private/rollout-journal.json
node deploy/connector/cli.mjs promote --original-id ORIGINAL64HEX --original-image sha256:ORIGINAL64HEX --candidate-image sha256:CANDIDATE64HEX --revision COMMIT40HEX --transaction UNIQUE16TO40HEX --journal /private/rollout-journal.json --reviewed-receipt /private/supervisor-review.json --health-origin http://127.0.0.1:18182
```

Supervisor receipt fields: approved:true, migrationContract:"soty.stopped-legacy-snapshot.v1", originalId, candidateId, configurationSha256, revision, applicationPolicySha256 (null without the optional rule). The old legacyNoPendingWritesObserved flag does not authorize this contract. The CLI checks exact original, prepared candidate and config fingerprint. This file is an explicit review input, not a cryptographic owner-auth mechanism. Existing owner authorization and controller review remain required. Original must be named soty-online-chat with the exact immutable ID/image. Health origin must match the original loopback8080 port binding. The safe journal uses fsync+rename+directory fsync and an exclusive lock. A retained crash lock requires investigation, never automatic deletion or a second rollout.

Prepare creates only the uniquely labelled stopped candidate. Promote prechecks every nonterminal status, uses standard Docker stop?t=10 on the exact original, confirms it stopped, and records observed exit code/time. Node as PID1 can ignore SIGTERM; standard Docker stop may end with137. Do not call that graceful drain. No separate blind kill or stop of other processes is used. Unresolved stop retains the barrier. Offline `snapshot` strictly validates and fsyncs the renamed canonical JSON, hashes every normalized field and records existing `.next` hashes. A successful legacy mutation ACK/poll delivery followed rename, so an unobservable empty write queue is unnecessary. A timeout/failed mutation or RAM-only GET outcome is not proof of rollback or completion. See the exact [preservation contract](../../docs/connector-transport-migration.md).

Every offline nonterminal job, including leased/running/unknown or queued with prior attempts, fences the release with recovery_required and leaves the original stopped. It never restarts c0ca automatically in that state. Complete/partial `.next` files are preserved, never imported as authority. Enter binds a complete-state marker; all connector mutations return503 before callback/expiry while reads remain available. Candidate import and subsequent verify must match the original state hash and import byte hash. Only then may leave reopen traffic. Journals retain selected authority hashes/counts and temporary filenames, never raw protected data.

Temporary helpers run the candidate image command `node server/connector-maintenance.js status|snapshot|enter|verify|leave|rollback`; original Env/mount paths stay in memory. Helpers have no network/ports, readonly image root, no capabilities,768MiB RAM,0.5 CPU,64pids and bounded tmpfs. Status does no migration; snapshot adds full validation and offline legacy fsync. Enter and rollback require offline exclusive ownership. Rollback refuses changed complete state, accepted durable request IDs or active jobs before replacing/removing authority files. Its final legacy-json/count0/bytes/SHA receipt is followed by another complete-state comparison. Candidate readiness requires unchanged ready agentModelProxy/applicationModelProxy default model, transport and application path from /health, plus /api/connectors/storage-ready `{ok:true,schema:"soty.connector-storage-ready.v1",storageReady:true,maintenance:true}` before verify/leave.

## Failure boundaries

- Docker request waits have absolute10s bounds, and dropped responses are reconciled by exact owned ID/label plus observed state. Rename/start/stop confirmations never rely solely on response success.
- A missing helper after CREATE is looked up by the same exact name for at most60 polls,250ms apart; CREATE is not repeated. The journal records its nonsecret name, verb, ID when known and safe engine error code. A helper that has already run is never restarted. Unresolved CREATE/START retains the helper boundary, including during leave; no second status helper is launched across it. A late CREATE alone remains stopped with restart disabled and is not evidence of database mutation.
- Before leave, ordinary failure with a proven terminal-only offline baseline and no retained `.next` evidence stops the candidate, checks/exports complete legacy state if needed and restores the original name. The exported digest must still match. Maintenance is cleared while both servers remain stopped; only then may the SAME original ID start and pass health. Any retained `.next` prevents automatic legacy restoration: c0ca reuses its PID filename and could overwrite that evidence on heartbeat. Missing baseline, digest mismatch or any unresolved step likewise returns recovery_required rather than restored.
- An unresolved timed-out Docker stop may still complete later. It is not safe to claim the still-running original is restored. An unresolved maintenance helper might still be mutating storage. Both paths retain the barrier and require supervised exact-ID readback; they do not start another helper or execute blind recovery.
- Leave is the admission commit boundary. If its response drops, status reconciles the marker. Once leave was attempted, this implementation conservatively refuses automatic downgrade on any unresolved outcome; active new jobs/request identities must not be discarded.
- No original/retained candidate container is automatically deleted. Successful short helpers are removed without force/volumes. Unknown/failed helper objects remain for exact-ID supervisor inspection. There is no cleanup of arbitrary names, host services, Docker daemon, Caddy or clients.
- Real Docker endpoint defaults, rootless/usernamespace mount access and static-IP reservations require disposable-container proof. A config fingerprint mismatch or unsupported AutoRemove/container-network original rejects the operation before cutover.

## Standard STOP timeout and diagnostics

The only actions remain `prepare` and `promote`. Standard Docker STOP retains its grace10s, but uses a STOP-specific20s HTTP request deadline. All other Docker calls retain the default10s. After the single STOP request, up to60 read-only inspections run within a15s monotonic observation window; an in-flight inspect remains independently bounded10s and may extend that window. No POSTstop retry, blind kill or alternate recovery command is introduced. Any finite deadline can still be followed by late completion, so unresolved STOP keeps the existing recovery barrier.

The journal preserves `stopReconciliation` with the safe allowlisted initial action error, one action count, inspect total/success/error counts, last safe inspect status/error/running flag and observation duration. It excludes exception messages, Config, Env and helper payloads. `primaryFailureCode` retains the initiating safe rollout failure when a later recovery failure sets `failureCode`. A failure is never described as restored solely because the old container was still running during an ambiguous STOP.

Focused synthetic tests use the production-default DockerApi timeout setting, prove the STOP-only margin, reconcile late observed STOP without repeating it, and verify safe diagnostic retention through recovery failure. Actual Docker regression and controller authorization are separate required evidence.
