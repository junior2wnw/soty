# Soty Connect host controller

`host-controller.mjs` runs as a single host Node 24.15 process with Docker access. The application container receives no Docker socket. The whole host checkout is pinned to `revision`; only `modules/connect` is replaced by signed module updates. The trusted update engine is a reviewed copy in `deploy/connect/update-engine.mjs`, pinned with the host release. It must remain available even if the module is restored to an older version without a recovery export. Its equality test is a release gate, not a runtime dependency on the replaceable module.

Run `node /absolute/source/deploy/connect/host-controller.mjs /absolute/config.json`. The nonsecret configuration requires `source` (HTTPS), `trustFile`, `sourceRoot`, external `stateDir`, external `releaseDirectory`, `revision` (40 hex), `runtimeName` (`soty-online-chat`), `healthOrigin` (`http://127.0.0.1:18182`), `initialRuntimeHasConnect` and `backupCommand` (an argv array whose first element is an absolute executable and which includes the exact element `{containerId}`). `channel` defaults to stable, `deploymentId` to soty-dev, and `dockerSocket` to `/var/run/docker.sock`. Backup arguments are never interpreted by a shell. The bounded backup must return a JSON receipt containing `ok:true`, `encrypted:true`, an absolute `receiptPath` and a SHA-256 `sha256`.

Application activation also requires `storageProbeImage`, an exact `sha256:` image ID for an independently trusted Node 24 runtime. The host passes its own pinned `deploy/connector/storage-probe.mjs` source to that image; the candidate application does not attest its own data format. Older configs can be read for rebase, but a missing probe pin never permits a new application start.

For the first installation only, append `--bootstrap-release /absolute/signed-release.json`. This explicit local input uses the same signature, expiration, sequence, compatibility, test and full-image gates. It requires `initialRuntimeHasConnect:false`, the original baseline image and module sequence zero. There is no automatic network-to-file fallback. A failed initial installation that fully restores the baseline may retry; a completed installation may not bootstrap again. The reviewed module0.1.0 seed maps only to the original runtime without Connect. The first actual signed release is0.1.1, whose distinct tree maps to its own built image.

For an isolated synthetic Docker canary, set `canary:true`, a name matching `soty-connect-canary-[a-z0-9-]+`, and a separate loopback port other than18182. Use independent source/state paths and a disposable data volume. The controller does not manufacture synthetic model credentials or perform external model calls. A real canary must exercise the same Docker configuration and SQLite marker protocol before production activation.

## Ordering and data preservation

Before fetching a release, the controller acquires an exclusive host lock and verifies the pinned host source before loading a baseline or executing recovery. It then loads its journal, recovers any pending module transaction using the pinned engine, settles the corresponding exact Docker transaction and verifies the active code/runtime. Activation and settlement repeat the source check, including settlement attempted by an error handler. It does not steal stale host or module locks. The durable host journal contains only container/image identities, hashes, phases, the nonsecret restart policy and encrypted-backup receipt. Environment values, mount configurations, network settings, job identifiers and raw Docker/child errors are not written to it.

The full Docker build has a20-minute deadline and runs the independent typecheck/module/runtime gates in the pinned Dockerfile. A successful immutable image ID is durably mapped to the module tree hash before activation. Existing mappings are never overwritten. The original image also has a durable mapping. Restoring a module tree therefore selects the corresponding original image rather than rebuilding or accidentally reusing the failed image.

The controller preserves runtime configuration through the reviewed connector rollout `createConfig` helper, including realised anonymous volumes and requested network endpoints. It adds the read-only `/run/connect-releases` mount, `SOTY_CONNECT_RELEASE_DIR`, and the two required allowed origins. It checks work before stopping and again after the exact original container is confirmed stopped. It rejects all queued/running work and respects operator-owned maintenance. The stopped original's encrypted backup must finish before starting the candidate. Backup failure or a preactivation race restarts the original without starting the candidate.

The SQLite probe opens the existing database read-only, requires the modern schema, returns only a count and marker state, and never falls back to JSON. Only a marker owned by this transaction can be cleared. Candidate startup requires health, SQLite storage-ready, exact Connect capabilities, unchanged model routing/readiness and unchanged policy hash. After admission, the previous container is retained with auto-restart disabled. The new container keeps the original restart policy. On restoration the candidate is stopped and its auto-restart disabled before the old container's policy is restored.

Rollback changes code and the serving immutable image. It uses the same latest SQLite volume. It never restores a backup, removes database files, or invokes legacy `connector-maintenance rollback`. The old image must be a compatible reader of the actual durable rooms and Apps formats. A rollback after admission is also refused if new active work prevents a safe stop. The journal then requires operator attention instead of silently discarding work.

## Durable rooms and Apps format gate

Before candidate/original START, enabling any automatic restart policy, old offline restoration helpers and settlement of an admitted/restored transaction, the controller checks the exact image's `io.soty.storage.readers` label and the actual mounted data. The current full application Dockerfile declares `{"version":2,"readers":{"rooms":[1,2],"apps":[1,2,3,4,5]}}`. A copied container label or old rooms-only manifest is not accepted. The historical backend-overlay Dockerfile now fails before copying source or declaring labels: current server/modules/contracts/dependencies must be built together with the root Dockerfile. Reader metadata cannot prove dependency or module-API compatibility. The label is a release capability contract whose implementation still needs an exact-image canary; it is not evidence that arbitrary labelled code is safe.

The exact `soty.storage-format.v2` probe reports `rooms` as `"empty"|1|2` and `apps` as `"empty"|1|2|3|4|5`; `soty.storage-start.v2` binds both formats to the container, immutable image and mount hash. Old probe output or pending start/restart receipts cannot be promoted to this format. Rooms v2 SQLite takes precedence over retained JSON. Apps `/data/apps/registry.sqlite` requires marker `soty.apps-registry.v1` with SQLite `user_version` 0/1, or markers v2 through v5 with the matching version, readable required projections and exact known target/source/saved trigger definitions. Apps5 is saved-only; discussion Apps6 remains unsupported. Only an absent or genuinely empty Apps directory is empty; future Rooms3 and Apps6 are rejected. Exactly one explicit `DATA_DIR=/data` is required. Zero-length/corrupt SQLite, symlinks, orphan journals, unknown versions, volume subpaths, overlapping data mounts and another running writer fail closed. The probe reads WAL normally and never uses SQLite `immutable=1`; it recognizes formats, not every stored record or full index/constraint/database integrity. Malformed legacy JSON still requires the separate migration/restore gate.

The supported target is a standard Docker `local` volume with `Scope:local`, no driver options, and a mountpoint matching the inspected runtime source. The guard checks that profile before and after probing; bind targets and volume subpaths are unsupported. Its running-writer scan compares Docker volume names and lexical source overlap. The operating profile requires one managed writer and operator verification that no foreign bind/symlink, driver alias, host process or remote process writes the backing store; the scan does not prove their absence. This contract covers rooms and Apps only; other durable stores require their own compatibility gates.

The format helper receives only one read-only `/data` mount and does not copy the application container's environment or config/socket mounts. Docker still inherits the independently trusted probe image's defaults: inspect that exact image and its Node/runtime hooks separately. The helper has no network or ports, a read-only image root, bounded memory/CPU/PIDs/tmpfs and only `DAC_READ_SEARCH` capability to read existing ownership-protected data. The journal records identities, format and mount hash; helper creation/start is reconciled by exact identity without repeating an unresolved mutation. Completed helpers are retained without automatic restart. Missing `-shm` or rootless/user-namespace restrictions may cause SQLite on a read-only mount to fail; this deliberately blocks activation and must be tested on a disposable real Linux Docker volume.

The first Apps5 write needs a prebuilt, reviewed Apps5-compatible rollback image and a tested mapping/cutover, as did the earlier storage transitions. Existing source floor2 also requires a genuinely binding-v2-capable runtime, not merely an Apps5 format label. A JSON-only/unlabelled reader or Apps4-only image cannot be made compatible by changing a container label. This guard may intentionally leave both application containers stopped rather than start an incompatible reader. Do not substitute an older backup, delete either SQLite database or rewrite schema markers/receipts to make rollback pass. Selecting this new pinned host-controller generation before publishing the release is essential; an already installed older controller does not acquire the guard from a module update. The [Apps5 reader receipt](../../docs/implementation/p3-apps-v5-reader.md) separates local SQLite/synthetic-engine evidence from the still-required exact-image Linux gate.

## Interrupted operations

Docker create/start/stop/rename responses can be lost. The controller journals each mutating intent before submitting it and reconciles by the exact container identity and observed state. It never repeats an unresolved mutation. Helpers are bounded, have no network or published ports, and stay retained as evidence after completion. A helper whose creation/start cannot be resolved blocks further activation. The host and module journals remain available even when code restoration or host reactivation fails.

After a crash, an operator must first establish that the recorded controller process is no longer running before removing a stale lock. Do not delete `host-state.json`, the module state, image mapping, failed containers, markers or SQLite files to unblock an update. Verify the exact recorded action/container/helper; unresolved state is intentionally not interpreted as permission to start a second writer. After admission but before the module commit, recovery may require stopping work or explicit operator reconciliation. This controller is not a general database-downgrade tool or an automatic repair for arbitrary manual Docker changes.

The local tests cover signed-code update/rollback, immutable mappings, configuration preservation, encrypted-backup ordering/failure, an offline admission race, lost responses, unresolved starts, stale locks, no-fetch-before-recovery, actual read-only SQLite marker behaviour, WAL-aware rooms/Apps migration detection and refusal of incompatible rollback/restart policies. Run `node --test deploy/connector/*.test.mjs deploy/connect/*.test.mjs`. The Apps-specific evidence and remaining Linux/exact-image gates are recorded in [P3-A3](../../docs/implementation/p3-apps-reader.md).

## Moving to a reviewed whole-application revision

`rebase-host.mjs` prepares a new pinned generation. It does not build, activate, restart, rename or remove containers, execute a process in Docker, change systemd, or edit the old source and journals. The operator must stop the update timer and verify no controller remains active before invoking it. Existing locks require operator reconciliation; the helper never steals them. Immediately before preparation, use the read-only maintenance probe to verify no queued/running jobs or maintenance marker. The helper itself performs only Docker inspection and HTTP readiness checks, including exact Connect version, SQLite readiness, and idle inference. The usual controller separately repeats the work/maintenance gates when it later activates the candidate.

Prepare a clean checkout of the new reviewed commit at an independent absolute source path. Replace only its `modules/connect` baseline with the exact currently installed module tree. The future signed module must have a different tree and a greater sequence. Do not copy the old host journal to this source or reset its update sequence. Choose an unused external state directory and an unused config filename whose parent directories already exist.

```sh
node /absolute/source-NEW/deploy/connect/rebase-host.mjs \
  --old-config /absolute/config-OLD.json \
  --new-config /absolute/config-NEW.json \
  --source-root /absolute/source-NEW \
  --state-dir /absolute/state-NEW \
  --revision FULL_40_CHARACTER_COMMIT \
  --app-origin-template 'https://{appId}.soty.example.org'
```

The optional application origin must pass the controller's HTTPS subdomain policy. Omitting it preserves the old value. All other deployment identity, trust, update feed, channel, Docker socket, runtime identity, health and backup settings are copied from the existing configuration. There is no arbitrary policy override. The new generation sets `initialRuntimeHasConnect:true`; the already installed runtime must actually have Connect.

Rebase preserves an existing `storageProbeImage`. When migrating an older config without that field, it pins the already inspected active immutable image as the Node-only probe runtime and verifies that exact image exists. Its application reader label is irrelevant to executing the host-owned probe; it still cannot serve as a v2 rollback application reader. Rebase creates no helper container, reads no data volume and does not prove the later Docker mount/probe will work.

Preparation holds the old host and module locks together, rejects pending recovery, checks both Git revisions and changes outside Connect, compares both module hashes against the active image's tree, and verifies image/container revision labels and identities. The new host journal retains only that verified baseline image; its image revision remains the actual older build revision while the source revision becomes the new commit. The module journal retains the exact `lastSequence`, `releaseHash` and version, rebinds the target to the new canonical module directory, and sets `previous` and `pending` to null. Old backup/stage paths belong to the old generation and must not be transplanted.

Both new journals are synced before a complete config is atomically published with no overwrite. Old config/journal bytes are checked again immediately before publication and remain unchanged. The successful receipt says `prepared`, not deployed. The operator then explicitly selects the new controller/config and follows the signed-release and runtime verification process. Keep the timer stopped until that selection is verified; never operate old and new generations concurrently against one runtime.

If preparation fails after creating new state, it deliberately retains the incomplete, unpublished generation for inspection. It will not retry over existing state or config. If the final publication result is uncertain, inspect the new config and both journals before any action; do not infer failure means nothing was written. Reconcile the evidence or choose another unused generation path. Normal application rollback keeps the latest live data and requires a reader compatible with every persisted schema; restoring an older data snapshot is a separate recovery procedure, never an automatic part of this migration.
