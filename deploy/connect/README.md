# Connect: выпуск и обновление на ssh dev

Этот каталог — доверенная обвязка первого потребителя, Сот. Сам переносимый модуль находится в `modules/connect`. Новые проекты копируют модуль, подключают browser/server/UI и предоставляют свои операции проверки сборки и активации. Docker-контроллер Сот не подменяет их инфраструктуру.

## Источник и доверие

Публичный источник: `https://xn--n1afe0b.online/releases/connect/stable.json`. Каждый выпуск также имеет постоянное имя `release-N.json`. `stable.json` меняется атомарно и не кешируется; номерной файл никогда не перезаписывается. Подписаны версия, список файлов и их SHA-256, номер последовательности, совместимость, канал, срок и доля установки. Подпись Ed25519 проверяется до исполнения кода.

Корень доверия: `trust/root.json`. Он поставляется при подключении проекта через проверенный канал, а не скачивается вместе с непроверенным релизом. Сервер Сот читает каталог релизов через mount только для чтения; приложению недоступны Docker socket, private signing key и журнал updater.

Закрытый ключ выпуска и отдельный RSA-ключ резервных копий находятся на операторском Windows-компьютере в `%APPDATA%\SotyConnect\operator-keys.dpapi`. Они защищены Windows DPAPI текущего пользователя и ограниченными правами каталога; открытые ключи можно хранить в Git. Не удаляйте Windows-профиль без отдельного переноса/резервирования ключей. Это не облачное восстановление ключа. При его потере установленный сайт продолжает работать, но новые выпуски потребуют явной замены доверия. Компрометация корня также требует отдельной операции ротации; это небольшой single-role протокол, не полная реализация TUF.

`operator-keys.ps1 -Action publish -PublishConfig <absolute-json>` расшифровывает signing key только в памяти и передаёт publisher через stdin. Конфиг содержит абсолютные `directory`, `outputDirectory`, `trustFile`, `keyId: "soty-connect-2026-09"`, `channel: "stable"`, `rollout: 100`. Приватные ключи нельзя класть в этот конфиг, переменные окружения, аргументы команд или репозиторий. Publisher проверяет прошлые артефакты, выдаёт только безопасную квитанцию и повышает последовательность. По умолчанию срок принятия релиза — 90 дней. Перед истечением публикуется новый подписанный выпуск/квитанция с новым номером. Истечение запрещает новые установки, но не выключает уже работающие аккаунты.

## Жизненный цикл

На `ssh dev` обвязка живёт в `/home/ai2/.local/share/soty-connect/`:

- `source` — Soty checkout фиксированного Git-коммита, внутри обновляется только `modules/connect`;
- `state` — независимые журналы, блокировки и привязка отпечатков модулей к неизменяемым Docker image ID;
- `releases` — публичные подписанные артефакты;
- `backups` — зашифрованные снимки `/data`, runtime-конфигурации и файла application tokens;
- `config.json` — источник, публичное доверие, адрес локальной проверки, расположение кода и команда резервирования;
- `node/bin/node` — проверенный Node 24.15 из действующего образа.

Пользовательский systemd timer `soty-connect-update.timer` проверяет источник раз в шесть часов с небольшим случайным сдвигом. Включённый linger позволяет ему работать без SSH-сессии. Каждый запуск — новый процесс: обновлённый код не остаётся навсегда загруженным старым watch-процессом.

До сетевого запроса контроллер разбирает незавершённую локальную операцию. Затем проверяет подпись, последовательность, срок, текущую версию и совместимость. Автоматически принимаются совместимые патчи линии `0.1.x`. Локально закреплённые Dockerfile и host controller не заменяются подписанным модулем.

Перед активацией собирается полный образ с проверками типов, тестами модуля, прежнего identity-протокола, маршрутизации моделей и сохранности Connector. Базовые образы закреплены digest. Новый frontend получает собственный service worker и кеш сборки. Привязка проверенного дерева к конкретному image ID сохраняется до остановки сервиса.

Контроллер отказывается от переключения при выполняющихся/ожидающих Connector-задачах или чужом maintenance marker. Он подтверждает остановку единственного писателя, проверяет очередь повторно, создаёт зашифрованный снимок и запускает новый контейнер с прежними переменными, портами, сетями, томом `soty-online-chat-data` и файлом application tokens. Старый контейнер сохраняется; его автоматический запуск отключается, чтобы он не стал вторым писателем после перезагрузки Docker. При восстановлении возвращается исходная restart policy.

До открытия приёма задач проверяются готовность хранилища, модуль Connect и прежние параметры модельных маршрутов. Откат возвращает **код** и запускает совместимый старый образ на **последних данных**. SQLite не заменяется снимком и не откатывается до legacy JSON: отозванные устройства, использованные recovery-коды и выполненные задачи не должны оживать. Первое подключение использует явно записанный baseline без Connect и локально доставленный подписанный bootstrap-релиз; дальнейшие запуски берут только HTTPS-источник.

## Операторские действия

Проверка: `systemctl --user status soty-connect-update.timer`, `systemctl --user status soty-connect-update.service`, `journalctl --user -u soty-connect-update.service`. Квитанции и журналы содержат идентификаторы образов и хеши конфигурации, не значения секретов.

Пауза обновлений: создать пустой файл `state/paused`; работа Сот продолжается. Возобновление: удалить именно этот файл после проверки причины паузы. Для разовой проверки запустить `systemctl --user start soty-connect-update.service`.

После аварийного завершения lock не удаляется по возрасту. Сначала проверяются PID, Docker-процессы, фазы журнала и отсутствие другого updater. Только после доказательства отсутствия владельца оператор снимает конкретную stale lock и повторяет контроллер. Не запускайте два независимых механизма выкладки Сот одновременно.

Проверить зашифрованную копию на операторском компьютере: `operator-keys.ps1 -Action verify-backup -BackupFile <snapshot.enc>`. Расшифрованные настройки не выводятся и не сохраняются на диск. Восстановление базы из backup — отдельная аварийная процедура с учётом более свежих отзывов и задач; штатное обновление её не выполняет.

Срок хранения снимков пока не ограничивается автоматическим удалением. Следите за свободным местом; очистка старых образов, контейнеров и копий — отдельное решение после проверки действующих журналов и сохранности ключа восстановления.

## Границы первого выпуска

Аккаунты изолированы по проектам; общий вход на независимых доменах, passkeys и ограниченный гостевой режим телевизора требуют следующего протокола. Старые ключи комнат Сот не отзываются через новую кнопку устройства. Переключение профиля Connect не скрывает прежние локальные комнаты от другого человека в том же браузерном профиле. Сохраняются зашифрованные копии обычных комнат и текстов; вложения и права управления компьютерами автоматически не переносятся.

Обновления не стирают аккаунты, но очистка данных браузера пользователем всё ещё требует второго устройства или заранее проверенного файла восстановления. Абсолютное обещание «никогда не потерять аккаунт» без такого способа восстановления было бы неверным.
